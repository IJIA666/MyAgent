## 新增需求

### 需求: MCP 外部工具扩展自愈保活
系统应当（SHALL）对当前连接的外部 `MCP` 工具进程建立生命周期监测，若捕获到进程崩溃、退出或因超时挂死，系统必须（MUST）自动启动热拉起自愈模块，采用带有最大次数上限（如 3 次）的指数退避（Exponential Backoff）重连策略重新建立工具管道，保障扩展功能的运行可用性。

#### 场景: MCP 进程单次超时崩溃后热拉起重启
- **WHEN** 大模型调用 `tavily_research` 时触发网络超时崩溃，进程挂死断连
- **THEN** 客户端拦截该底层错误，触发重连哨兵守护，以 1s -> 2s -> 4s 退避序列自动拉起新 `MCP Server` 进程重建连接，在后续轮次中让工具正常回归可用。

### 需求: 超时等系统报错防幻觉重试
系统必须（MUST）在 `System Prompt` 中显式提供异常归因与重试响应的决策指令。明确区分“网络超时/基础设施繁忙等执行层异常”与“工具契约参数 Schema 不匹配校验报错”：
1. 面对前者，大模型必须（MUST）原参重新发起请求或直接报错返回用户，绝对禁止变动工具既定入参名称或擅自注入幻觉参数重试；
2. 仅在接收到确切的参数校验不通过异常时，才允许模型在对齐 Schema 后进行字段修正重试。

#### 场景: 大模型遭遇系统级网络超时原参重试或报告用户
- **WHEN** 大模型执行搜索调用并接收到 `Request timed out` 的底层基础设施报错
- **THEN** 模型通过错误区分指令判定其为网络瞬时异常，在下一轮中自动以原输入参数重新调用或直接告知用户网络不通，绝对不会尝试篡改参数名或自行想象出类似 `apiKey` 字段强行调用。
