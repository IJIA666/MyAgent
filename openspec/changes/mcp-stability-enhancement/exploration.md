# 探索主题: 会话 1782660662450.json 暴露的稳定性与可用性缺陷综合分析

## 1. 问题定义
在 `watcher-debounce` 变更落地后，通过新落地的 `systemReminder` 审计字段，我们在最新测试记录 [1782660662450.json](file:///d:/projects/MyAgent/.myagent/sessions/1782660662450.json) 中发现了三个相互交织的系统级稳定性与可用性缺陷：
1. **推理语言飘移**：大模型在应对“只读 Plan 阶段拦截限制”与“用户外部路径请求”的高强度规则博弈时，放弃了中文人设，本能倒向英文思考；
2. **MCP 进程雪崩**：外部 `tavily_research` 工具发生单次网络超时后，整个 MCP Server 进程崩溃，导致后续调用完全瘫痪；
3. **参数幻觉重试**：大模型将“系统级超时错误”误判为“参数错误”，在重试中盲目脑补出不合规的 `query` 和 `apiKey` 参数，造成 token 浪费。

## 2. 关键发现与调研结果
- **可观测性闭环**： 挂载在 User 消息上的 `systemReminder` 存盘属性成功运作，使我们得以首次白盒化审阅大模型在面对只读拦截时的思维路径与行为流，证明了上一变更方案的可观测性成效。
- **规则冲突博弈引发语言飘移**： 飘移的根源在于面临“C 盘跨路径请求”与“只读 Plan 阶段硬性拦截限制”的高负荷规则博弈。英文作为大模型更成熟稳健的语种被其本能激活为退化思维语种以维持逻辑紧密性；而工作区全英文技能描述仅为辅助的注意力偏置，并非决定性因素。模型最终输出仍是 100% 简体中文回复，整体无质损。
- **MCP 进程自愈保活缺失 (Respawn Defect)**： 第一次超时引发进程异常崩溃后，系统的 MCP 客户端未提供任何心跳监测或热拉起（Respawn）自愈机制，导致扩展能力随进程挂死而彻底瘫痪。
- **无归因的盲目重试 (Blind Retry without Attribution)**： 模型的 `reasoning_content` 仅写有 "The search timed out. Let me try again." 证明其缺乏底层对“错误类型区分”的能力。由于模型未对错误性质（是网络故障还是 Schema 参数不合法）进行定位归因，便盲目发起重试，从而导致其胡乱将 `input` 篡改为 `query` 并捏造 `apiKey` 幻觉字段。

## 3. 方案对比与推荐方向
| 评估维度 | 方案 A (推荐)：维持语言现状 + 落地 MCP 保活与防幻觉拦截 | 方案 B：全局强行惩罚推理语言 | 结论 |
| :--- | :--- | :--- | :--- |
| **进程高可用** | 解决崩溃自愈，进程可自动拉起重启 ✓ | 进程挂死问题无法解决 ✗ | 方案 A 占优 |
| **逻辑推演深度** | 保持英文思考，保留大模型对复杂博弈的处理精度 ✓ | 强行惩罚推理链会降低模型推理结构严密性 ✗ | 方案 A 占优 |
| **参数幻觉率** | 通过自愈报错或重试规则对重试动作进行防捏造参数拦截 ✓ | 仍无法遏制超时下的胡乱猜测 ✗ | 方案 A 占优 |

**推荐路径**： 选用 **方案 A**。
1. **对于语言问题**：保持现状（大模型仅内部使用英文思考，不影响最终中文回复），不作惩罚性强控，防范性能和逻辑退化；
2. **对于 MCP 崩溃问题**：在 MCP Client 驱动层引入崩溃热拉起与指数退避（Exponential Backoff）自愈机制；
3. **对于参数幻觉问题**：在 System Prompt 中显式提供“错误区分与响应引导规范”。明确区分“网络/执行超时错误”与“Schema 参数校验错误”的不同应对策略。遇到前者（网络故障或系统超时等基础设施异常），强制模型原参重试或终止并报错，绝对禁止篡改参数或注入 apiKey 等幻觉字段；仅在捕获到明确的“参数校验不合法”类型报错时，才允许模型在下一轮对齐契约微调入参。

## 4. 约束、风险与未知项
- **自愈循环死锁**： 若配置出错导致 MCP 启动即崩溃，热重启可能演变为频繁死循环，必须设定最大重试次数上限。

## 5. 否决方案
- **推理链强行拦截英文**： 可能会引发大模型推理阻断，引起模型报错或拒答，代价过大，故予以否决。
