# 探索主题: 文件检索性能瓶颈与假死防爆重构

## 1. 问题定义
智能体在运行中调用 `grepSearch` 或 `globSearch` 对工作区文件进行全文定位检索时，由于当前的递归遍历 `scanDir` 完全采用同步 IO（`readdirSync` / `statSync` / `readFileSync`），且缺乏对 `.venv`、`.myagent/temp`、`dist` 等无关庞大目录的过滤排除。当工作区稍微具有一定规模（例如包含 Python 虚拟环境或编译缓存）时，主进程 Event Loop 将被严重阻塞发生假死，甚至因为全量读取海量文件而触发内存溢出（OOM）崩溃，导致智能体核心的文件感知能力失效。

## 2. 关键发现与调研结果
- **代码库现状**：
  在 [search.ts](file:///d:/Projects/MyAgent/src/adapters/tools/tools/filesystem/search.ts#L11-L28) 中，`scanDir` 递归函数是全同步逻辑，过滤项属于硬编码。
  在智能体运行时，会全量把检索到的文件在主线程中加载并进行比对，造成极长的不可控等待。
- **核实与洞察**：
  经联网核实，处理 Node.js 大规模目录树遍历的最佳实践有两种：
  1. 使用专门为爬行优化的高性能库 `fdir`，其速度极快，过滤方便。
  2. 使用 Node.js 原生的 `fs.promises.opendir` API。与 `readdir` 将所有文件名一次性载入内存不同，`opendir` 提供了异步流式迭代器（Asynchronous Iterator），能够逐个输出目录项，将内存消耗降至极低，配合异步迭代器能优雅避开同步阻塞。

## 3. 方案对比与推荐方向
| 评估维度 | 方案 A (原生 `fs.promises.opendir` 异步流式迭代 + 自研极简信号量) | 方案 B (引入第三方高性能爬虫库 `fdir`) | 选型分析 |
| :--- | :--- | :--- | :--- |
| **依赖成本** | **零依赖，不需要增加包体积（手写信号量）** ✓ | 需要引入 `@types/fdir` 与 `fdir` 依赖 ✗ | 方案 A 占优 |
| **内存开销** | 极低（异步流式按需加载，无瞬间暴涨） ✓ | 低（库内部做了并发调优） ✓ | 两者相当 |
| **过滤灵活性**| 极强（可在异步生成器遍历时实时剪枝） ✓ | 强（提供 chainable API 过滤） ✓ | 两者相当 |
| **环境兼容性**| 强（使用 Node.js 核心 API，无向下兼容包版本包袱） ✓ | 中（存在因 Node 版本或打包工具引起的兼容问题） ✗ | 方案 A 占优 |

**推荐路径**：
**选择方案 A (基于 Node.js 原生的 `fs.promises.opendir` 异步流式生成器模式 + 自研极简信号量并发调度器)**。
为了彻底贯彻纯原生、零依赖的技术底座路线，在文件并发读取防爆句柄的控制上，我们拒绝引入如 `p-limit` 等第三方 npm 依赖包。我们将在工具层内部自研一个极简的（数十行代码）、基于 Promise 队列的信号量调度器，用于将 `fs.promises.readFile` 的同时打开数强制限制在安全区间（如 20~50 个），以此完美抵御系统文件句柄耗尽的风险，且不产生任何包负担。

## 4. 约束、风险与未知项
- **排除规则的目录级前置“剪枝（Pruning）”约束**：
  为保障检索性能呈量级跃升，排除规则判定逻辑在与异步生成器结合时，**必须在目录遍历的顶层即行拦截**。即当异步生成器迭代出某 `Dirent`，若判定其命中了排除目录（如 `.venv`），必须直接跳过，**严禁对其执行 `yield*` 下探**，从根源上避免进入该盘区的子目录树，而不是在叶子节点处过滤文件名。
- **文件描述符超载风险 (EMFILE) 防护**：
  在 Grep 检索中，通过手写的信号量调度器（Semaphore）包裹文件读取操作，实施滑动窗口并发控制，防止高并发扫描大型项目时，物理文件句柄耗尽。
- **配置化动态排除规则**：
  排除项（包括系统级默认排除项如 `.git`, `node_modules`, `.venv`，以及工作区自定义忽略项）由 `AppConfig` 的 `runtimeLimits` 动态注入，保证该优化工具在差异化工作区环境中的适配性。

## 5. 否决方案
- **同步全量加载方案**：彻底舍弃当前的同步 `scanDir` 方案，因其无法满足中大型项目开发的鲁棒性要求，且会导致智能体由于 Event Loop 卡死而引发严重的 Flaky 超时失败。
- **引入第三方并发包方案**：否决为了限流而引入额外第三方包（如 `p-limit`），避免引发包生态依赖包袱。
