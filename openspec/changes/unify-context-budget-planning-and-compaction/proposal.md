## 改造原因

当前上下文水位插件只估算一次消息历史，超过阈值后便直接执行中段压缩；压缩服务又无条件完整保留最新用户轮次，并在摘要生成成功后直接视为压缩成功。若受保护尾部本身已经过大，中段摘要可能无法使下一次请求回到安全水位，进而造成无效压缩、重复重启或连续压缩。现有读取去重和大工具输出卸载只能预防新内容膨胀，不能替代压缩触发时对完整请求的统一预算判断。

现在需要把自动与手动压缩收敛为同一条可验证的决策链：先执行可恢复剪枝并重新估算，再根据预测收益一次性选择中段或全量压缩，最后验证结果是否真正满足安全目标。

## 变更内容

- 新增统一的上下文预算规划行为，估算消息历史、系统前缀、工具定义、动态附件及模型输出预留共同构成的完整请求预算。
- 在语义摘要前对旧工具结果执行可恢复的结构化剪枝，并在剪枝后重新估算；若已恢复安全水位则跳过摘要。
- 在第一次摘要调用前预测中段压缩结果；预计收益足够时执行中段压缩，否则直接执行全量检查点摘要，同一次模型请求不得先后执行两种摘要。
- 压缩后重新估算新历史，只有实际缩小并回到目标水位时才原子提交；失败、空摘要、摘要膨胀或收益不足均保留原历史。
- 自动触发与 `/compact` 手动入口复用同一规划与执行链；手动入口允许显式请求全量压缩。
- provider 仍报告上下文溢出时最多重新规划一次，禁止形成无限压缩或重启循环。
- 首期不建设单条消息分块，不对普通 user/assistant 历史执行静默硬截断；异常摘要溢出必须保留原历史并明确失败。
- **BREAKING**：最新完整用户轮次不再无条件突破 token 预算受到保护；当受保护尾部使中段压缩无法满足安全目标时，规划器可以直接选择全量检查点摘要。
- **BREAKING**：`/compact` 不再被限定为只执行中段压缩，默认由统一规划器选择策略，并新增显式全量压缩语义。

## 业务能力

### 新增业务能力

无。

### 修改业务能力

- `context-compaction`：增加完整请求预算、可恢复剪枝、策略预判、全量检查点、结果验证和有限溢出恢复，并修改最新轮次保护与手动压缩契约。

## 影响范围

- 上下文压缩与水位触发：`CompactionService`、`TokenWatermarkPlugin` 及其 Hook 重启控制。
- Token 预算契约：`TokenEstimatorPort` 及完整 LLM 请求估算调用方。
- 摘要协议：中段历史摘要与全量检查点摘要需要明确区分输入范围和输出语义。
- 工具历史治理：复用 `read-file-stub-deduplication` 与 `tool-output-offloading` 的可恢复信息，新增旧工具结果的请求期结构化剪枝。
- 手动命令：`/compact` 的参数解析、策略选择、状态反馈与失败行为。
- 配置与测试：复用现有运行时阈值配置，更新 `context-compaction` 增量规格及相关单元、集成和回归测试。
- 不移动探索文件；设计依据继续保留在 `openspec/explorations/system-prompt-competitive-research.md`。
