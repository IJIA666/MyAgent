# 探索主题: 对话暴露问题分析与安全机制优化

## 1. 问题定义
- **核心问题定位**： 本次分析旨在解决在 `Plan` 模式下对终端命令一刀切拦截所导致的问题。重点改进拦截后对大模型的自愈引导不足，以及智能体对“专用工具优先”原则遵循度较低的系统性缺陷。

## 2. 关键发现与调研结果
- **代码库现状**： `terminal-guard.ts` 中 `READONLY_COMMAND_WHITELIST` 只硬编码了极少数如 `git status` 等命令，且在 `Plan` 模式下会对所有非白名单终端命令一刀切实施 `BLOCKED (Plan Mode Only)` 拦截。

- **自愈引导缺失**： 网关拦截后仅抛出冰冷的拒绝错误，没有向大模型提供任何建设性的改用只读工具或推迟执行等提示，导致大模型在失去行为退路后只能原地进行无效重试。

- **专用工具漠视**： 智能体在面对磁盘分析任务时，无视了“优先使用专用文件 API 工具”的指令，本能地偏向于使用通用的 `execute_command` 命令，从而引发了不必要的安全碰撞。

- **工具认知偏倚**： 系统提示词中“尽量使用工具”的强引导对终端 `execute_command` 工具产生了负面吸附。大模型将命令行也归入普通工具，为了满足调用工具以获取客观数据的偏好，会倾向于选择泛化能力最强但也最危险的终端工具。

- **竞品调研核实**： 调研证实 `Claude Code` 的 `Plan` 模式同样是不进行工具集物理裁剪的只读运行态，保持静态完整下发以维持高 `Prompt` 缓存命中。其拦截和限制完全发生在运行时网关执行层，通过拦截抛出 `Tool execution denied` 异常来实现安全约束。

- **权限扩展机制**： 系统内置了 `HumanApprovalPlugin` 机制，在文件读写 `API` 越界时会触发人机审批并将通过的物理路径加入临时白名单 `addTemporaryReadWhitelist` 中实现动态放行。但终端 `execute_command` 的工作目录 `cwd` 强制锁定在常规工作区，不支持此白名单机制。

## 3. 方案对比与推荐方向
| 评估维度 | 方案 A (工作模式感知) | 方案 B (细粒度命令分类) | 方案 C (工具完全下发隔离 - 推荐方向) |
| :--- | :--- | :--- | :--- |
| **防死循环** | 良好 ✓ (智能体能识别 Plan 约束) | 一般 ✗ (可能仍会尝试其他写命令) | 完美 ✓ (智能体在 Plan 模式下无此工具可选) |
| **查询能力** | 一般 ✗ (仍无法运行非白名单命令) | 极佳 ✓ (允许安全只读的系统查询) | 差 ✗ (彻底丢失所有终端查询能力) |
| **实施成本** | 低 ✓ (仅修改 Prompt 提示词) | 中 ✗ (需重构安全沙箱过滤逻辑) | 极低 ✓ (直接在 tools 传递层过滤剔除) |
| **安全性** | 中 ✗ (依赖智能体自觉与网关硬拦截) | 高 ✓ (细粒度分类不易产生漏洞) | 极高 ✓ (工具物理级隔离，无逃逸可能) |

- **组合方案推荐**： 建议保持工具定义的 100% 静态完整下发，绝对不执行运行时物理裁剪，以捍卫底座 `Prompt` 缓存命中率；转而通过安全网关拦截报错中的自愈引导与 `<system-reminder>` 气泡中的前置策略偏好实现双轨纠错防死循环。

- **错误自愈引导**： 在终端命令拦截错误中返回包含“引导性自愈提示词”的内容，明确指导大模型改用哪些只读文件 `API` 工具，或者提示其将高危修改操作记录在任务计划中。

- **高级扩展方案**： 针对外部路径扩展，可将 `subst` 挂载虚拟盘符与 `WHITE_LIST_ROOTS` 白名单配合作为“高级手动配置项”。因该方案具有 Windows 平台独占性且显著降低安全防护边界，不推荐作为系统内置的通用功能。

## 4. 约束、风险与未知项
- **平台兼容差异**： 细粒度只读命令分类规则在不同 `OS` 平台中存在别名差异，可能引入误拦截或越权漏洞。

- **隔离后遗留问题**： 彻底物理隔离 `execute_command` 后，智能体将完全失去只读的终端状态获取能力，可能影响某些复杂只读诊断任务。

## 5. 否决方案
- **纯规则字面限制**： 仅依靠 `Prompt` 级规则限制智能体在 `Plan` 模式下不要使用写工具。因为大模型具有不确定性，在没有底层沙箱和物理隔离保障下极易发生溢出和误操作，故予以否决。

- **运行时动态裁剪**： 在切换工作模式时对工具定义集进行增删和过滤。虽然可在源头阻断，但会导致大模型缓存面临大面积击穿，引起极大的交互延迟与额外成本开销，故予以否决。

- **AST 语法树解析**： 引入 bash-parser 对解包后命令进行语法树级分析。虽然泛化能力优于正则穷举，但 bash 语法树与 Windows PowerShell 完全不兼容，跨平台成本过高；且即便解析正确，写倾向的语义判定仍难以穷尽，故在当前 Windows 优先的场景下予以否决。
