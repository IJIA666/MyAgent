# 探索主题: Plan 模式终端边界与审批一致性

## 1. 问题定义
当前 `Plan` 模式下，用户在执行明显偏只读的 Windows 查询命令时，出现了三类相互冲突的体验：一是提示文案把 `dir` 归类为“写倾向或未识别命令”；二是系统会弹出审批；三是审批通过后命令仍会在执行期被拦截。该现象暴露的核心问题，不只是某一条命令是否够安全，而是 `Plan` 模式、终端只读观测、审批提示与执行期结构校验之间的边界定义并不一致，导致用户无法预期什么命令“理论上可批”、什么命令“实际上可执行”。

## 2. 关键发现与调研结果
- **代码库现状**：
  - `src/core/usecases/brain/prompts.ts` 明确规定了两层约束：其一，`Plan` 阶段必须优先使用只读原生工具做诊断，严禁把 `execute_command` 当作分析检索工具；其二，Windows 下只能执行单条原子命令，禁止 `|`、`>`、`<`、`%`、`;` 等复合连接、重定向和展开符号。
  - `src/adapters/tools/impl/system/terminal.ts` 中，`Plan` 模式的前置拦截只依赖 `checkCommandSafetyLevel(...)` 的结果；只要返回 `allow`，就不会在这里被 `Plan Mode Only` 拒绝。
  - `src/adapters/tools/impl/system/terminal-guard.ts` 中，`checkCommandSafetyLevel(...)` 采用“危险写动作正则 + 只读命令前缀白名单”的粗粒度判定。CMD 白名单包含 `dir`、`type`、`findstr`，因此 `dir /-C /w ...` 这类命令会先被视为“可进入下一步”的只读命令。
  - 同一文件中的 `validateCommand(...)` 又单独执行更严格的结构校验，直接拒绝所有包含 `|`、`>`、`<`、`%` 等复合符号的命令。因此，前置安全评级与执行期结构校验并非同一套规则。
  - `src/adapters/tools/impl/system/terminal-config.ts` 中的 `extractSafePrefix(...)` 只能为“命令 + 纯字母数字子命令”生成稳定前缀；像 `dir /-C` 这类合法但带参数的只读命令，无法形成可靠的持久授权前缀，进一步放大了审批文案与真实执行能力之间的脱节。
  - 会话证据 `.myagent/sessions/session_20260705T082547.285Z-9e5ec2b6-d99b-4fb3-842e-1ce7074a6659.json` 已证实该分层不一致确实发生在真实运行中：`wmic logicaldisk where name="C:" get size,freespace,volumename` 被 `Plan Mode Only` 直接拒绝；`dir /-C /w C:\Windows\Temp 2>nul | find " 个文件"` 被执行期以 `>` 为由拒绝；`dir /-C /w C:\Users\%USERNAME%\AppData\Local\Temp 2>nul | find " 个文件"` 被执行期以 `%` 为由拒绝。
- **核实与洞察**：
  - OpenCode 的 `plan` 是“只读分析代理”，默认拒绝文件编辑，但仍会在运行 bash 前请求用户许可；其安全文档还明确声明 permission system 是用户体验层的提醒，不是 sandbox，也不承担真实隔离职责。
  - OpenClaw 采用“trusted operator + sandbox mode”模型。默认主会话工具直接运行在宿主机上；若需要隔离，应按 session 和 sandbox 边界拆分。其文档明确把 exec approvals 定义为防误操作的 guardrail，而不是授权边界本身。
  - Hermes 明确把“操作系统级隔离”定义为唯一真实安全边界，并指出 approval gate、allowlist、pattern scanner 都只是进程内启发式控制，不构成 containment。它允许通过 terminal backend 把 shell/file 行为放进 container、remote host 或 cloud sandbox。
  - Claude Code 的本地分析资料也体现了相同倾向：`plan` 属于 permission mode，而 workspace trust 是独立边界；`prepareContextForPlanMode(...)` 甚至允许在 `plan` 中保留 auto 语义；同时 plan 文件读写是被显式允许的。这说明 `plan` 在竞品里更接近“工作模式切换”，而不是“彻底禁掉一切执行能力”。
  - 综合代码现状与竞品事实，当前问题既包含实现级缺陷，也包含设计哲学偏差。更合理的边界不是“Plan = 无终端”，而应是“Plan = 无副作用”；审批的职责也不应被误当成安全边界本身。

## 3. 方案对比与推荐方向
| 评估维度 | 方案 A：Plan 禁止一切终端 | 方案 B：Plan 允许严格只读、严格原子、可静态判定安全的系统查询 | 方案 C：Plan 放宽到语义上只读的复合 Shell |
| :--- | :--- | :--- | :--- |
| 体验一致性 | 高，但能力明显不足 | 高，且能覆盖常见只读观测 | 低，容易出现“看似只读但难静态判定” |
| 安全边界清晰度 | 高 | 高 | 低 |
| 与当前原子命令护栏的兼容性 | 高 | 高 | 低 |
| 实现复杂度 | 低 | 中 | 高 |
| 与竞品方向的一致性 | 偏弱 | 强 | 中 |
| 结论 | 过度保守，不推荐 | 推荐 | 风险过高，不推荐 |

**推荐路径**：将 `Plan` 重新定义为“无副作用模式”，而不是“无终端模式”。在该模式下，应允许极小集合、可静态证明安全的系统只读查询，但继续禁止复合连接、重定向、环境变量展开和脚本化语法；一旦命令最终会被执行期结构校验拒绝，前置审批层就必须同步拒绝，不能再弹出一个注定无法执行的审批框。对于复杂的只读诊断需求，应优先补专用只读工具，而不是放宽 shell 语法。

## 4. 约束、风险与未知项
- 若继续保留“前置评级”和“执行期结构校验”两套规则，就必须保证二者在允许集合上严格同构，否则仍会重复出现“审批成功但执行失败”的假阳性体验。
- 如果要在 `Plan` 中增加系统只读查询能力，需要先定义宿主机查询的边界，尤其是工作区外路径、磁盘信息、系统临时目录等宿主机状态是否允许被 `Plan` 观测。
- 若不补充专用只读工具，仅靠“单条原子命令”约束，很多常见诊断需求仍无法表达，产品体验会继续逼迫模型去生成本不应通过的复合 shell。
- 竞品普遍把审批视为操作护栏，而非真正隔离。若本项目继续把“审批”同时承担“提示、授权、安全边界”三种职责，后续规则设计会持续混乱。

## 5. 否决方案
- **继续维持当前的审批与执行分层脱节**：该方案会持续制造“可以审批但不可能成功执行”的假象，属于体验和语义双重错误。
- **直接放开 `|`、`>`、`%`、变量展开等复合 shell 语法**：这会把安全模型从静态可判定退化为语义猜测，不适合作为 `Plan` 模式的基础能力。
- **把 Plan 定义为彻底零终端能力**：这能减少规则复杂度，但会把许多本可安全完成的只读观测任务全部排除掉，且明显偏离 OpenCode、Hermes、Claude Code 一类竞品对 `plan/permission/sandbox` 的边界划分。
