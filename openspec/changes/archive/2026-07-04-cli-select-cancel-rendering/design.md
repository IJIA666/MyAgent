## 背景

当前 CLI 菜单使用 `@clack/prompts` 的高层 `select()`。该 API 在取消时内建了删除线渲染，而当前仓库并不需要这种语义。继续依赖高层 `select()` 会让展示层绑定第三方库的取消表现，无法只改取消帧而保留现有业务逻辑。

## 目标与非目标

**目标**

- 为仓库内所有单选菜单提供统一的取消渲染。
- 取消时只显示取消结果，不再显示删除线选项。
- 尽量保留现有菜单的选项、初始值、业务分支和调用方式。

**非目标**

- 不改动 `p.text()`、`p.confirm()`、`p.intro()`、`p.outro()` 等其它 Clack 交互组件。
- 不顺手重构 Slash Command 路由或 `InputListener` 生命周期。
- 不改变 `/workmode`、`/model`、主菜单的业务含义与后续状态流转。

## 设计决策

### 决策 1：引入仓库内单选菜单适配层

新增一个仓库内单选菜单适配函数，对外仍提供“传入 message/options/initialValue，返回选中值或取消符号”的能力，但把最终渲染控制权收回仓库内。

推荐实现方式：

- 基于 `@clack/core` 的 `SelectPrompt` 组装一个轻量适配器。
- 复用已有的 Clack 常量/辅助函数处理导航展示。
- 在 `cancel` 状态下自定义最终帧，只输出取消消息，不渲染删除线选项。

这样做的原因：

- 比自行重写整套键盘交互更小、更稳。
- 比 ANSI 清屏补丁更不依赖第三方内部帧序列。
- 可以一次性覆盖所有单选菜单调用点。

### 决策 2：取消时不再展示当前焦点项

取消不是提交，因此取消态不应继续展示当前高亮项。最终渲染应只表达“本次选择被放弃”，避免任何“该项被否决”的视觉暗示。

### 决策 3：单元测试锁定渲染语义

为适配层暴露可测试的纯渲染函数或稳定的渲染片段构造函数，测试以下约束：

- 取消态输出不包含删除线 ANSI 样式。
- 取消态输出不包含当前焦点项文本。
- 提交态仍可保留现有选中项展示。

## 风险与权衡

| 风险 | 缓解策略 |
| :--- | :--- |
| 适配层与 Clack 低层 API 绑定 | 保持实现尽量薄，只覆盖当前需要的单选能力 |
| 菜单外观与原始 Clack `select()` 略有差异 | 接受可控差异，优先保证取消语义正确 |
| 后续再新增 `p.select()` 调用点可能绕过适配层 | 用搜索与单元测试锁住当前调用点，后续 code review 继续约束 |
