# 探索主题: 将内置工具抽象为虚拟 MCP 层 (Virtual MCP Layer)

## 1. 问题定义
当前的 `simple-agent-core` 引擎将 `readFile`、`writeFile`、`listFiles` 等本地基础能力通过 Node.js 原生的 `fs` 模块硬编码在 `src/tools.ts` 中。这种做法导致大模型推理循环（Agent Brain）与特定的宿主执行环境（Host Environment）产生了紧密的物理耦合，限制了 Agent 未来向浏览器端或跨机器部署的灵活性，同时也没有在内部统一工具的调用协议标准（目前是原生函数调用与 MCP 远程调用双轨并行）。

## 2. 关键发现与调研结果
- **现有逻辑**：`src/tools.ts` 中写死了本地路径沙箱保护与文件读写逻辑。`src/session.ts` 中在处理大模型 Tool Call 返回时，需要分别判断该调用是命中本地函数还是远端 MCP 服务器。
- **业界对标（Claude Code / Hermes Agent）**：经过检索相关的 Obsidian 笔记，发现两大主流项目均采用了**“混合模式”**。即它们并没有激进地要求用户必须自行配置外部的文件 MCP Server，而是为了保障“开箱即用（Out-of-the-box）”的低门槛体验，依然内建了基础环境的执行权限。

## 3. 方案对比与推荐方向
| 方案 | 优点 | 缺点 | 结论 |
| :--- | :--- | :--- | :--- |
| **A. 维持原生硬编码** | 简单直接，无需改造 | 强耦合 Node 环境，调用路径碎片化 | 架构演进的阻塞点 ✗ |
| **B. 纯粹外部 MCP 化** | 极致解耦，核心引擎纯逻辑化 | 极高的新手配置门槛，破坏了开箱即用 | 不适合桌面级独立产品 ✗ |
| **C. 混合模式 (内置虚拟 MCP)** | 既保持开箱即用，又实现了协议级统一解耦 | 内部需要开发一套轻量的 MCP Server 适配层 | **最佳折中架构 ✓** |

**推荐路径**：采用**混合模式（内置虚拟 MCP 层）**。
在应用内部，保留原生文件的物理操作能力，但在架构边界上，将这些原生方法封装为一个符合 MCP 协议的 `LocalFileSystemMcpServer` 类。对于核心引擎的 `SessionManager` 而言，它眼中不再有“本地方法”与“远程 MCP”之分，所有的工具池一律通过标准化 MCP 协议进行获取与回调。

## 4. 约束、风险与未知项
- **协议转换开销**：在同进程内使用 MCP 协议格式（JSON-RPC）进行互相调用，虽然逻辑上解耦了，但可能会带来微小的序列化/反序列化性能损耗（针对极大数据流读写时需留意）。
- **生命周期管理**：目前的 MCP Client 默认是走 STDIO 拉起子进程，我们需要在 `mcp-client.ts` 中扩充对“内存级/进程内 MCP Server”的路由直连支持，避免真的去开辟子进程。

## 5. 否决方案
- **将文件操作推向独立进程的 MCP Server**：虽然非常干净，但要求用户在使用 Agent 前必须先行准备文件管理器的二进制服务，严重损耗了用户体验，故在当前阶段否决。
