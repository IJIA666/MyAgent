## 背景

在之前的加固中，系统将工作区路径限定在了 `process.env.AUTHORIZED_WORKSPACE_DIR`。当前的主控测试脚本 `run_testbed.ts` 已经实现了子进程级别的环境变量注入（即动态将测试盘符挂载为工作区，并在子进程中通过 `env` 传递给智能体运行）。这意味着，普通用户在本地运行此 Agent 时，根本不需要（也不应该）手动配置 `AUTHORIZED_WORKSPACE_DIR`。

在进行竞品调研后，确认主流项目同样没有暴露类似的物理工作区配置给用户。因此，本设计的技术落脚点不仅在于清理配置文件，更在于通过静态“警示注释”和动态“单元测试”双层防线，锁定 `loader.ts` 中的隐式环境变量加载逻辑，杜绝该隐式后门被重构工具或后续开发者视为 Dead Code 误删的重大隐患。

## 目标与非目标

**目标:**
- **配置净化**：从 `.env.example` 和本地 `.env` 文件中删除 `AUTHORIZED_WORKSPACE_DIR` 键值。
- **代码警示**：在 `src/config/loader.ts` 的工作区解析逻辑上，补充极致醒目的开发者警告注释，防止未来重构时误删。
- **测试锁定**：新建 `test/config/loader.test.ts` 单元测试，确保 `AUTHORIZED_WORKSPACE_DIR` 环境变量如果被删除，测试套件会以强阻断形式拦截构建，构筑 CI 级的防线。

**非目标:**
- **非目标 1**：不重构工作区路径的核心解析逻辑。不改变 `realpathSync(resolve(process.env.AUTHORIZED_WORKSPACE_DIR || process.cwd()))` 的回退和物理路径锁定行为。
- **非目标 2**：不对 `run_testbed.ts` 或其他评测框架逻辑进行改动。

## 架构决策

- **架构决策 1：采用隐式内部环境变量读取（方案 B）而非重构为命令行参数（方案 C）**
  - **原因**：目前测试框架利用子进程 `env` 注入非常成熟。如果改为命令行参数，主程序需要引入额外的 argv 解析库，并需要同时修改 `run_testbed.ts` 及其引用的多进程启动器。方案 B 以几乎为零的代码重构风险和改动代价，完美保持了对评测网的安全兼容。
  
- **架构决策 2：建立硬性单元测试防护网**
  - **原因**：静态的注释警告在面对大范围重构或自动化 Dead Code 扫描时有可能会被忽略。引入一个显式对 `loadConfig()` 识别 `AUTHORIZED_WORKSPACE_DIR` 环境变量的 Vitest 单元测试，从机制上确立了这一隐式读取不仅不是“死代码”，而是系统“被测的核心安全契约”之一。任何误删该代码的行为均会导致 CI 报错。

- **架构决策 3：测试用例采用安全的临时路径，避免污染外部环境**
  - **原因**：为了确保在干净的环境或 CI 服务器中运行测试时不会报错，测试用例应当在 workspace 目录下动态创建测试专用的临时目录，配置给环境变量运行 `loadConfig()` 后，再将其清理干净。

## 风险与权衡

- **风险点：误删隐式读取将导致靶场文件被物理污染甚至破坏**
  - **缓解策略**：在 `test/config/loader.test.ts` 中配置两项高强度断言：
    1. 验证没有环境变量时回退到 `process.cwd()` 的绝对物理路径。
    2. 验证设置该环境变量后，`loader.ts` 必须提取其绝对物理路径。这使该变量在重构阶段处于高度受控状态，无法在不改动测试的情况下被随意删除。
