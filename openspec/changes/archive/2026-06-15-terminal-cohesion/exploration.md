# 探索主题: 终端执行工具的高内聚架构重构

## 1. 问题定义
目前高阶终端执行工具 `terminal.ts` 已经顺利实现了沙箱隔离、流式截断、超时强杀和智能后台化功能。但该文件的体积过大（约 700 行），同时处理了进程管理、安全防御、持久化配置读写以及控制台 UI 交互四大职责，违背了单一职责原则（SRP），给后续维护及单元测试带来了潜在的复杂度。

## 2. 关键发现与调研结果
- **代码库现状**：`terminal.ts` 的 `executeCommandTool` 函数集成了白名单校验、安全正则审查、平台命令重定向、文件流溢写、进程 spawn 和双重超时逻辑。因为混合了交互逻辑（`readline` 界面），使得测试中测试后台缓冲观察期和执行流控时极易由于 UI 提问导致挂起，不得不强制设为 `YOLO` 模式。
- **核实与洞察**：根据优秀 Agent 的模块化实践，底层的进程控制引擎应是无状态、无 IO 交互的纯净底座。白名单审查属于安全拦截网关插件，而工作模式和白名单的持久化属于存储服务。将它们拆分后，不仅逻辑清晰，而且可以对白名单匹配、前缀提取、进程限流等功能分别进行高覆盖率的单元测试。

## 3. 方案对比与推荐方向
| 评估维度 | 方案 A (保持单文件集中设计) | 方案 B (拆分为多模块架构) | 结论 |
| :--- | :--- | :--- | :--- |
| 职责单一性 (SRP) | 弱 ✗ (混合了进程控制、安全正则、持久化与交互 UI) | 强 ✓ (职责完美分离，各子模块专注于自身领域) | 方案 B 占优 |
| 模块耦合度 | 高 ✗ (进程管理与界面交互代码直接杂糅在一个大函数内) | 低 ✓ (各组件通过解耦接口通信，支持插拔式引入) | 方案 B 占优 |
| 可测试性 (Testability) | 中 (编写底层流控测试时必须绕过或 Mock 繁杂的安全模式) | 高 ✓ (可以单独为白名单、路径校验或纯流底座写测试) | 方案 B 占优 |
| 调用与理解成本 | 低 ✓ (单文件全量导出，外部调用方直接导入引用即可) | 中 (外部需引用组合，但在 tools.ts 门面封装后对外部无感) | 方案 A 占优 |

**推荐路径**：选择 **方案 B**。
- 将 `terminal.ts` 纵向拆解为以下子模块：
  - `terminal-engine.ts`：负责原生的 `child_process.spawn` 执行底座、双重超时及流式防爆（Disk Spilling）的核心逻辑。
  - `terminal-guard.ts`：负责硬正则拦截、沙箱工作区 cwd 边界校验。
  - `terminal-config.ts`：负责工作模式和白名单允许命令的文件级 JSON 持久化存取。
  - `terminal-interactive.ts`：负责封装 `readline` 在控制台的询问交互，提供 Always Allow 的选择。
- 在 `tools.ts` 中通过 Facade 进行统一拼装并暴露给 `execute_command` 工具调用，实现对大脑层无感重构。

## 4. 约束、风险与未知项
- **循环依赖风险**：拆分后各模块（如 Config 与 Engine，Interactive 与 Config）之间存在相互引用，需要通过依赖注入（Dependency Injection）或者合理的参数传递规避循环导入。
- **交互冲突**：在大脑并发调用工具时，多任务同时要求进行人工交互，可能导致 stdin 输入混乱，重构时必须对交互提问做排队串行化处理。

## 5. 否决方案
- **YOLO 模式完全下沉到引擎**：曾考虑将 YOLO 模式判定完全合并到引擎底层，但由于工作模式还影响了其它文件安全工具的行为（未来可能扩展到 file 写入安全），因此应当由独立的 Guard 组件统一裁决，故否决。
