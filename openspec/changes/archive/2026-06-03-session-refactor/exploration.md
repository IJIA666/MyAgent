# 探索主题: SessionManager 重构分析

## 1. 问题定义
目前 `src/brain/session.ts` 承担了过多的职责，代码行数已达 400+ 行。作为一个智能体的核心大脑，它混杂了状态管理、网络请求、流式解析以及执行引擎的多重职责，这在长期维护中极易导致“上帝类 (God Class)”问题，违反了单一职责原则 (SRP)。

## 2. 关键发现与调研结果
在对 `session.ts` 及相关引用（`cli.ts`, `command.ts`, `index.ts`）进行代码审查后，发现其当前职责纠缠于以下三个维度：
- **状态持久与历史管理层**：维护 `sessionId`、`messageHistory`、以及静默落盘 `saveState/loadState` 和回滚 `rollback` 逻辑。
- **大模型驱动与流式解析层**：初始化 `OpenAI` 客户端，处理模型切换，并直接在 `chat()` 中解析 DeepSeek 的流式 `chunk` (包含特殊的 `reasoning_content`)，以及拼装 `tool_calls`。
- **智能体 ReAct 引擎引擎层**：控制大模型的 `maxIterations` 循环，对接 `ToolRegistry` 执行工具，并将执行结果组装成 `tool_call_result` 上卷回历史流中，同时负责调用 `AgentTracer` 写执行日志。

**核心洞察**：如果未来需要接入完全不兼容 OpenAI 格式的模型，或者想把会话存入 SQLite 数据库，都需要修改这个庞大的核心文件。

## 3. 方案对比与推荐方向

针对当前的代码架构，我们有以下重构路径：

| 方案 | 优点 | 缺点 | 结论 |
| :--- | :--- | :--- | :--- |
| **方案 A：按领域彻底拆分 (推荐)** | 彻底解耦。将 `SessionState`（状态与持久化）、`LlmDriver`（模型与流解析）、`AgentEngine`（ReAct 控制环）分离。 | 需要改变对外暴露的接口，可能要配合修改 `cli.ts` 与 `command.ts` 的调用方式。 | 能够支撑未来的长线架构演进。 |
| **方案 B：提取状态层，保留引擎** | 将落盘和回滚提取到单独的 `SessionContext` 中，但模型调用和工具循环仍留在主类中。 | 改动范围小，仅隔离了文件 I/O 逻辑。 | `chat()` 的 200+ 行深层嵌套逻辑未得到根本改善。 |
| **方案 C：暂不重构** | 没有破坏现有稳定逻辑的风险。 | 随着特性增加，该类将不可避免地走向 1000+ 行，成为技术债。 | 仅适合短期验证阶段。 |

**推荐路径**：建议采用 **方案 A**。我们可以先将持久化层与历史上下文分离为一个纯粹的 `SessionContext`，然后将模型请求剥离为一个 `LlmDriver`。`SessionManager` 退化为一个外观 (Facade)，专门负责协调它们以及调度工具引擎。

## 4. 决策结果
- 已与用户对齐，正式确认采取 **方案 A (彻底拆分解耦)** 进行后续的重构。

## 5. 约束、风险与未知项
- **对外接口兼容性**：`cli.ts` 和 `command.ts` 高度依赖当前的 `session` 实例方法，拆分时需考虑平滑过渡，或直接修改调用方。
- **状态一致性风险**：在重构流式处理（Streaming）和上下文快照（Snapshot）时，若拆分不当可能导致大模型回复上下文断层。
