## 背景

目前项目中的 `src/config.ts` 文件承担了配置定义、环境变量插值、模型默认参数映射、配置文件 I/O 与子进程变量隔离等多项职责，总代码量接近 400 行。在未来接入更多模型协议、集成外部工具（如扩展不同的沙盒运行时）时，单一文件内的修改极易引发代码冲突并造成模块间的相互影响。

## 目标与非目标

**目标:**
- 将 `config.ts` 彻底按领域（纯类型声明、模型元数据、环境沙箱安全、底层文件加载）进行物理拆分。
- 实现针对上游消费者（`index.ts`、`session.ts` 等）的平滑过渡，零侵入原有调用链路。

**非目标:**
- **不**引入新的配置存储引擎（例如不引入 SQLite，继续使用 json/env）。
- **不**构建厚重的面向对象服务类（Service Managers），保持现有的纯函数导出风格。
- **不**改变项目对外部环境变量（如 `DEEPSEEK_API_KEY`）的依赖结构。

## 架构决策

- **门面模式 (Facade)**: 创建 `src/config/index.ts`，重新导出内部所有的打散模块（`types`, `models`, `loader`, `mcp-env`）。理由：这是能够同时满足内部高内聚、对外“无痛迁移”的最佳妥协。
- **提取并复用通用工具**: 现有的 `interpolateEnvVars` 与 `requireEnv` 属于通用基础工具，不仅限于配置加载，因此沉淀至现有的 `src/utils/env.ts` 中。理由：这保证了 Utils 职责的纯粹。
- **分离子进程环境逻辑**: 建立 `src/config/mcp-env.ts` 存放 `SAFE_ENV_WHITELIST`。理由：沙箱安全与权限限制是个独立的关注点，它对配置有依赖，但自身逻辑极为封闭，剥离出来不仅能减小核心配置模块的体积，也有助于未来的权限扩充审计。

## 风险与权衡

- **[风险] `config/index.ts` 导出遗漏** → **缓解方案**：在迁移后立即运行 `tsc`（或 `npm run build`）以静态排查丢失的导出。
- **[风险] 环境变量加载顺序颠倒** → **缓解方案**：确保 `dotenvConfig()` 仍然保留在 `loader.ts` 最顶层的 `loadConfig()` 入口方法的第一阶段（仅在确保文件存在后），从而保证所有用到环境变量的地方都不会拿空值。
