## 背景

当前系统的 `RuleManager` 负责全局规则、局部规则及技能目录的加载与更新。在 `RuleManager` 初始化时，它会通过原生 Node.js 的 `fs.watch` 对工作区目录 `.agent/skills` 进行递归文件变动监听。然而，因为缺乏事件频控防抖机制，极易因外部编辑器（如 VS Code 缓存写入）或系统闲置扫描（如 Windows 索引器、安全软件扫描元数据）引起的多次细微变动事件，导致在一瞬间（通常在几十毫秒内）疯狂执行规则缓存刷新和系统提示词同步，进而引爆 CPU 并产生大量无效刷屏日志。

## 目标与非目标

**目标:**
- 在 `RuleManager` 监听器回调中引入 100ms 的轻量级防抖机制，合并瞬时密集的并发文件事件为单次有效加载。
- 确保系统在规则/技能被真实编辑保存时，能准确在 100ms 延迟后更新并同步 System Prompt。
- 消除高频多重触发导致的日志刷屏和 CPU 震荡。

**非目标:**
- 不引入外部第三方库（如 `chokidar`），维持系统“零外部依赖”与“最小侵入性”红线。
- 不修改 `RuleManager` 的规则加载、提示词拼装以及技能扫描的核心业务逻辑。

## 架构决策

- **手写 Node.js 防抖合并机制 (Debounce)**： 在 `RuleManager` 内部声明一个私有的 `watchDebounceTimer: NodeJS.Timeout | null = null` 定时器引用。在 `fs.watch` 事件触发时，首先调用 `clearTimeout(this.watchDebounceTimer)` 清除已有的计时器，再使用 `setTimeout` 延迟 100ms 执行加载。这确保了在元数据剧烈震荡期内没有任何新事件触发后，才会最终引发一次实质性刷新。
  - *Why X over Y?* 相比于引入 `chokidar`，原生 `setTimeout` 防抖实现仅需十行以内的代码改动，且能 100% 解决高频触发的抖动问题，完美契合最小改动原则，完全避免了第三方依赖带来的兼容性和体积负担。

- **[Amend 修正] 防抖单元测试验证**： 在单元测试中引入 `vi.useFakeTimers()` 模拟时钟挂起。通过连续高频模拟调用 watcher 变动回调，并执行 `vi.advanceTimersByTime(100)` 让虚拟时钟步进，从而以 100% 确定性的断言校验 `reloadRules`（或重载流程）仅被真实执行了一次，确保频控机制的正确性。

## 风险与权衡

- **[防抖触发延迟]** -> 由于设置了 100ms 防抖延迟，在实际手动修改技能/规则后，重载操作会往后顺延 100ms。因为该流程是异步热加载，100ms 的人体无感延迟完全不影响系统运行精度与智能体交互响应。
- **[内存泄漏风险]** -> 定时器如果在实例销毁时仍未触发可能会引发内存挂起。但 `RuleManager` 在应用程序的生命周期中为全局单例，随进程启动和终止，因此无需显式进行定时器清理，无泄漏风险。
