# 探索主题: 规则与技能热重载 Watcher 防抖机制设计

## 1. 问题定义
在 Windows 或其他主流操作系统上，由于编辑器保存动作、系统杀毒软件元数据扫描等外部行为，导致基于 Node.js 原生 `fs.watch` 的热加载机制（ `RuleManager` ）产生严重的高频并发事件抖动（Watcher Double-Fire）。因为当前代码缺少防抖合并策略，任何微小的文件读取或元数据碰触，都会在几十毫秒内向大模型及日志狂刷十几次重复的重载操作，进而导致 CPU 资源暴增与日志可观测性失效。

## 2. 关键发现与调研结果
- **代码库现状**： 经深挖源码，在 [RuleManager.ts](file:///d:/projects/MyAgent/src/core/usecases/brain/RuleManager.ts#L89-L106) 的 `initSkillsWatcher` 中，直接使用了原生的 `watch(skillsDir, { recursive: true }, () => { ... })` ，未做任何的频控与防抖逻辑。一旦底层触发变动，便无延迟同步拉起 `refreshSkillsCache` 与 `reloadRules` 。
- **核实与洞察**： 通过联网检索核实，原生 `fs.watch` 映射到底层操作系统的文件系统变更通知（如 Windows 上的 `ReadDirectoryChangesW` ），任何一次常规保存都可能产生数个元数据、文件长度和内容写入的分离事件。业界标准的轻量防抖（Debounce）合并时间设置为 `100ms` 至 `200ms` ，能有效解决该缺陷。
- **闲置触碰根源**： 即使在用户完全无操作的闲置期内，Windows 搜索索引服务（ `SearchIndexer.exe` ）或杀毒软件也会进行后台轮询，从而触碰技能目录下文件的修改时间（ `mtime` ）或访问属性。原生 `fs.watch` 极其粗糙，无法识别“内容是否变化”，属性一旦被触碰就会立即上报并触发重载。
- **终极去噪设想**： 除了 `100ms` 级别的防抖时间合并外，未来的最优演进方向是在 `RuleManager` 缓存刷新前，对技能文件夹的内容（如列表或文件大小哈希）进行快速极简的状态指纹（Fingerprint）对比。如检测到内容指纹完全一致，则静默拦截，避免任何实质性的重载，从而达成完美的抗噪能力。

## 3. 方案对比与推荐方向
| 评估维度 | 方案 A (推荐)：轻量手写防抖 | 方案 B：引入 Chokidar 库 | 结论 |
| :--- | :--- | :--- | :--- |
| **外部依赖** | 零依赖 ✓ | 需要额外安装第三方包 ✗ | 方案 A 占优 |
| **重构成本** | 极低（仅需 5-10 行修改）✓ | 需引入类型、调整依赖配置 ✗ | 方案 A 占优 |
| **防抖效果** | 100ms 级别毫秒防抖合并，满足当前需求 ✓ | 专业级，支持 awaitWriteFinish ✓ | 两者相当 |

**推荐路径**： 选用 **方案 A（轻量手写防抖）**。通过在 `RuleManager` 内部扩展私有属性 `watchDebounceTimer`，在事件到来时执行 `clearTimeout` 并用 `100ms` 的 `setTimeout` 延迟真正执行，以最小的侵入性消除高频事件引发的性能震荡与日志刷屏。

## 4. 约束、风险与未知项
- **无状态重叠**： 防抖重载在极罕见的并发写竞争下可能导致短暂的最后一次写未被读取，但因为 100ms 防抖时间极短，且最后一次事件必然会因为重新设置的 `setTimeout` 而在 100ms 之后被完整执行，风险基本为零。

## 5. 否决方案
- **引入 Chokidar**： 虽功能完备，但引入第三方包会破坏系统的“零外部包依赖”红线，增加无谓的代码体积与版本管理负担，故予以否决。
