## 背景

当前 `RULE_FILE_SANDBOX` 常量（`prompts.ts:11`）的后半段明确告知模型"一旦你尝试越权操作外部目录，工具将返回拒绝访问错误"。这是一种负面的执行结果预判，可能导致模型在推理层即自行拒绝调用工具，从而跳过工具层的审批流程。

跨项目对标（Claude Code、OpenCode、Hermes、OpenClaw）均不在 System Prompt 中使用此类结果预判措辞，而是将安全性完全交由工具层处理。

此外，多个文件系统工具的 `description` 字段使用"授权工作区内""受限的工作区沙箱内"等措辞反复暗示边界，可能叠加强化模型的自我审查。

## 目标与非目标

**目标:**
- 消除 System Prompt 中导致模型提前拒绝越界操作的负面预判措辞
- 将工具 `description` 中的边界描述从"禁止/受限"口吻调整为"默认边界 + 工具层处置"的中性口吻
- 确保 Agent 面对越界请求时仍会尝试调用工具，由安全策略层决定审批或拒绝

**非目标:**
- 不改变安全策略引擎的实际执行逻辑（`secureResolveWritePath`、`terminal-guard.ts` 等）
- 不移除工具 description 中的工作区边界信息（防止模型误以为工具无全盘访问能力）
- 不改变 `RULE_ERROR_HANDLING` 等其他系统规则
- 不改变审批流程的 UI 交互或策略配置

## 架构决策

### 决策 1：RULE_FILE_SANDBOX 措辞替换策略

**选择**：将负面预判半句替换为正向委托指令。

**新措辞**：
> 所有文件操作默认在授权的工作区目录下执行。不要仅因目标路径位于工作区外而提前拒绝用户请求——应正常调用工具，由工具层依据安全策略执行、请求审批或拒绝。

**Why**: 
- "默认在工作区内"保留了边界信息，不产生"工具无限制"的错觉
- "不要仅因…提前拒绝"直接针对问题根因，消除模型自我审查
- "由工具层依据安全策略执行、请求审批或拒绝"将决策权交还给工具层，与审批执行链路的实际行为一致
- 不承诺"越界一定会触发审批"——工具层可能直接拒绝，也可能审批，措辞保持诚实

**替代方案**：
- ❌ 完全移除边界描述：风险过高，模型可能误以为工具可全盘访问
- ❌ 仅删除后半句、不补充正向指令：未解决模型自我审查的根因，只是减少了一个暗示源
- ❌ 改为"你可以尝试越界操作"：过度鼓励，可能导致模型频繁发起越界调用

### 决策 2：工具 description 调整粒度

**选择**：仅调整含有否定/受限语义的措辞，保留默认边界信息。

**调整原则**：
- `"授权工作区内"` → `"默认在工作区内；外部路径由工具层依据安全策略处置"`
- `"受限的工作区沙箱内"` → `"工作区沙箱内"`
- `"禁止读写工作区外部路径"` → `"外部路径由安全策略管控"`
- 保留所有功能性描述（如"支持可选的行范围分页读取"）不变

**Why**：
- 工具 description 是模型理解工具能力的核心信息来源，不能移除边界信息
- 调整后的措辞从"命令式禁止"转为"声明式边界 + 委托处置"，与 System Prompt 的语义对齐
- 改动量小、风险可控，不改变工具的实际行为

**替代方案**：
- ❌ 移除所有工作区边界措辞：模型可能误判工具能力范围
- ❌ 在每个 description 中完整重复"由工具层审批"：冗余，委托语义已在 System Prompt 中声明

### 决策 3：终端工具 description 独立处理

`ExecuteCommand` 的 description 中"禁止读写工作区外部路径"与其他限制（禁止复合连接符）混合。此次仅调整与工作区边界相关的措辞，其他限制保持不变。

## 风险与权衡

| 风险 | 缓解策略 |
|:---|:---|
| 模型可能更频繁地发起越界工具调用，增加审批打断频率 | 可接受——这正是期望行为。若打断过于频繁，可通过调整 `ApprovalPolicy` 的频次控制来缓解，而非回退 prompt |
| 不同模型对措辞敏感性差异大，效果可能有波动 | 措辞保持通用、中性，不针对特定模型优化。需在不同模型上实测验证 |
| 过度移除工具 description 的边界信息导致模型误判能力范围 | 已决策保留"默认在工作区内"等边界声明，仅移除否定预判 |
