## 背景

当前 IJIA Agent 项目的代码库中广泛应用了 TypeScript，但在文档注释（TSDoc/JSDoc）的书写习惯上尚未完全统一。部分注释保留了 JavaScript 时代的 JSDoc 类型标记（例如 `@param {string} sessionId`），还有部分类或函数的入参在注释中没有清晰的破折号连字符分隔，降低了现代 IDE（如 VS Code）对 TypeScript 智能悬浮提示的渲染美观度，也给后续的代码文档自动生成带来了一定的不便。

## 目标与非目标

**目标:**
- 统一 `src` 目录下所有导出（Exported）的类（Class）、接口（Interface）、函数（Function）和方法（Method）的注释规范。
- 遵循官方 TSDoc 标准：完全剔除注释中的冗余类型声明（如 `{string}`、`{number}` 等），将类型表达留给 TypeScript 自带的静态类型系统。
- 统一参数描述语法为：`@param paramName - 自然语言描述`，统一返回值描述语法为：`@returns 自然语言描述`。
- 梳理并美化内部复杂实现的单行注释（`//`），使其逻辑层级分明。

**非目标:**
- **不引入 Lint 强校验**：本次重构不会引入 `eslint-plugin-tsdoc` 等静态分析插件，以免增加项目依赖复杂度和开发开销，完全通过本次重构手工统一。
- **不对非导出成员强制要求 TSDoc**：项目内的私有方法或未导出的辅助函数不作强制 TSDoc 要求，保持注释的轻量。
- **不对测试文件进行大规模补齐**：`test` 目录下的测试脚本不作为本次 TSDoc 补齐的范畴，仅聚焦于生产环境源码（`src`）。
- **坚决不改动任何业务逻辑与类型定义**：严禁在重构过程中修改任何实质性逻辑或变量命名。

## 架构决策

### 1. 注释格式的取舍 (TSDoc vs JSDoc)
对于 TypeScript 编写的系统，选用 TSDoc 是业界的最佳实践。
- **决策内容**：使用标准的 `/** ... */` 写文档注释，参数使用 `@param name - 描述` 的破折号风格。
- **决策理由**：TSDoc 去除了传统 JSDoc 在 `{}` 中标注类型的语法。由于 TS 已经是强类型，在注释中重复标注 `{string}` 会带来二次维护成本，一旦类型改变而注释未改，将产生致命误导。使用 TSDoc 可以完美适配现代 IDE 渲染，且对 TypeDoc 等生成工具有极佳的兼容性。

### 2. 行内注释规范
- **决策内容**：对于函数内部实现，统一使用 `//` 进行单行注释，每条注释与上一行代码保持一个空行（若前面有代码），且在 `//` 之后保留一个空格。
- **决策理由**：保持代码排版的呼吸感，避免代码块过于拥挤，增强逻辑步骤的连贯性。

## 风险与权衡

- **[风险] 频繁合并冲突**
  - **描述**：由于本次变动涉及 `src` 目录下的多个文件，若其他开发者同时在修改这些文件，会导致严重的合并冲突。
  - **缓解策略**：由于注释修改不涉及逻辑变更，我们在生成具体 tasks 后，应以“快准狠”的节奏一次性完成修改并提交，尽量缩短合并窗口。

- **[风险] 人工修改遗漏**
  - **描述**：大面积的手工重构可能遗漏部分文件的导出项。
  - **缓解策略**：逐个模块目录（`action/`, `brain/`, `config/`, `interface/`, `utils/`）依次清点，对照 `index.ts` 暴露的门面接口，确保所有导出的 API 均已覆盖。
