# 探索主题: 项目代码注释风格统一

## 1. 问题定义
当前项目（IJIA Agent）存在注释风格不统一的问题，具体表现在 JSDoc/TSDoc 的格式不一致（例如部分包含类型声明，部分参数或返回值缺少描述等），这在 TypeScript 环境下产生了类型冗余，并影响了 IDE 的悬浮提示体验。本探索旨在确立统一的注释规范，消除代码与文档在表示类型时的冗余，提升代码可读性与可维护性。

## 2. 关键发现与调研结果
- **代码库现状**：
  - 核心模块文件（如 `src/brain/context.ts`、`src/brain/TokenEstimator.ts`）中已经广泛应用了 JSDoc/TSDoc 风格的文档注释，但存在冗余的类型标注（例如 `@param sessionId 可选...` 中夹杂对类型的中文重复解释，或在其他地方混用 JSDoc 的 `{type}` 标注）。
  - 函数内部包含大量中文单行注释（`//`），能较好地梳理流程。
- **核实与洞察**：
  - 经联网核实，在 TypeScript 项目中，首选采用 TSDoc 规范。
  - TSDoc 作为 TypeScript 官方标准，不建议在注释中包含冗余的类型信息（如不写 `@param {string} name`），而直接使用 `@param name - 描述` 的形式，把类型定义交给 TS 编译器本身，从而避免注释与代码定义不同步的维护代价。

## 3. 方案对比与推荐方向
| 评估维度 | 方案 A (轻量规范) | 方案 B (标准 TSDoc - 推荐) | 结论 |
| :--- | :--- | :--- | :--- |
| **覆盖范围** | 仅限类和核心函数头部，不强制写 `@param` | 所有导出的 Class、Method、Function、Interface 等 | 方案 B 能最大化保障公开 API 的文档完备性 |
| **TS 契合度** | 一般，类型提示不完全 | 极高，去除冗余类型，利用 TS 原生类型，IDE 悬浮提示极佳 | 方案 B 占优 |
| **维护成本** | 低，开发开销小 | 中，需要维护参数与返回值说明 | 方案 B 成本在可接受范围内 |
| **生成工具支持** | 较弱 | 完美支持 TypeDoc 等文档生成器 | 方案 B 占优 |

**推荐路径**：
使用**方案 B（标准 TSDoc 规范）**。在项目所有导出（Public）的类、接口、函数与方法上，使用不带类型信息的 TSDoc 风格注释。对参数使用 `@param paramName - 自然语言描述` 语法，对返回值使用 `@returns 自然语言描述` 语法。内部复杂逻辑使用行内单行注释（`//`）进行分步表述。这一规范达成了文档完备度与维护成本的最佳平衡。

## 4. 约束、风险与未知项
- **代码修改范围**：若对整个项目的所有文件进行大面积注释修改，可能会导致 `git diff` 产生大量微小变动，增加冲突风险。因此建议在重构或新增功能时逐步按此规范应用，或者在非活跃分支上进行集中统一。
- **Git 操作限制**：根据项目全局规则，严禁执行 commit/push 等 Git 操作，因此注释统一方案的执行结果需提交给用户手动进行版本管理。

## 5. 否决方案
- **全面严苛规范**：由于其强制对项目里所有私有方法、辅助函数、局部属性均补全严密的 TSDoc 描述，并在 ESLint 中开启强制检查，这在小规模快速迭代的项目中开发成本过高，且容易导致后续重构时注释与实现脱节，故予以否决。
