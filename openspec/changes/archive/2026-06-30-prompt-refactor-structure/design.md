## 背景

在当前的系统提示词管理文件 `src/core/usecases/brain/prompts.ts` 中，核心指令集 `BASE_SYSTEM_PROMPT` 作为一个整体模板字符串硬编码在代码中。9 条红线规约混排在一起，职责异构，缺乏物理隔离。这带来了序号手动编号易出错、修改时容易误伤相邻规则的维护隐患。

## 目标与非目标

**目标:**
1. **常量化抽取**：将 `BASE_SYSTEM_PROMPT` 中 9 条核心红线指令分别提取为独立的 TypeScript 常量，实现物理隔离，便于逻辑寻址与测试。
2. **自动装配与序号自愈**：在模块冷启动加载阶段（Compile Once），通过数组 `map` 赋予序号并拼接成最终的 `BASE_SYSTEM_PROMPT`，实现规则序号自动生成与排序自愈。
3. **Prefix Cache 100% 友好**：重构在 Node.js 模块冷启动加载时仅执行一次拼接，会话期间保持只读，对大模型侧透明，完全不影响前缀缓存命中率。
4. **单测防护网**：引入单元测试，一方面断言最终渲染后的系统提示词不再包含冷启动替换的占位符（如 `{{OS_SECURITY_INSTRUCTIONS}}`），确保占位符被成功消费；另一方面校验所有抽取的规则常量是否全部被完整装配进 `BASE_SYSTEM_PROMPT`，防范装配遗漏。

**非目标:**
1. **不做运行时动态拼接**：坚决不在每次请求运行时动态拼装，避免因引入会话级或时间戳变量导致大模型前缀缓存大面积失效。
2. **不改变提示词语义**：本次重构仅改变代码组织结构，不改变任何提示词的具体语义。

## 架构决策

我们采纳 **冷启动模块常量抽取 + 数组 map 自动装配** 的重构方案。

### 方案对比与抉择理由
- **对比方案 A (维持现状)**：虽然 100% 保证缓存命中，但规则序号全手工修改、缺乏物理隔离，容易污染相邻规则。
- **对比方案 B (运行时动态拼接)**：在每次 API 调用时才拼接规则。这虽然具备物理隔离与自愈能力，但极易在 turn 过程中误引入会话级或请求级变量，导致 Prefix Cache 命中率下降。
- **选择方案 C (本方案)**：在模块冷启动时仅进行一次编译拼接，会话期间只读。对模型侧而言，最终的字节流没有任何改变，不仅 100% 缓存友好，而且完美解决了方案 A 的手工维护序号及防手滑污染问题。

## 风险与权衡

- **风险：规则常量装配遗漏**
  - **描述**：由于将大文本块拆分为了多个独立的 `RULE_*` 常量，如果开发者在装配数组 `SYSTEM_RULES` 中遗漏了某项，会导致该红线规则在最终的 `BASE_SYSTEM_PROMPT` 中丢失。
  - **缓解策略**：在单元测试中，使用反射或导出变量校验，断言每一个导出的规则常量都必须是 `BASE_SYSTEM_PROMPT` 的子串；同时校验最终文本里不存在 `{{OS_SECURITY_INSTRUCTIONS}}` 占位符。
