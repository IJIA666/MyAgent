# 探索主题: 智能体网站登录与浏览器控制方案

## 1. 问题定义
为现有的极简 TypeScript 智能体（IJIA Agent）设计并集成一套登录任意网站的核心能力。重点解决在智能体自动化控制浏览器时面临的以下两个痛点：
1. **登录风控破解**：如何安全地应对网站的扫码登录、短信验证码、图片滑动验证等高强度人机验证机制。
2. **状态持久化与复用**：如何使智能体在后续的任务中保持已登录的会话状态，避免每次运行都需要重复人工登录，保障自动化的流畅度。

## 2. 关键发现与调研结果
- **代码库现状**：
  - 目前智能体为 TypeScript 命令行工具，入口位于 [index.ts](file:///d:/Projects/MyAgent/src/index.ts)。
  - 其工具调用体系在 [toolRegistry.ts](file:///d:/Projects/MyAgent/src/action/toolRegistry.ts) 中管理，分为本地文件系统的虚拟 MCP 服务与外部真实的 MCP 服务。
  - 目前项目中没有任何浏览器控制或网络请求模拟的动作工具，需要进行全新的包依赖引入与 Action 挂载。

### 跨项目竞品分析与核实
通过对 [Agents](file:///d:/Projects/Agents) 目录下全部 7 个参考项目的深度检索与分析，我们提炼了它们在浏览器自动化与登录会话管理上的竞品对比：

| 参考项目 | 浏览器控制实现 | 登录/会话保持方式 | 鉴权风控应对 |
| :--- | :--- | :--- | :--- |
| **hermes-agent** | 通过 `agent-browser` 命令行守护进程操作本地 Chromium，或通过 HTTP 连接 Browserbase 等云端浏览器。 | 本地默认为基于 Task 的 uuid 随机 Session（瞬时）；支持 `/browser connect` 开启 CDP WebSocket 调试直连本地浏览器共享 Session。 | 默认无头模式无法过验证。但可通过 CDP 端口（9222）直连，直接复用用户在常用浏览器中已登录的会话，免密过验证。 |
| **claude-code** | 主体是轻量级 CLI 工具（通过 `curl` 与 JSDom 静态解析）；在自动化验证（Verifier Skill）中，引导用户引入本地 `Playwright` 自动化测试库或配置 Chrome DevTools MCP、Claude Chrome Extension。 | 建议在运行环境中使用环境变量（如 `TEST_USER` / `TEST_PASSWORD`）安全存储登录凭证，避免明文硬编码。 | 在技能指令中显式配置登录页面 URL、表单输入节点、并以重定向 URL 或页面特定标志元素作为 Post-login 登录成功判定，实现自动化表单登录验证。 |
| **tinypace-ai-desktop** | 桌面级 Electron 应用。主程序并没有内置浏览器控制动作，而是通过 `ProxyMCPServer` 聚合管理所有 stdio/sse/http 类型的 MCP 插件。 | 自身不管理会话，完全下放给挂载的外部自动化 MCP 插件自主管理。 | 依赖外部 MCP 的滑块/验证码破解能力。 |
| **opencode / openclaw** | 主体不包含内置浏览器交互 Tool，主要通过静态抓取或 API 操作，其 `playwright` 关键字仅用于自身 E2E 冒烟与回归质量测试。 | 无内置的登录控制。 | 无相关能力。 |

### 核心设计启示
1. **结合 Hermes 的 CDP 直连思想**：通过 Playwright 的 `chromium.connectOverCDP` 接口，支持直连用户本地已经开启远程调试端口的 Chrome 浏览器，直接共享已登录状态，对滑块/扫码等高强度安全防护能起到天然豁免的作用。
2. **结合 claude-code 的验证器登录与风控应对思想**：
   - 对于本地自主启动的独立浏览器，支持配置登录 URL 和环境变量中的 `TEST_USER`、`TEST_PASSWORD`，并在 Playwright 中以判定特定元素或重定向地址的方式判定自动登录结果。
   - 当遇到风控人机阻碍时，利用有头模式（`headless: false`）阻塞并提醒用户在弹出的浏览器中手动进行验证/扫码，完成后按回车继续，以实现最实用的“智能体+用户协同”风控过线方案。
   - 结合 Playwright 的 `launchPersistentContext` 接口将 Cookies、LocalStorage 缓存到本地物理目录（`.myagent/browser-session/`），实现二次访问静默登录。

## 3. 方案对比与推荐方向
| 评估维度 | 方案 A：内置 Playwright 原生 Action (融合版) | 方案 B：外部 Puppeteer MCP | 方案 C：静态 Cookie 注入 |
| :--- | :--- | :--- | :--- |
| **滑块/验证码/扫码应对** | **极佳** ✓ (支持有头窗口供用户手动扫码，或直连本地运行中浏览器免扫码) | **差** ✗ (无头模式下智能体无法应对风控) | **极佳** ✓ (用户在自己浏览器登录后提取) |
| **登录态保持** | **高** ✓ (可通过本地持久化 Profile，或直连 CDP 共享浏览器会话) | **中** ✗ (需额外处理外部服务的挂载卷配置) | **高** ✓ (手动导出/导入保存) |
| **工程依赖成本** | **高** (需引入 `playwright` 并下载浏览器内核) | **低** (主程序无依赖，仅需配置外部 MCP 节点) | **极低** (仅需 `fetch` 或 `axios`) |
| **智能体网页交互能力** | **极佳** ✓ (直接调取 DOM、截图，可对 DOM 节点映射简化标号) | **良好** ✓ (支持交互与截图，但需通过 MCP 通信) | **差** ✗ (无浏览器引擎，仅限抓取静态 HTML/接口) |
| **最终评估** | **推荐选用**。综合了 Playwright 本地持久化控制与 Hermes 的 CDP 直连思想，功能最全面。 | 放弃。难以解决人机校验等前置登录阻碍。 | 放弃。每次 Cookie 过期都需人工频繁更新，体验不佳。 |

**推荐路径**：
选择 **方案 A：内置 Playwright 原生 Action (融合版)**。
- **两用登录通道**：支持在 Native Tool 中指定 `cdpUrl` 参数或配置。如果配置了 `cdpUrl`，通过 `connectOverCDP` 共享用户本地运行中浏览器的登录态；否则使用 `launchPersistentContext` 启动具有持久 Profile 目录（`.myagent/browser-session/`）的内置浏览器，支持有头模式（`headless: false`）供首次人工扫码/过验证登录。
- **DOM 标号映射**：在网页 Snapshot 的文本输出中，参考 Hermes 设计对可交互元素标号并生成简洁的辅助树，避免冗长的 HTML 字符，使智能体能极其精准地通过 `@eN` 点击或填写元素。
- **状态存储**：所有内置浏览器会话数据存放在项目工作区内的隐藏目录 `.myagent/browser-session/` 中，与外部环境隔离，安全易清理。

## 4. 约束、风险与优化应对
1. **浏览器内核体积与复用策略**：
   - **风险**：直接让 Playwright 自动下载 Chromium 内核（数百兆空间）对极简 CLI 的首次运行体验伤害极大，且可能受网络环境限制。
   - **优化**：在工具层设计**本地浏览器环境探测机制**。启动时优先扫描系统常规目录（如 Windows 注册表或 Chrome 默认安装路径），若存在已安装的 Chrome 或 Edge 浏览器，优先通过 `executablePath` 指定复用系统自带浏览器；仅在未发现本地浏览器或版本过低时，再引导 fallback 下载隔离 Chromium 内核。
2. **反爬风控防范的局限性与人机协作**：
   - **风险**：许多具有高级安全防护（如 Cloudflare, Akamai）的网站，不仅检测 JS 层的 `navigator.webdriver` 特征，还会通过 TLS 指纹、IP 质量以及真实的鼠标运动轨迹等行为分析进行拦截。因此，完全依赖 `playwright-extra` 及其 stealth 插件并不是万能的。
   - **优化**：将 `playwright-extra` 作为**渐进增强（Progressive Enhancement）**的辅助手段，绝不抱有绝对依赖。将核心防护应对策略牢牢锁定在**“有头模式窗口（headless: false）+ 用户手动过验证”**的协同设计上。智能体遇到无法穿透的风控时，能有尊严地唤醒可视化窗口交由用户手动点击，完成后继续自动逻辑。
3. **CDP 直连模式的隐私与会话污染防范**：
   - **风险**：如果智能体直连用户日常正在使用的工作主力浏览器（如共享其原本开启的调试端口），其执行的各种跳转、点击与 DOM 修改操作将极大程度干扰用户的正常办公，且大模型频繁抓取 DOM 也有敏感信息泄露的隐私隐患。
   - **优化**：在直连方案设计中，**强制或强烈引导用户使用隔离命令启动专用的调试浏览器实例**（例如命令：`chrome.exe --remote-debugging-port=9222 --user-data-dir="C:\Users\<user>\.myagent\dedicated-chrome"`）。确保智能体连接的是一个物理隔离、干净且安全的沙箱浏览器窗口，不污染日常主力环境。
4. **命令行交互阻塞与会话同步**：
   - **风险**：在首次登录或面临滑块验证时，需要暂停智能体的推理循环。若没有良好的阻塞设计，会导致智能体继续向下流转引起调用失效。
   - **优化**：设计健全的异步阻塞等待机制（如提示“已调起浏览器界面，请在窗口中完成登录/过风控，完成后回到终端回车以继续...”），提供轮询或回车确认回调，确保智能体在已完成状态同步后再恢复执行。

## 5. 否决方案
- **方案 B：外部 Puppeteer MCP 服务**：
  - **舍弃原因**：默认的官方 Puppeteer MCP 启动为纯无头环境，在面对滑块、图片和扫码验证时，智能体自身缺乏处理能力，又无法便利地让用户在弹出的 GUI 窗口中手动辅助登录，导致首关登录即失败。
- **方案 C：静态 Cookie 注入**：
  - **舍弃原因**：无法支持智能体进行后续复杂的自动化网页操作（例如需要点击某按钮后加载的动态 DOM、交互式的表单提交等），局限性极大，无法实现真正的智能体多级操作。
