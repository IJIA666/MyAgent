## 背景

当前 `ask_user_question` 的等待边界划分错误：系统把“等待用户选择”当成了“普通工具执行中的同步等待”。结果是：

- `agent-loop` 会为工具调用统一挂载 `toolTimeoutMs`（默认 30 秒）；
- `InteractionHandler` 虽然内部有更长的等待逻辑，但外层普通工具超时会更早触发；
- 用户只要在选择界面停留稍久，就会被错误判定为“工具超时”，而不是“run 正在等待人类输入”。

这不是单纯的超时值配置问题，而是执行语义问题。结合本仓库现有调用链、竞品源码以及 OpenAI 官方的人类审核/恢复运行模式，可以确认：等待人类输入应当从普通工具超时模型中剥离，转为 interruption + resumable state。

## 目标与非目标

**目标：**

1. 将 `ask_user_question` 定义为一种需要人类参与的中断式执行语义，而不是普通同步工具。
2. 当该工具被调用时，当前 run 进入 pending interaction 状态，并持久化足以恢复的上下文。
3. 用户回答后，从同一 run 的状态恢复继续执行，而不是伪造新的用户轮次。
4. 默认不为用户选择设置自动超时；等待仅在用户回答、用户取消、会话关闭或进程退出时结束。

**非目标：**

1. 不顺带修复 `multiSelect` 的独立完成度问题。
2. 不要求在本 change 中把审批链路整体迁移到同一机制，只允许在设计上预留复用空间。
3. 不扩展到后台任务、长任务调度等更广义的执行模式体系；本 change 只解决 `ask_user_question` 的边界问题。

## 架构决策

### 决策 1：为工具元数据引入人机中断执行语义

**方案**：在工具元数据层引入 `executionMode`（或等价但语义同级的字段），至少区分：

- `immediate`：普通即时工具，沿用现有普通工具执行/超时模型；
- `human_interruption`：触发人机交互中断，不在普通工具 Promise 中同步等待用户回答。

`ask_user_question` 使用 `human_interruption`。

**理由：**

- 这比新增布尔值 `requiresUserInteraction` 更稳妥。当前问题不是“要不要更长超时”，而是“是否仍属于普通工具执行”。
- 显式执行语义有利于后续复用到审批、人类复核等场景，但本 change 只落地到 `ask_user_question`。
- 能避免继续围绕 `toolTimeoutMs` 打补丁，把错误模型制度化。

### 决策 2：引入 `pendingInteraction` 并纳入会话持久化

**方案**：当 `ask_user_question` 被调用时，不直接在工具执行栈里阻塞等待，而是创建一条 `pendingInteraction` 状态并写入会话/上下文。该状态至少需要包含：

- interaction 标识；
- 工具名与必要载荷（标题、选项、是否允许自由输入等）；
- 对应的 run 标识或恢复锚点；
- 创建时间；
- 当前状态（pending / answered / canceled）。

**理由：**

- 用户回答可能发生在当前同步执行链路之外，不持久化就无法可靠恢复。
- 这与官方 human review / resumable state 的模式一致，也更接近竞品的 deferred / pending 设计。
- `pendingInteraction` 是“等待人类输入”这一事实的真实建模，优于用长超时伪装等待。

### 决策 3：回答后恢复同一 run，而不是创建新用户轮次

**方案**：CLI 或会话管理层收到用户回答后，将回答写回对应 `pendingInteraction`，随后恢复原 run 的执行，从中断点继续推进；恢复结果应作为该次工具调用的返回值进入后续推理上下文。

**理由：**

- 用户回答本质上是之前工具调用的 completion，不是新的独立任务起点。
- 若伪造新用户轮次，会破坏工具调用闭环、污染会话语义，并增加 prompt/context 对齐难度。
- 与 OpenAI 官方“pause the run, then resume with the same state”一致。

### 决策 4：默认不设置自动超时

**方案**：`ask_user_question` 默认无自动超时。框架不再为这类等待注入诸如“5 分钟后返回空字符串”的默认行为。等待结束条件限定为：

- 用户明确回答；
- 用户明确取消；
- 会话关闭；
- 进程退出或恢复状态丢失。

若未来某些业务确实需要 deadline，应由调用方显式声明，并作为单独能力设计，而不是以框架默认行为存在。

**理由：**

- 用户选择的本质是主观决策，不应被静默超时替代。
- 默认超时会把“人没选完”和“系统失败”混为一谈，造成错误恢复与误导性结果。
- 这与用户体验和竞品/官方主流策略一致。

## 执行流概览

1. agent 调用 `ask_user_question`。
2. 工具注册层识别其执行语义为 `human_interruption`。
3. `agent-loop` 不为其走普通工具同步等待路径，而是创建 `pendingInteraction` 并暂停当前 run。
4. CLI 渲染问题，等待用户回答或取消。
5. 用户提交后，会话层将回答写回 `pendingInteraction`，恢复同一 run。
6. 原工具调用获得回答结果，后续推理继续。

## 风险与权衡

| 风险 | 影响 | 缓解思路 |
| :--- | :--- | :--- |
| 现有 `NativeTool.execute` 契约主要围绕同步返回结果设计 | 若边界改造不彻底，可能出现“表面中断、内部仍阻塞”的半完成状态 | 在设计上明确 `human_interruption` 不走普通工具同步等待模型，并在任务中单独覆盖 `virtual-mcp` / `agent-loop` 契约调整 |
| run 恢复锚点与现有会话持久化路径对不齐 | 可能出现重启后无法恢复、或恢复到错误位置 | 明确把 `pendingInteraction` 纳入现有会话状态保存路径，并要求手动验证“提问中退出再恢复”的场景 |
| interaction 长时间悬空 | 会话中残留脏状态，后续输入无法正确路由 | 只允许单个 active `pendingInteraction`，并在取消、会话关闭、恢复失败时显式清理 |
| 审批链路未来也需要类似能力 | 若本次抽象过度，容易把边界做大 | 本 change 只对 `ask_user_question` 落地；审批只在设计说明中标注“可复用同类底座”，不纳入当前验收范围 |
