## 背景

当前代码库中 `src/action/native-tools/file-system.ts` 暴露的写文件工具设计过于粗糙，大模型在使用其进行代码修改时认知负担极大，极易因为行号漂移或上下文算错导致改出致命 Bug。参考业界成熟 Agent 的最优实践，急需从底层切换到“全量写入 + 精确字符串替换”的双工具模式。

## 目标与非目标

**目标:**
- 新增 `editFile` 工具：入参为 `targetPath`, `old_string`, `new_string`, `replace_all`（可选，默认 false）。
- 在 `editFile` 工具执行层实现拦截安全网：
  - 如果找不到 `old_string`，抛出具有指导意义的错误（如提示重新查阅当前文件）。
  - 如果找到多个 `old_string` 但未设置 `replace_all` 为 true，必须抛出错误并提示模型：“找到了多处匹配，请扩大 old_string 的前后文范围以保证唯一性”。
- 调整并明确现有的 `writeFile` 工具的职责定位（全量覆盖与创建），优化两者对模型的系统提示语（Description）。

**非目标:**
- 本次变更不支持类似 Unified Diff / Git Patch 等复杂的多文件批量打补丁机制。
- 本次变更暂不考虑极其复杂的“AST 解析替换”，仅做字符串级别的纯文本特征匹配。

## 架构决策

- **职责切分：** 不在现有的 `writeFile` 工具上增加冗余参数（如同时包含 content 和 old_string 供其二选一），这会使模型选择困难。决策是明确分化出两个独立的方法：一个管全量，一个管增量。
- **彻底抛弃行号：** LLM 的 Tokenizer 机制使得它对于代码的绝对行数极不敏感，基于特征文本替换是最符合其自回归特性的机制，因此在增量工具中完全摒弃行号。
- **强制唯一性校验：** 修改文件是高危动作。如果特征码不够唯一，宁可报错让大模型多耗费一轮对话重新组织更长的 `old_string`，也绝不允许它抱着侥幸心理随意替换文件中的某一部分。用计算时间换安全性。

## 风险与权衡

- **风险：严格匹配容错率低。** 大模型在生成 `old_string` 时可能经常忽略原代码的前置空格、Tab 或空行，导致原本存在的代码匹配不到。
- **权衡与缓解：** 初期实现可先采用严格模式（或者做最简单的 Trim 匹配）。如果在真实测试中发现模型因此频繁受挫，后续可迭代增强，引入类似 Claude / Hermes 内部的多层级模糊匹配策略（即依次尝试严格匹配、消除前导空格匹配、无视所有空白符匹配等容错算法）。这也是一个值得持续打磨的点，但核心架构必须先立起来。
