## 背景

原终端安全网关设计中，使用静态硬编码只读白名单 `READONLY_COMMAND_WHITELIST` 放行基本命令。在 Windows 物理环境下，为避免 `spawn(shell: false)` 执行原生指令（如 `dir`）导致的 `ENOENT` 错误，大模型必须使用 `powershell` 或 `cmd` 包裹执行。

由于现有的安全校验（`checkSafety`）与安全前缀提取（`extractSafePrefix`）不具备“剥壳”清洗能力，导致系统被迫推荐用户去授权过于宽泛的 `powershell:*` 规则，这会架空整个安全防线；若拒绝放行，则会导致极高频的审批弹窗，极大增加了用户的使用摩擦。

为了彻底解决这一系统兼容性与安全审计透明度的根本冲突，本设计提出“解包剥壳校验”的架构重构。

## 目标与非目标

**目标:**
1. **白名单配置显式化**：废弃硬编码白名单，改用本地工作区下可控的 `.agent/allowed_commands.json` 配置文件，并在文件缺失时自动初始化常用安全规则。
2. **内核命令剥壳核验**：在匹配白名单和提取安全前缀前，统一对命令进行递归解包剥壳（`unboxNestedCommand`），实现“一处授权，多环境通用放行”。
3. **极高健壮性剥壳算法**：规避正则表达式匹配捕获组在遭遇嵌套引号（如内层包含 `--filter='src/**'` 等）时的语法截断风险，同时防止多重引号结构的最外层引号误删，以及对 PowerShell 匿名脚本块的精确识别。
4. **透明审批用户教育**：在人工挂起审批弹窗时，如果存在解释器外壳包装，必须显式在提示信息中披露“解包后的真实内核命令”，保障用户的安全知情权。

**非目标:**
1. 不对终端执行进程引擎 `terminal-engine.ts` 进行无状态 spawn 行为的重构。
2. 不负责执行复杂的内层 Shell 转义反斜杠清洗（例如将 `\"hello\"` 转为 `hello`），内部转义字符交由下游解释器处理。
3. 不对非终端工具的其他安全插件进行改动。

## 架构决策

### 决策 1：弃用静态硬编码白名单，引入本地预设自动初始化
* **理由**：硬编码白名单是黑盒的，不便于不同项目组自定义微调。设计上通过解耦，在加载配置时，如果 `.agent/allowed_commands.json` 缺失，则自动通过写文件写入预设规则列表（含 `git status:*` 等常用规则）存盘，既把控制权交还给用户，又保障了首日运行无感放行体验。

### 决策 2：白名单提取与匹配“一处授权，跨解释器通用”
* **理由**：当用户已经授权了 `npm run:*` 规则后，Agent 发起 `powershell -Command "npm run test"` 应当能够自动放行。设计上要求对待核验指令一律先剥壳、后核验，剥壳还原的核心命令与规则比对，直接抹平了解释器差异，极大地降低了多次授权的摩擦力。

### 决策 3：切片剥壳与闭合引号匹配点算法
* **理由**：
  * **切片非正则提取**：正则匹配捕获组 `shellMatch[2]` 会在内层指令包含嵌套引号时被直接截断。我们通过正则 `shellPrefixPattern` 仅匹配定位到 `-Command` / `-c` 后，利用 `slice` 截取全部剩余内容作为内层命令，再做引号剥除。
  * **闭合点校验**：若内层命令为 `"cmd A" --arg "cmd B"` 这种首尾均有引号的多组结构，单纯用 `startsWith` 和 `endsWith` 会误判定为成对引号而将其剥离，破坏命令结构。引入 `getMatchingQuoteIndex` 从首字符开始扫描，识别首个未转义引号的成对闭合索引，只有闭合索引恰在末尾才视作成对引号予以剥除。
  * **脚本块精准清洗**：使用正则 `^&\s*\{` 限制大括号剥离条件，防止将 `--config={tsconfig.json}` 误判定为 `& { ... }` 块而被破坏。

### 决策 4：审批透明告知机制
* **理由**：若解包剥壳后的实际内核指令与模型调用的原始包装指令不一致，安全提示返回 message 会显式列出“外壳”与“核心指令”对比。这提升了人机协作的知情度，防止恶意 Agent 利用 `powershell` 外壳进行欺骗性命令注入。

## 风险与权衡

* **[风险点 1]：解包失败可能会导致高危命令绕过**
  * *缓解策略*：解包仅作为“自动放行比对（`Auto` 模式）”的前置判定。如果恶意命令解包失败，在白名单中不会有匹配项，系统将依然退回到默认的人工挂起（`suspend`）审批流，而无法绕过执行。此外，绝对黑名单（`isHardlineDangerous`）拦截处于最外层，解包逻辑仅影响白名单自动匹配，因此安全红线没有任何降低。
* **[风险点 2]：在无权限目录或未初始化工作区时的文件 IO 异常**
  * *缓解策略*：在 `terminal-config.ts` 的读写流程中，全部使用 `try-catch` 包裹，若抛出异常直接回退到空列表和内存缓存向下兼容，保证主引擎绝不崩溃。
