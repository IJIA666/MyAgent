## 1. 问题边界

上一轮 change 已经收紧了终端运行时、审计补录与 Plan 放行边界；最新日志暴露的剩余问题不在 runtime 放行链路，而在诊断任务本身的规划与表述质量：

1. 工具或系统查询失败后，模型仍会尝试升级为更复杂的 shell 方案，而不是优先回退到内置只读工具、缩小问题或显式暴露不确定性。
2. `listFiles` 枚举缺少明确停机条件，容易在大目录树上重复扩散，带来低价值循环和 token 浪费。
3. 目录存在性、目录枚举、真实大小测量、执行失败这几类证据没有被严格区分，导致回答会把“枚举结果”夸大成“深度扫描结论”。
4. 最终建议仍可能混入高风险、绝对化的清理结论，例如把安装缓存目录概括成“可整目录删除且无副作用”。

因此，本次设计只收紧“诊断任务规划与回答质量”边界，不回头改动既有的终端运行时、安全审批或审计落盘设计。

## 2. 目标与非目标

### 2.1 目标

- 让诊断类回合在工具失败后具备稳定的降级路径，避免“失败后升级命令复杂度”的反模式。
- 为目录枚举建立有限预算与停机条件，避免长链 `listFiles` 扩散。
- 让回答显式区分证据等级，只有拿到真实大小测量后才能宣称“已确认大头”或给出释放空间估算。
- 为高风险清理对象建立保守分层，阻断“一刀切可删”的绝对化建议。

### 2.2 非目标

- 不修改 `execute_command` / `terminal` 的运行时安全策略本身。
- 不引入新的模型输出后处理器或回答重写器。当前真实架构只有 `BeforeToolSelection`、`BeforeModel` 与工具调度链路，本次优先复用这些现有边界。
- 不试图做通用磁盘分析产品；本次只修复诊断规划与回答可信度。

## 3. 设计决策

## 3.1 用“诊断状态 + 条件提醒”替代事后纠偏

当前最稳定的注入点是 `ModelRequestAssembler` 的 system-reminder 阶段。这里已经会把 `date/cwd/workMode` 动态挂到最后一条 `user` 消息尾部，因此本次继续沿用这个边界，而不是额外发明新的消息通道。

改造方向：

- 在 `AgentLoop` 侧维护当前回合的轻量诊断状态，至少包括：最近一次系统查询失败/被拦截标记、目录枚举次数、是否拿到真实大小测量、高风险清理目标命中情况。
- 在 `ModelRequestAssembler` 侧识别“诊断/排障/磁盘清理建议”类回合；命中后，把降级规则、证据分级约束、停机条件和清理安全提示注入 `<system-reminder>`。
- 非诊断类回合仍维持现有提醒最小集，避免把诊断约束污染到普通编码任务。

这样做的原因是：当前代码路径没有稳定的“模型回答生成后再审核”钩子，最可靠的收敛方式仍是把正确边界在下一次模型请求前讲清楚。

## 3.2 失败降级矩阵

本次不允许“系统查询失败后升级为更复杂 shell 复合命令”的恢复路径。失败后只能进入以下三类动作之一：

1. 回退到内置只读工具继续拿低风险证据，例如继续 `listFiles` / `readFile` / 其他原生只读工具。
2. 若内置工具已无法提升证据等级，则直接汇报当前未知项，要求用户缩小范围或接受不确定性。
3. 仅当存在明确、单一、原子、可静态证明安全的系统查询缺口时，才允许重新发起一次更准确但仍简单的系统查询；若再次失败或被拦截，必须停止升级。

这里的核心不是“完全禁止系统查询”，而是禁止把失败恢复写成“不断加壳、不断拼接、不断升级复杂度”。

## 3.3 扫描停机规则

`LoopPreventionPlugin` 目前只能阻断“同一工具 + 完全相同参数”的重复调用，挡不住“换目录继续 `listFiles`”这类低价值扩散。因此需要一层面向诊断任务的额外停机状态。

改造方向：

- 为诊断枚举设置有限预算，例如“本轮最多扩展若干个候选目录”或“连续若干次枚举未提升证据等级即停机”。
- 预算扣减不以“是否报错”为唯一信号，而以“是否新增高价值候选、是否获得真实大小测量、是否缩小结论不确定性”为判断依据。
- 一旦达到停机条件，后续模型请求必须收到明确提醒：禁止继续扩散扫描，应转入汇总、声明证据边界或向用户请求更窄目标。

这层状态应落在 `AgentLoop` 或其相邻的调度闭环中，因为只有这里同时看得到工具调用意图与返回结果。

## 3.4 证据分级与可宣称边界

本次把诊断证据至少分为四档：

- `presence`: 只知道路径/对象存在。
- `enumeration`: 只知道目录枚举结果或候选列表。
- `measured`: 已拿到真实大小、容量或其他可量化数据。
- `error`: 查询失败、被拦截或结果不足以支撑结论。

对应约束：

- 只有 `measured` 证据才能支撑“已确认大头”“预计可释放 X 空间”这类强结论。
- `enumeration` 最多只能支撑“疑似候选”“建议下一步测量”，不能包装成“深度扫描完成”。
- `error` 必须显式暴露，不得被表述成“扫描无结果但整体结论仍可信”。

由于当前系统没有单独的回答后置校验器，这些约束会以 system-reminder 和相关提示词规则的形式进入模型上下文，并由测试锁住文案边界。

## 3.5 高风险清理建议分层

清理建议不再只看“像不像缓存目录”，而要显式分层：

- `forbidden`: 没有充分产品级证据时，禁止建议整目录删除的对象，例如安装缓存、修复介质、共享组件缓存等。
- `cautious`: 可以提示“可能占用空间，但副作用未知，需要先确认用途”的对象。
- `candidate`: 已有明确证据、且副作用通常可控的临时目录或用户级缓存候选。

本次先把风险最高、最容易被误判为“可随便删”的对象纳入禁止或谨慎层，避免回答出现绝对化清理建议。

## 5. 风险与权衡

- 约束过强会让诊断回答更保守，但这是有意取舍。相比“看起来全面却证据失真”，保守但诚实更符合当前问题性质。
- 诊断任务识别若做得过宽，会把普通编码任务也套上清理/扫描约束；因此提醒注入必须是条件性的，而不是全局常驻长提示。
- 若把停机预算完全写死，可能对少数真实大目录场景过早终止；因此预算应与“证据是否升级”结合，而不是单纯计数。
