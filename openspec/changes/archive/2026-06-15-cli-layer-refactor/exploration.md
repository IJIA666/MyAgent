# 探索主题: 终端用户界面层解耦重构 (CLI Layer Refactor)

## 1. 问题定义
现有 `src/interface/cli.ts` 源码长度达 424 行，包含了按键监听、菜单展示、路由分发、终端控制台彩化排版等多种异质职责，导致 UI 展现、流式数据交互和系统状态控制逻辑高度交织，大幅降低了该模块的独立可测试性。重构目标是实现输入控制与视图输出逻辑的彻底解耦。

## 2. 关键发现与调研结果
- **代码库现状**：`cli.ts` 强依赖 `readline` 模块，并通过 `@clack/prompts` 渲染高级交互菜单。当用户触发菜单时，会暂时关闭 `readline` 实例并在退出菜单后重新初始化。同时，它直接在内部调用 `console.log` 拼装了大量的 ANSI 终端色彩与 Token 监控回显块。
- **核实与洞察**：通过对 Node.js 命令行交互架构的调研，解耦的最佳实践是将终端视图输出与底层的事件流捕捉进行解耦，使其单向流转。另外，由于输入重叠，`InputListener` 对 `stdin` 的监听生命周期需与门面进行协同，以防抢占控制台焦点。

## 3. 方案对比与推荐方向
| 评估维度 | 方案 A (极致解耦与 Facade 门面模式) | 方案 B (轻量抽取视图与输入组件) | 结论 |
| :--- | :--- | :--- | :--- |
| 模块正交性 | 极强 ✓ (`InputListener`/`Renderer`/`Dispatcher` 物理分离) | 一般 ✗ (输入流控制与 REPL 循环交织) | 方案 A 职责更单一，分层更清晰 |
| 测试便利性 | 极高 ✓ (可直接 Mock InputListener 进行模拟输入测试) | 较低 ✗ (仍需较复杂的进程级 readline 模拟) | 方案 A 更易于覆盖单元测试 |
| 实现与重构成本 | 较高 ✗ (需要处理 readline 控制权在组件间的平滑流转) | 较低 ✓ (仅抽离渲染纯函数，现有状态结构不变) | 方案 B 开发成本较低 |
| 状态共享复杂度 | 高 ✗ (需在 Facade、Listener 与 Dispatcher 间传递控制状态) | 低 ✓ (所有上下文均原生保存在单个控制类中) | 方案 B 逻辑共享更简易 |

**推荐路径**：选择 **方案 A (极致解耦与 Facade 门面模式)**。通过引入 `CliFacade` 组合三大子组件。虽然重构时需要理清交互控制权及 `readline` 的生命周期，但这一路径提供了最高级别的职责正交性，并且便于未来对输入源或渲染器进行平替（例如引入更先进的 CLI 框架）。

## 4. 约束、风险与未知项
- **控制权抢占冲突**：当 `CommandDispatcher` 调起交互菜单（如 `@clack/prompts`）时，必须暂时闭合 `InputListener` 的 `readline` 句柄，否则会导致两个组件同时尝试从 `stdin` 读取，引起交互错乱。
- **状态流转复杂度**：需要将当前是否处于流式响应生成状态（`isGenerating`）、重置/回退状态的操作等合理暴露，以便 `InputListener` 和 `Dispatcher` 共享。

## 5. 否决方案
- **方案 B (轻量抽取视图与输入组件)**：虽然能以极低成本抽离部分渲染方法，但 `REPL` 主循环仍然和键盘监听交织在 `cli.ts` 中，无法从根本上纯化控制台界面层，不便于后续的交互扩展与测试。
