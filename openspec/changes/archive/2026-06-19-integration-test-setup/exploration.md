# 探索主题: 系统配置与运行期集成测试必要性评估

## 1. 问题定义
在系统配置经历了去厂商化（`AGENT_LLM_`）及 ESLint 物理阻断重构后，系统拥有了高内聚的单元测试（Mock 环境下的隔离测试）。然而，目前系统在面对真实的物理硬件环境（物理磁盘读取、网络请求装配、跨模块生命周期联动、MCP 子进程真实隔离）时，依然缺乏真实运行期集成测试的卡关保障。
本探索旨在评估集成测试在当前架构下的必要性，并制定后续测试加固的推荐方向。

## 2. 关键发现与调研结果
- **代码库现状**：
  - **单元测试局限**：目前所有的单测均在内存环境中通过 Vitest 运行，所有的外部 IO、环境变量及 MCP Server 调用要么被 Mock，要么被高度隔离。这导致以下物理集成路径缺乏拦截：
    1. 物理磁盘上的 `.env` 和 `mcp_config.json` 在格式损坏或读写冲突时的动态自适应表现。
    2. 配置对象装配大模型驱动（`driver.ts`）并初始化真正的网络客户端时，由于 API Endpoint 拼接等细节导致的物理连接阻碍。
    3. MCP 子进程在被 `spawn` 拉起时，操作系统级别的环境变量泄漏控制。
  - **现有集成测试状况**：当前 `test/scripts` 目录下存在针对“评测靶场一键运行与清理”的自动化脚本（如 `run_testbed.ts` 等），这属于系统级的端到端评测测试，但它们过于重型（测试整个 Windows 清理逻辑与靶场防护），无法直接内聚和轻量化地验证配置/模型/MCP 层的子系统集成。
- **集成测试的核心必要性**：
  1. **验证物理文件与插值装配**：确保 `.env` 中的 `AGENT_LLM_HEADERS` 等高级配置格式，在通过 `interpolateEnvVars` 转换并应用到网络适配器时的物理可执行性。
  2. **真实的 MCP 环境安全卡关**：验证当宿主机包含大量敏感信息时，拉起的真实子进程确实无法读取到白名单外的变量，这是通过纯 Mock 无法 100% 模拟的操作系统级行为（如 Node.js 的 `child_process.spawn` 细节）。

## 3. 方案对比与推荐方向

| 评估维度 | 方案 A (仅维持现有单元测试) | 方案 B (引入配置与生命周期集成测试) | 结论 |
| :--- | :--- | :--- | :--- |
| **真实 IO 边界校验** | 无法验证 ✗ (依赖 Mock，漏掉磁盘与系统交互) | 完美验证 ✓ (基于真实临时目录读写物理文件并运行) | B 占优 |
| **环境安全漏洞拦截** | 理论推演 ✗ (只能验证 mock 函数的行为) | 物理审计 ✓ (真实拉起进程并检测子环境防泄露) | B 占优 |
| **维护成本与延迟** | 极低 ✓ (单测速度快，毫秒级) | 中等 ✗ (由于需要磁盘读写和子进程调用，耗时秒级) | A 占优 |

**推荐路径**：
基于“安全第一”和“高扩展性”的 Agent 原则，我们推荐采用 **方案 B (引入配置与生命周期集成测试)**。
但考虑到执行效率，集成测试无需覆盖所有日常开发用例，应作为独立套件存在（例如通过 `test/integration` 目录或以 `*.spec.ts` 命名与 `*.test.ts` 单测隔离），并在 CI 门禁或发布前执行。
重点针对以下两个集成路径补充轻量集成测试：
- **物理配置引导集成**：在临时目录中物理创建或删除 `.env` 与 `mcp_config.json`，验证 `ensureConfigFiles` 的文件复制、DOTENV 读取及字段级插值完全对齐。
- **MCP 进程隔离集成**：物理 `spawn` 一个能够打印自身环境变量的 Dummy 节点，验证宿主机的敏感变量确实没有溢出到该进程中。

## 4. 约束、风险与未知项
- **子进程权限风险**：在 Windows/macOS/Linux 等不同操作系统上，`spawn` 执行基础指令（如 `node`）的路径解析存在差异。集成测试需要对平台差异进行优雅处理，避免因平台差异造成测试假红。

## 5. 否决方案
- **直接使用真实的大模型 API 进行网络集成测试**：
  - *否决原因*：这会产生真实的网络 API Key 欠费、密钥泄漏风险以及测试 latency 极大。集成网络时应使用本地 Mock Server (例如使用 msw 或本地 http server 拦截) 来取代真实的互联网 API 请求。
