## 背景

当前系统的测试套件 100% 为单元测试，它们运行在高度隔离的内存 Mock 环境中。在经历了全局环境变量前缀重构和 ESLint 阻断后，虽然单元测试完全覆盖了相关代码逻辑，但在操作系统级物理子进程环境变量防泄露、以及物理 `.env` 的自适应生成机制上，依然没有建立集成级的自动化防护。为此，需要搭建集成测试框架，并补充具体的物理配置读写测试与 MCP 子进程隔离安全测试。

## 目标与非目标

**目标:**
1. **测试套件物理隔离**：建立 `test/integration` 目录专门存放集成测试用例，通过物理路径和测试脚本与常规的单元测试（`npm run test`）完全隔离开来。
2. **物理配置自适应测试**：使用唯一的临时物理工作目录，物理生成并写入 `.env`，物理删除并检验 `ensureConfigFiles()` 的文件引导复写逻辑。
3. **真实子进程隔离审计**：利用 Node.js 的 `child_process` 模块在集成测试中物理 `spawn` 拉起一个专门的环境自检子进程，验证大模型 API Key 等敏感环境变量确实被拦截阻断而未传导至子进程。

**非目标:**
1. **网络连接第三方服务的集成测试**：本次集成测试不发起任何真实的公网连接（不请求真实的 OpenAI 或 DeepSeek API），仍然采用内部 Mock 响应以保证高测试速度和防欠费/防泄密。
2. **多操作系统差异下的路径强绑定**：不对具有强宿主系统依赖的路径进行绝对写死，使用 `path.resolve` 与临时系统目录进行自适应解析以保证测试跨平台兼容。

## 架构决策

### 决策一：在 `package.json` 中配置独立的集成测试脚本
- **技术细节**：在 `package.json` 的 `scripts` 中增加 `"test:integration": "vitest run test/integration"`。
- **理由**：集成测试涉及物理磁盘读写以及真实的子进程 `spawn` 延迟。通过这种区分，常规的 `npm run test`（仅执行内存级单元测试）可以在毫秒级完成，保证开发自检的即时反馈；而集成测试可以在 CI 或发布前单独运行，兼顾开发体验与系统安全性。

### 决策二：使用独立的临时沙箱目录测试物理配置引导
- **技术细节**：在测试执行时，利用 `fs` 创建 `test-temp-integration-workspace` 临时沙箱工作区，并在 `afterEach` 中递归清空。测试时将 `process.cwd()` 或 `env.AUTHORIZED_WORKSPACE_DIR` 指向该临时沙箱，进行物理文件的读写与自生成校验。
- **理由**：如果在主工作区直接执行物理文件修改，可能会污染主工程中的 `.env` 或 `mcp_config.json`，导致开发环境崩坏。临时沙箱工作区能提供绝对安全的磁盘集成校验。

### 决策三：编写专门的环境自检 Node.js 脚本作为 Dummy MCP Server
- **技术细节**：在 `test/fixtures/dummy-mcp.ts`（或 `test/integration/mcp-isolation.spec.ts` 内部动态写入临时 js 文件），在拉起子进程时执行 `node <dummy_js>`。该 dummy 进程仅执行一行逻辑：将自身接收到的 `process.env` 以 JSON 格式输出到 stdout。测试用例捕获 stdout 并利用 `JSON.parse` 审计其中是否包含系统级的敏感前缀变量。
- **理由**：物理 `spawn` Node.js 子进程是检验操作系统级环境变量泄漏的终极防线，能够 100% 模拟生产环境下拉起 MCP 时的物理隔离效果。

## 风险与权衡

### 风险点：测试时子进程挂死或残留僵尸进程
- **描述**：如果拉起的 Dummy MCP 子进程由于没有正确接收到退出信号，或者在集成测试报错中断时未能被正确杀死，会导致系统的临时资源泄漏，甚至在 Windows 上锁定临时文件。
- **缓解策略**：
  - 子进程自毁：Dummy 子进程设计为“只打印一次环境变量便立即退出（Process Exit 0）”的同步流，不执行挂起循环。
  - 在测试的 `afterEach` 中，显式调用 `subprocess.kill('SIGKILL')` 强行回收可能挂死的子进程。
