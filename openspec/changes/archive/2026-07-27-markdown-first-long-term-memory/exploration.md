# 探索主题: Markdown-first 长期记忆

## 1. 问题定义

旧长期记忆把 Markdown 文件、会话结束后的 Forked Agent 提炼、Embedding、向量数据库和每轮模型调用前的 RAG 注入绑定为同一条运行链路。当前工作树已经完成并归档 `remove-rag-vector-memory-runtime`：生产源码、配置、依赖和测试中的旧记忆服务、RAG、Embedding 与 VectorDB 均已移除。新的问题不是如何复原旧实现，而是如何从干净基线构建一个可审计、可编辑、上下文成本有界的长期记忆能力，并在没有规模证据前避免重新引入数据库、向量索引、分块管线和后台模型。

本次探索聚焦“单工作区的 Markdown-first 长期记忆”。第一版由主 Agent 使用现有标准文件工具读取和修改 Markdown，不新增记忆专用工具。用户全局记忆、跨工作区合并、自动会话提炼和语义检索属于可能的后续阶段，不应阻塞第一版。

## 2. 关键发现与调研结果

- **代码库现状**：
  - `openspec/changes/archive/2026-07-25-remove-rag-vector-memory-runtime/` 已记录并实施旧链路删除；当前 `git status` 显示 `MemoryService`、`LongTermMemoryPlugin`、Embedding/VectorDB 端口与适配器均已删除，相关配置和测试也已迁移。
  - `SessionManager` 在 `src/core/usecases/engine/session.ts` 中先创建 `SessionContext`、设置 `appConfig`，再创建 `RuleManager`。这提供了一个明确的“会话启动时加载一次记忆快照”的装配点，不需要恢复 `BeforeModel` 或 `SessionClosed` 插件。
  - `RuleManager` 当前负责读取 `.myagent/global_rules.md`、`.myagent/rules/guize.md` 和技能元数据，并调用 `SessionContext.updateSystemPrompt()`。记忆机制规则可以进入 system prompt，但实际 `MEMORY.md` 内容不能混入 `<local_rules>` 或其他强制规则：记忆是可能过期的辅助事实与偏好。
  - `buildSystemPrompt()` 已将稳定人设、工作区上下文和易变环境分层。它适合承载四种记忆类型、保存/排除/召回规则和记忆信任边界，不适合直接承载会持续变化的 `MEMORY.md` 正文。
  - `ConversationState` 将 system prompt 固定保存在消息历史第 0 项，当前压缩实现也会保留该项。实际记忆索引更适合在模型请求组装阶段作为独立、非持久化的 meta user context 注入，既不提升为 system 权威，也不与用户真实消息拼接。
  - `buildNativeTools()` 是内建工具的唯一装配入口，现有文件工具已经覆盖列举、读取、写入和编辑能力。第一版没有必要再复制一套 `memory` 工具协议；客户端只需为当前项目 `ApplicationPaths.memoryDir` 增加精确的受限读写资源范围，文件修改继续经过现有权限模式。
  - 现行目录契约把 workspace `.myagent/` 限定为配置、规则和技能，把项目私有运行数据放在 `~/.myagent/projects/<workspace-key>/`。Auto Memory 是机器本地、按项目隔离且不应提交的持久数据，因此应新增 `ApplicationPaths.memoryDir = <projectDataDir>/memory/`，作为 `logs/`、`state/`、`artifacts/`、`tmp/` 的同级分类，而不是写入 workspace。
  - 当前规则加载单文件上限是 20KB。记忆索引应采用同等级的硬边界，并额外限制行数，避免长期增长侵蚀提示词预算。
- **核实与洞察**：
  - [Claude Code 官方记忆文档](https://code.claude.com/docs/zh-CN/memory)明确区分用户编写的 `CLAUDE.md` 与 Claude 自动维护的记忆。自动记忆使用纯 Markdown，`MEMORY.md` 前 200 行或 25KB 在会话开始时加载，主题文件通过标准文件工具按需读取。
  - 本地 `D:\projects\Agents\claude-code-analysis\src\memdir\memoryTypes.ts` 定义了 `user`、`feedback`、`project`、`reference` 四种类型，以及保存排除项、过期校验和召回规则；这些是模型行为约束，不是数据库分类体系。
  - `D:\projects\Agents\claude-code-analysis\src\utils\claudemd.ts` 的 `getMemoryFiles()` 把 Auto Memory 入口加入 CLAUDE.md 文件集合，`getClaudeMds()` 生成合并上下文；`src\utils\api.ts` 的 `prependUserContext()` 再把该上下文作为独立 meta user message 放到请求前面。压缩时会清除文件缓存并从磁盘重新加载。除这条核心路径外，还存在受 feature gate 控制的主题选择和后台提取增强，但第一版不应把可选增强误认为必需链路。
  - [Codex 当前配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)暴露了独立的线程提取模型、全局合并模型、线程闲置时间、候选数量、保留时间和生成/使用开关。本地 `D:\projects\Agents\codex` 源码显示其完整写入管线以状态数据库负责领取、租约、重试和阶段结果，再把最终记忆沉淀为 Markdown；其本地记忆读取工具则只是受根目录约束的 list/read/逐行文本 search，并不依赖向量数据库。
  - Codex 的数据库解决的是异步批处理协调问题，不是“Markdown 无法存储记忆”。MyAgent 第一版没有并发后台提取、跨线程领取和全局合并需求，因此没有引入数据库的理由。
  - OpenClaw 的内建记忆虽然也以 `MEMORY.md` 和日记 Markdown 为事实源，但当前方案已经发展到 400-token/80-token overlap 分块、SQLite、Embedding、文件 watcher、混合召回和重建机制。它适合已有大规模语料与检索需求的阶段，不适合 MyAgent 当前的零数据基线。
  - Hermes Agent 的有限容量 Markdown、会话冻结注入和可见写入结果可以作为边界参考，但其专用 add/replace/remove 工具不是第一版必须复制的机制。MyAgent 可以用现有文件工具完成相同读写；客户端继续负责通用路径与输入安全，“不得保存凭据和秘密”则由 Auto Memory 机制规则与人工可审计性约束。
  - 因此，存储介质、生成策略和召回策略必须拆开决策：
    1. 存储可以是 Markdown；
    2. 第一版生成可以由主 Agent 在当前回合通过工具完成，不需要额外模型；
    3. 第一版召回可以靠始终加载的小索引和按需读取主题文件，不需要 RAG。

## 3. 方案对比与推荐方向

| 评估维度 | 方案 A：单文件全量注入 | 方案 B：Markdown 索引 + 主题文件 | 方案 C：自动提取 + 数据库/RAG | 结论 |
| :--- | :--- | :--- | :--- | :--- |
| 存储可审计性 | 高，只有一个文件 | 高，索引和正文均可直接编辑 | 中，Markdown 与派生索引/状态并存 | A/B 明显优于 C |
| 首期实现成本 | 最低 | 低到中 | 高 | A 最低，B 仍可控 |
| 上下文成本 | 随记忆总量线性增长 | 只固定加载小索引，正文按需读 | 可按召回限制，但每轮有检索成本 | B 最均衡 |
| 编辑/删除一致性 | 天然一致 | 需要维护索引链接和主题文件，允许检测并修复短暂不一致 | 需要索引重建、删除传播和版本一致性 | B 不承诺跨文件事务，但可确定性审计和修复 |
| 额外模型调用 | 无 | 无 | 提取、选择或合并需要额外调用 | 第一版选择无额外模型 |
| 扩展到较大记忆集 | 弱 | 中，先靠主题组织，后续可加文本搜索 | 强 | 当前规模下 B 足够 |
| 提示词缓存稳定性 | 文件变化会改变前缀 | 启动时冻结索引，当前会话不重写前缀 | 每轮注入内容可能变化 | B 最适合现有三层提示词 |
| 错误记忆治理 | 人工编辑容易 | 标准文件工具 + 可审计 Markdown + 结构校验 | 错误可能扩散到提取与索引 | B 风险更可控 |

**推荐路径**：采用方案 B，并把它限制为一个不含后台智能体的第一阶段能力。

### 3.1 文件布局与作用域

第一版只实现当前项目的机器本地私有记忆，路径由规范化 workspace 生成的 `workspace-key` 隔离：

```text
~/.myagent/projects/<workspace-key>/memory/
├── MEMORY.md
└── topics/
    ├── user-profile.md
    ├── collaboration-feedback.md
    ├── project-context.md
    └── external-references.md
```

- `MEMORY.md` 只保存主题链接和一行摘要，不保存长正文。
- 每个索引项建议保持在约 150 字符以内。
- `topics/*.md` 保存可独立理解的用户信息、反馈、项目背景和外部引用；按主题组织，不按会话、日期或记忆类型建立物理目录。
- 主题文件使用固定 frontmatter：

```yaml
---
name: 项目背景
description: 记录无法从代码和 Git 推导的项目动机、期限与约束
type: project
---
```

- `type` 只允许 `user`、`feedback`、`project`、`reference` 四种受支持值。它是模型分类与审计元数据，不是数据库枚举；未知或缺失类型应被报告，但不应导致 Markdown 正文不可读。
- `name`、`description` 和 `type` 是主题文件的事实源；`MEMORY.md` 是人和模型都可阅读的导航索引，可根据主题 frontmatter 确定性重建。不加入 embedding、chunk id、向量状态、数据库主键或自动生成时间戳。

主题选择与文件命名采用以下第一版约定：

1. `topics/` 保持单层目录，第一版不创建子目录。
2. 文件名使用小写 ASCII kebab-case，格式为 `[a-z0-9]+(?:-[a-z0-9]+)*\.md`。
3. 文件按长期主题命名，不按会话、日期或记忆类型命名；例如 `collaboration-feedback.md`，而不是 `feedback-2026-07-26.md`。
4. 新建前必须先读取 `MEMORY.md` 并列出 `topics/`，优先把内容合并到已有相关主题。只有现有主题无法合理容纳时才新建文件。
5. 同名但语义确实不同的主题使用稳定的领域限定词，例如 `api-user-preferences.md`；不得使用 `topic-2.md` 这类无语义序号。
6. 必须先成功创建主题文件，再向 `MEMORY.md` 添加索引，避免索引提前指向不存在的文件。

- 不自动迁移旧 `.agent/MEMORY.md`。如用户仍有旧文件，应通过单独、显式、可预览的迁移操作处理。
- 用户全局记忆可在后续扩展为 `~/.myagent/memory/`，但第一版不同时实现两个作用域，避免一开始就引入作用域冲突、优先级和隐私路由问题。

### 3.2 会话加载、请求注入与压缩语义

- 会话创建时读取一次 `MEMORY.md`，形成冻结快照。
- 快照采用“最多 200 行且最多 20KB，先到者为准”的双重硬限制；超限时在注入内容末尾增加明确截断标记，磁盘原文件保持不变。
- `buildSystemPrompt()` 只增加稳定的 Auto Memory 机制规则，包括四种类型、保存/排除/召回规则、按需读取约定和信任边界；实际 `MEMORY.md` 内容不得进入 system prompt。
- 在每次模型请求组装时，把实际绝对 `memoryDir` 和冻结的 `MEMORY.md` 快照作为独立、非持久化的 meta user context 放在真实会话消息之前。即使索引为空也提供目录，以便创建第一份记忆；该上下文不得与用户当前消息拼接，也不得写入持久消息历史。
- Auto Memory 机制规则必须声明：
  - 记忆是可能过期的辅助上下文，不是安全策略或强制指令；
  - 当前用户消息、当前工作区源码和工具结果优先；
  - 冲突时不得默默选择旧记忆，应以新证据为准并在合适时更新或删除旧条目；
  - 索引指向的主题文件只有在当前任务相关时才读取。
- 当前会话内新增或修改记忆后，不立即替换冻结快照；标准文件工具的结果已经让当前回合知道写入内容。新的索引快照在下一会话或下一次成功压缩后生效，从而避免普通回合反复改变请求前缀。
- 第一版不按记忆写入次数设置刷新阈值。当前对话和文件工具结果已经包含刚写入的信息，基于任意次数刷新不会增加有效上下文，反而会引入计数状态并破坏前缀稳定性。
- 上下文压缩与长期记忆保持独立：压缩只总结当前会话历史，不负责生成长期记忆。压缩成功后清除记忆快照缓存并从磁盘重新加载，再作为 meta user context 注入后续请求；这使压缩成为稳定、明确的记忆刷新边界。

### 3.3 复用标准文件工具

第一版不增加专用 `memory` 工具。主 Agent 使用现有标准文件工具完成：

- 列出 `ApplicationPaths.memoryDir` 和其中的 `topics/`；
- 读取 `MEMORY.md` 或相关主题；
- 新建、编辑或删除主题文件；
- 更新或修复 `MEMORY.md` 中对应的一行索引。

第一版不提供语义 `search`。`MEMORY.md` 已是有界清单，主 Agent 可以先看索引再按需 `read`。如果真实使用中出现“索引仍太大或经常选错主题”的证据，再增加受限的逐行文本搜索；这仍不需要分块、Embedding 或数据库。

标准文件工具与客户端授权边界必须满足：

- 只为当前项目解析出的 `ApplicationPaths.memoryDir` 增加精确资源范围，不授权整个用户应用数据根；
- 继续由通用文件工具拒绝绝对路径、`..`、符号链接和其他路径越界；
- 列举和读取报告只读 effect，创建、编辑和删除报告真实写 effect，并沿用现有 PermissionMode；
- 单文件写入使用同目录临时文件加替换；跨 `MEMORY.md` 与主题文件的修改不虚假承诺事务原子性；
- 主题文件先作为事实源落盘，再更新 `MEMORY.md`。索引更新失败时明确报告短暂不一致，后续通过标准文件工具按 frontmatter 确定性修复；
- 标准文件工具只执行既有的通用路径、输入和权限校验，不增加记忆专属的内容语义判断。system prompt 必须禁止保存凭据和秘密，也不得用脆弱启发式宣称已经识别所有“提示词注入”；记忆的非权威语义由 system prompt、消息边界和人工可审计的 Markdown 共同保证；
- 文件工具响应继续明确显示实际修改内容，便于用户审计。

主 Agent 的保存触发规则：

1. 用户明确说“记住”或“忘记”时必须处理该意图；符合长期边界时写入或删除，涉及秘密时拒绝，属于临时或可推导内容时说明原因并确认真正值得长期保留的部分；
2. `user` 保存用户角色、目标、知识背景和长期偏好；
3. `feedback` 保存用户纠正和用户明确肯定的非显然工作方式，并记录 **Why** 与 **How to apply**；
4. `project` 保存无法从源码和 Git 推导的项目目标、动机、期限、利益相关方背景和当前约束；
5. `reference` 保存外部系统中最新信息的位置与用途，而不是复制外部内容；
6. 普通任务状态、可从源码/配置/Git 重新发现的事实、代码结构快照、修复配方、临时路径、一次性错误、未经确认的推测、原始会话摘录以及已有规则不得保存；
7. 不在 `SessionClosed` 自动运行模型，不把每个会话都视为需要提炼。

忘记与删除采用以下语义：

1. 用户要求忘记主题中的一条内容时，只删除对应正文；主题仍有有效内容则保留文件和索引。
2. 用户要求忘记整个主题，或删除后主题只剩空 frontmatter 时，先删除主题正文或主题文件，再删除 `MEMORY.md` 中的索引行。若第二步失败，可以暂时留下可修复的断链，但被要求忘记的正文不得继续留在磁盘。
3. 删除后若主题含义发生变化，必须同步更新 frontmatter 的 `name`/`description` 与索引摘要。
4. 无法唯一确定用户要求忘记的范围时，必须先读取相关主题并澄清，不能执行模糊批量删除。
5. 磁盘删除不能物理擦除已经进入当前会话历史的内容。用户提出“忘记”后，主 Agent 必须立即停止应用、引用或提及该内容；成功压缩或新会话后再由磁盘事实提供干净快照。

### 3.4 与当前代码的建议集成点

建议通过一个小型明确的垂直切片实现，而不是恢复旧 `MemoryService`/`LongTermMemoryPlugin`：

1. 新增只读 Markdown 记忆上下文加载器，职责只包括项目记忆路径解析、有界读取、文件名/frontmatter/索引校验和冻结快照；不包含工具协议、LLM、AgentLoop、Hook、Embedding 或召回排序。
2. 扩展 `ApplicationPaths` 增加 `<projectDataDir>/memory/`，并在 `src/index.ts` 使用 `appConfig.applicationPaths.memoryDir` 创建单例加载器、注入 `SessionManager`；标准文件工具保持现有装配，不增加记忆专用注册项。
3. `SessionManager` 私有持有冻结记忆快照，并在 `open()` 阶段首次读取。不得注册 `BeforeModel` 或 `SessionClosed` 记忆插件。
4. 记忆快照不写入 `SessionContext` 或会话持久化；规则或技能刷新只重建稳定 system prompt，不把实际 `MEMORY.md` 内容混入其中。
5. `buildSystemPrompt()` 增加 Auto Memory 机制规则，明确四种类型、主题复用与命名、保存/排除/召回、忘记/删除、按需读取和过期校验。
6. `ModelRequestAssembler` 在请求期投影中把冻结快照包装为独立 meta user context，并保证它不进入持久消息历史和压缩摘要源。
7. `CompactionService` 成功提交压缩历史后刷新记忆快照；失败或跳过压缩时保持原快照。
8. 在现有文件读取与写入授权边界中，仅增加当前项目 `ApplicationPaths.memoryDir` 的精确资源范围，继续复用通用文件工具及其 read/write effect。
9. CLI 可增加只读 `/memory` 审计入口，用于显示根目录、容量、四类主题、断链索引和未知类型；第一版不需要内置编辑器，编辑仍通过标准文件工具或用户直接修改 Markdown。

### 3.5 分阶段验收

**第一阶段：显式、文件化记忆**

- 无记忆文件时，启动不得失败或因读取主动创建文件；
- 无记忆索引时，请求仍提供当前项目实际 `memoryDir`，模型能够使用标准文件工具创建第一份记忆；
- 有记忆时，在会话创建时读取索引并形成冻结快照，普通请求不重复读盘；
- system prompt 只包含稳定机制规则，实际索引通过独立 meta user context 进入请求；
- 四种 frontmatter 类型可以被加载、审计和用于保存/召回约束；
- 新主题遵循单层目录、kebab-case 和“先查找复用、后决定新建”的命名约定；
- 用户明确记住、更新和忘记均通过标准文件工具可靠修改 Markdown；
- 忘记单条内容、清空主题和忘记整个主题具有明确且可验收的不同结果；
- 手工编辑或删除主题后，下次会话或成功压缩后反映磁盘事实；断链和未知类型可被明确报告并确定性修复；
- 成功压缩后重新加载磁盘索引，压缩本身不自动生成长期记忆；
- 生产依赖和运行时中保持 VectorDB、Embedding、LanceDB、RAG、分块与记忆专用模型零残留。

**第二阶段：基于证据的可用性增强**

只有在真实记忆数量、索引长度、误选率或遗漏案例证明需要时，才考虑：

- 受限逐行文本搜索；
- 用户全局与项目工作区双作用域；
- `/memory` 的交互式审批、编辑和迁移；
- 记忆使用/更新次数等不含正文的诊断指标。

**第三阶段：自动提取实验**

只有在显式记忆稳定且用户确实需要自动学习时，才单独探索：

- 哪些会话满足闲置、长度、来源和隐私条件；
- 是否使用当前主模型的缓存上下文，还是独立廉价模型；
- 如何预览、暂存、批准、拒绝和回滚候选记忆；
- 如何防止并发提取、重复处理和错误记忆扩散。

即使进入第三阶段，最终事实源仍保持 Markdown。数据库只能在出现真实的异步任务领取、租约、重试或大规模检索需求后作为派生协调状态重新论证，不能默认成为记忆正文的主存储。

## 4. 约束、风险与未知项

- **记忆与规则混淆**：若直接复用 `RuleManager` 的 `<local_rules>`，模型会把可过期记忆当强制规则。必须有独立语义层和明确优先级。
- **提示词注入**：记忆文件可被模型或用户编辑，不能默认可信。结构隔离、非权威声明、当前证据优先和客户端权限只能降低记忆影响模型判断或执行危险操作的概率，不能证明注入风险已经消失。第一版接受这一残余风险，并依靠私有目录、可审计 Markdown 和工具权限限制影响范围。
- **索引/主题一致性**：虽然没有向量索引，但 `MEMORY.md` 仍可能指向不存在的主题。跨文件写入不具备事务原子性；主题 frontmatter 是事实源，启动加载或 `/memory` 应报告断链并给出确定性修复结果，而不是静默猜测。
- **主题重复与命名漂移**：模型可能为同一主题创建多个近义文件，或生成大小写、空格和层级不一致的路径。第一版通过单层 kebab-case、创建前列举与优先复用约定降低风险，加载器负责报告非法文件名和重复索引，但不自动合并语义近似主题。
- **写入权限体验**：记忆写入属于持久修改，应沿用现有 PermissionMode。明确“记住”的用户请求可作为当前调用意图，但不能绕过工具执行边界。
- **当前会话可见性**：冻结快照意味着刚写入的记忆不会立刻进入请求期 meta context。文件工具结果提供当前回合可见性，新的快照在下一会话或成功压缩后生效。
- **标准工具格式漂移**：不使用专用记忆工具意味着客户端不会替模型决定主题结构。system prompt 必须提供精确模板，加载器必须报告重复索引、未知类型和断链；若后续实现 `/memory`，它应展示同一审计结果，但不得静默改写用户 Markdown。
- **多实例并发写入**：多个 MyAgent 实例可能同时读取并修改同一个主题或索引；单文件临时文件加替换只能防止文件损坏，不能避免最后写入者覆盖先前更新。第一版明确不保证同一工作区的多进程写入合并安全；出现真实并发需求后再单独评估文件锁或带版本检查的写入，而不是在当前阶段恢复数据库。
- **项目作用域**：第一版使用 `~/.myagent/projects/<workspace-key>/memory/`，与同一 workspace-key 的其他私有运行数据共同隔离。是否需要跨项目共享用户偏好仍是后续产品决策，不能用复制项目记忆的方式隐式实现。
- **容量阈值**：200 行/20KB 是基于 Claude Code 的 200 行/25KB 经验和本项目现有 20KB 规则上限的初始值。第一版使用固定常量和明确诊断，不提前增加配置面；只有实际 token 使用或截断案例证明不同工作区需要不同阈值时，才考虑配置化。
- **自动提取价值未知**：当前没有实际记忆数据、遗漏率或人工记忆负担证据。第一版不应为假设中的未来规模支付后台模型与协调复杂度。

## 5. 否决方案

- **恢复旧 `MemoryService` 并只删除向量部分**：旧类同时承载文件写入、Forked AgentLoop、生命周期编排和索引同步，会把新设计重新绑回已否决架构。
- **每次 `BeforeModel` 全量注入或检索**：破坏提示词缓存稳定性，为每轮增加 I/O 或模型调用，而且当前没有规模证据。
- **第一版引入 Embedding、VectorDB、SQLite 或 LanceDB**：没有需要分块和语义召回的数据规模，也没有派生索引一致性收益，反而重建刚删除的复杂度。
- **会话关闭时无条件启动提炼模型**：会增加尾延迟、成本和错误记忆概率；短会话、失败会话和敏感上下文也不应默认进入记忆。
- **把所有正文写进单个 `MEMORY.md`**：实现最简单但增长会直接推高每次会话的固定 token 成本，最终仍需要迁移到主题文件。
- **按记忆写入次数刷新会话快照**：刚写入的内容和文件工具结果已经存在于当前对话，任意次数阈值不会增加有效信息，却会引入计数状态并破坏请求前缀稳定性。第一版只在新会话和成功压缩后刷新。
- **第一版开放容量阈值配置**：当前没有不同工作区需要不同阈值的证据。过早加入配置类型、加载、校验和测试只会扩大实现面；先使用固定常量和诊断，再根据真实截断案例决定是否配置化。
- **新增专用 `memory` 工具**：第一版的列举、读取、创建、编辑和删除都与现有文件工具重复。路径与权限属于通用文件安全边界，类型和保存判断属于 system prompt 软约束；复制一套工具协议只会扩大维护面。
- **无路径边界、无格式约束地随意写 Markdown**：复用标准文件工具不等于放弃治理。必须精确授权当前项目 `ApplicationPaths.memoryDir`、给出固定 frontmatter 模板、限制索引容量，并通过加载器或 `/memory` 报告结构问题。
- **把实际 `MEMORY.md` 内容放入 system prompt**：会把可能过期的记忆提升到过强的指令层级，也会把稳定机制规则和动态事实混为一体。实际索引应作为独立 meta user context 注入。
- **首期同时实现项目与用户全局双作用域**：会立即引入优先级、隐私、冲突合并和工具路由问题；应先验证单工作区模型。
