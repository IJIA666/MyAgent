## 背景

在多轮 React/ReAct 会话中，系统经常需要动态挂载临时技能上下文和项目局部规则文件（`.myagent.md`）。在当前实现中，由于 `DefaultContextAdapter` 在每次 LLM 交互时通过 splice 将临时 `system` 消息插拔式塞入最后一条 `user` 消息之前，导致了历史前缀哈希的毁灭性变动。这直接击穿了类似 DeepSeek API 或 Claude API 等底层支持的前缀缓存（Prompt Caching），引致交互响应变慢与 Token 计费成本上升。

## 目标与非目标

**目标:**
- **锁定前缀缓存**：重构 `DefaultContextAdapter` 组装结构，将临时技能与局部规则以特定 XML 标签封装，内嵌拼接在最新一条 `user` 消息的 `content` 尾部，并在持久化历史中物理保留，将 Prompt Caching 命中率提升至 95% 以上。
- **呈现层组件化折叠**：在 Harness 的终端 UI 渲染、日志记录、Rollback 回滚提示语展现时，解析内容中的 XML 定界符并重构为可点击折叠的精美微型卡片，折叠隐藏复杂的技能与规则，在保护排版紧凑性的同时，保留用户的上下文知情权，防范黑盒排查困境。
- **高水位安全兜底**：维持 Token 水平线检测与 `compact()` 压缩的物理轮换，防止由于历史不剪枝导致上下文无限膨胀与单 Session API 超时。

**非目标:**
- **不引入子代理**：本次重构在单会话主循环中解决，不引入 Subagent 或 Session 分叉等复杂的并发控制。
- **不演进自主加载**：本阶段暂不将技能载入演进为 Tool-driven Index（工具驱动索引与按需拉取）模式。
- **不改动模型底层驱动**：不改动 `LlmDriver` 底层的流式数据解析结构。

## 架构决策

- **决策 1：最新 User 消息内容内嵌拼接**
  - *替代方案*：传统中间插入独立 System 消息。
  - *选择理由*：中间插入 System 消息会导致前一轮在“用户输入结束点”落盘的缓存单元被新插入的节点破坏，使得后面的历史全部缓存击穿。将 XML 内嵌拼接在 User 消息尾端，利用了历史消息单向递增追加的特性，100% 锁定了前缀哈希，完全兼容 DeepSeek 硬盘缓存。

- **决策 2：物理持久化带 XML 的消息 + 终端 UI 特征解析与折叠渲染**
  - *替代方案*：1) 持久化干净历史，基于元数据快照动态重载；2) 呈现层通过正则过滤器进行物理抹除净化。
  - *选择理由*：动态元数据重载方案实现复杂，且易引入状态同步漏洞。而彻底的正则抹除虽然解决了排版问题，但会导致调试和排查时的大模型上下文处于“完全黑盒状态”。选择物理持久化带 XML，同时在终端渲染层解析 XML 标签并折叠为带小图标的精美组件（Widget），不仅能实现极端紧凑的视觉效果，还能在用户需要时点击展开，完美兼顾了工程可行性与卓越的 UX 体验。

- **决策 3：增加 XML 前后定界引导语句**
  - *选择理由*：大模型可能将 user 消息内部内嵌的 XML 规则误判为普通业务文本而降低服从度。在拼接 XML 时，加入固定的系统声明前缀（如 `[SYSTEM NOTE: ...]`），并在拼装前对用户输入进行安全转义，以确保模型对规则和技能的最高强度服从。

## 风险与权衡

- **[风险点：长历史下物理压缩的 TTFT 延迟峰值]**
  - *权衡取舍*：由于不剪枝，在长会话下 Token 增长较快。一旦接近水位红线触发 `compact()` 物理轮换，系统会对前缀哈希进行一次性总结重置，导致单次长 TTFT 延迟。
  - *缓解策略*：在终端提供明确的“系统上下文压缩中”提示，平抑用户焦虑；物理重置在整个会话生命周期中频率极低，平均开销极小。
- **[风险点：大模型指令偏航或格式逃逸]**
  - *权衡取舍*：大模型在多轮交互中可能将 XML 内的指令当成普通输入处理。
  - *缓解策略*：在大括号/XML 标签前后追加清晰的系统定界指引语句，且在拼装前对用户输入进行转义，确保模型对规则的绝对遵从。
