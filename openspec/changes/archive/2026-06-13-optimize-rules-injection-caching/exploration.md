# 探索主题: 主会话局部规则与技能注入的缓存优化探索

## 1. 问题定义
大模型在执行多轮对话或 `ReAct` 工具交互时，我们需要动态为当前轮次注入特定项目规则（ `.myagent.md` ）与临时技能详情（ `SKILL.md` 正文）。当前在最后一条 `user` 消息前强行插入独立的 `system` 消息节点的设计，不仅破坏了消息时序（打破了 `user -> assistant -> tool -> user` 连替），而且导致历史哈希错位，致使服务端的 `Prompt Caching` 缓存大范围失效，产生了高昂的 API 开销与极大的响应延迟。因此，我们需要寻找一种在不引入复杂的子代理（ Subagent ）架构前提下，最能保障缓存命中率、维护时序完整、同时合理控制会话体积的注入方案。

## 2. 关键发现与调研结果
- **代码库现状**：我们分析了 [DefaultContextAdapter.ts](file:///d:/projects/MyAgent/src/brain/adapters/DefaultContextAdapter.ts) 的 `assemble` 逻辑，发现其通过在 `lastUserIndex` 之前插入独立 `system` 消息来挂载临时技能与局部规则。在多轮交互中，由于旧注入节点位置的跳变，会导致消息前缀哈希频繁错位，破坏了服务端缓存。
- **行业单会话缓存机制洞察**：
  - **动态分块与缓存锁定 (Claude Code)**：利用 `lodash/memoize` 对本地规则的读取进行内存锁定，限制运行期内的前缀抖动。同时将 `System Prompt` 数组化分块注入（Coordinator, Agent, Default 等），并显式在倒数第二条消息中挂载 `cache_control: { type: 'ephemeral' }`。
  - **即时工具输出注入 (Gemini-CLI)**：采用 JIT 机制，在 `read_file`、`write_file` 等高意图工具返回结果时，动态发现路径下的 `GEMINI.md`，直接将其拼接到工具的 `response` 尾部一同返回。规则作为工具输出追加，前缀哈希严格稳固。
  - **不可变碎片追加与呈现过滤 (Codex)**：通过 `ContextualUserFragment` 强类型定义，动态上下文渲染为带有专属 `start/end` 标记的字符串作为独立消息单向物理追加（No history rewrite）。在 TUI 呈现层利用 `is_contextual_user_fragment` 辅助函数匹配标记并过滤隐藏，实现存储与呈现分离。
  - **时序系统消息尾部追加 (OpenCode)**：环境或技能发生变动时，不在头部修改 System Prompt，而是以 `<conversation-checkpoint>` 消息块的形式在会话最尾端进行增量追加，规避缓存大范围失效。

## 3. 方案对比与推荐方向
| 评估维度 | 方案 A：最后一条 User 消息 Content 拼接 | 方案 B：传统中间插入独立 System 消息 (当前方案) | 方案 C：子代理分叉隔离 (Forked) | 结论 |
| :--- | :--- | :--- | :--- | :--- |
| **缓存前缀保护** | 极佳 (保留历史哈希前缀，近 100% 缓存命中) | 极差 (历史索引变动，高频发生击穿) | 极佳 (主会话完全静态) | 方案 A 和 C 占优 |
| **消息时序完整性** | 完美 (保持自然 role 轮替) | 破坏 (中间插入 system 节点) | 完美 (保持自然 role 轮替) | 方案 A 和 C 占优 |
| **开发与维护成本** | 极低 (轻量级字符串模版替换) | 较低 (现成代码，但逻辑脆弱) | 极高 (引入子进程与状态流转) | 方案 A 占优 |
| **历史上下文体积** | 中等膨胀 (需依赖高水位物理重置) | 严重膨胀 (残留冗余节点) | 极小 (完全隔离噪声) | 方案 C 占优，方案 A 可控 |

**推荐路径**：选择 **方案 A（最新 User 消息内容内嵌拼接）** 加上 **高水位物理压缩（ `compact()` ）兜底** 的混合路径。
理由：该路径在不引入子代理的前提下，用极低的代码开发成本，实现了 100% 的时序完整和极高的短时高频交互缓存命中。虽然牺牲了“上下文绝对不膨胀”，但现代模型拥有极大的上下文物理容量，结合 10% 价格的 Prompt 缓存折扣，即使出现温和膨胀，其费用与响应时间也远远低于因缓存频繁击穿而带来的损耗。我们只需在大容量警戒线上以物理压缩（ `compact()` ）进行一次性的缓存重置，即可获得长效且高性价比的表现。

## 4. 约束、风险与未知项
- **长历史时的物理重置代价**：由于牺牲了上下文绝对不膨胀，当单次会话持续极久并达到警戒水位线（如 60k Tokens ）触发物理压缩时，大模型在当前轮次会由于缓存重置产生一次性长达数秒的 `TTFT` 延迟和单次全量 Token 计费。
- **多技能并发重叠限制**：如果用户同时激活多个重型技能，全部拼接在最新一条 `user` 消息中会导致单轮请求的 Token 数爆发，需要做好单个 User 消息长度的硬上限拦截与警报机制。

## 5. 否决方案
- **会话内高频实时历史剪枝**：被舍弃。如果在每一轮交互之后都尝试在本地“抠掉”上一轮 User 消息中注入的技能全文，不仅代码实现复杂度高、极易导致哈希重组错乱，而且会由于每一轮都改变历史消息文本，导致大模型服务端的 `Prefix Cache` 发生高频击穿，丧失了缓存的加速和省钱红利，得不偿失。
