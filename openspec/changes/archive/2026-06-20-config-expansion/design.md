## 背景

目前系统中针对 Agent 运行迭代上限和各类工具输入/输出字符截断的阈值，均以局部硬编码常量的形式分散在代码库的各个子模块中。这使得外部环境（如对接推理时间与调用配额各异的 LLM 模型时）无法对系统的运行额度和资源开销进行灵活管控。我们需要引入一种全局配置管理和依赖注入模式，以在统一收口这些参数的同时维持现有模块的松耦合设计。

## 目标与非目标

**目标:**
- 统一将最大迭代轮数、大工具落盘限制、批量读取限制、搜索结果限制及自动压缩水位 5 个核心常数归集并收口至 `AppConfig.runtimeLimits` 配置对象下，实现逻辑分类管理。
- 允许通过环境变量及 `.env` 对这 5 项参数进行自由设定。
- 确保当未配置相应环境变量时，系统能无缝降级使用原先的硬编码数值作为兜底。
- 提供面向 Native 工具、插件及领域服务的松耦合依赖注入路径。

**非目标:**
- 本次改动**不引入**复杂的运行时配置热刷新或动态监听器，配置仅在系统初始化阶段（即 `loadConfig()` 调用时）一次性加载并执行防御性深度冻结。
- 本设计**不改变**工具本身的执行机制，仅改变其读取阈值的策略。

## 架构决策

### 1. 采用 `SessionContext` 作为配置的运行时传输载体
- **决策内容**：在 `SessionContext` 中维护 `appConfig?: AppConfig` 属性，并在 `SessionManager` 实例化时将全局配置注入。工具执行时，通过传入的 `sessionContext` 参数来读取具体的配置限制。
- **决策原因**：
  - 本地的 Native 工具是在 `LocalFileSystemMcpServer` 实例化时一并静态注册的。如果通过构造函数将 `AppConfig` 传递给每个工具，会导致工具的声明与虚拟 MCP 服务器的装配层变得臃肿且极难维护。
  - 原本工具在执行 `execute(args, sessionContext)` 时就会接收 `sessionContext`。将其作为媒介在运行时传递配置，能保证工具的单例特征，解耦实例化依赖，实现零侵入性注入。

### 2. 在配置加载器中执行 fail-safe 类型安全校验
- **决策内容**：在 `src/config/loader.ts` 解析环境变量时，必须进行防呆防崩溃处理。
- **决策原因**：环境变量获取的皆为 `string`，对其进行 `parseInt` 或 `parseFloat` 转换时，可能因非法格式（如配置为 `"abc"` 或为空白字符）产生 `NaN`。此时加载器必须静默捕获该异常，并自动回退为对应的常量默认值，确保系统在配置出错时仍能正常启动，而不会直接引发 runtime crash。

### 3. 选择手写轻量级辅助解析器而非引入 Zod 依赖
- **决策内容**：在配置加载层手动封装高复用型的类型安全转换函数，而不引入 Zod 库。
- **决策原因**：通过查看 `package.json`，本项目目前没有任何地方依赖 Zod。为了仅解析 5 个新增环境变量而额外引入 Zod 库，会增加项目的依赖负担和加载开销。我们通过在 `src/config/loader.ts` 中封装极简且健壮的数字/浮点数转换辅助函数（辅以 NaN 判定与默认值退化机制），即可在零依赖开销的前提下完全实现类型安全与 fail-safe 保护。

## 风险与权衡

- **[配置项未配置或缺失]**
  - *风险描述*：用户运行在干净的环境（如没有新增环境变量的测试沙箱）中可能直接导致未定义异常。
  - *缓解策略*：在 `loadConfig()` 中提供硬编码常量值兜底：
    - `maxIterations` 默认 `20`
    - `largeToolOutputLimit` 默认 `8000`
    - `readManyFilesLimit` 默认 `50000`
    - `searchLimit` 默认 `100`
    - `compactionWatermarkFactor` 默认 `0.8`
- **[配置在运行期被意外修改]**
  - *风险描述*：由于 JavaScript 对象的引用传递，某些业务逻辑可能会无意中修改全局配置。
  - *缓解策略*：继续严格执行 `Object.freeze(config)` 深度冻结机制，阻止在任何其他地方对 `AppConfig` 及子配置对象进行运行时篡改。
