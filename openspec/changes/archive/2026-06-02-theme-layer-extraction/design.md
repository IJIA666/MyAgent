## 背景

当前代码库中，`src/interface/cli.ts` 和 `src/interface/command.ts` 直接硬编码了大量的 ANSI 颜色字符串常量（例如 `\x1b[32m` 等）。这种做法导致界面底层渲染逻辑与系统核心的业务流调度逻辑高度耦合，在视觉样式调整以及未来的多端 UI 演进（如 Web 适配）时存在极大的隐患。

## 目标与非目标

**目标:**
- 提取并隔离所有 ANSI 常量至专属的 `src/interface/theme.ts` 抽象层中。
- 提供一组高度语义化的包装函数集（如 `theme.success()`, `theme.error()`, `theme.dim()` 等）。
- 替换现有业务控制流及调度中心里所有涉及硬编码拼接颜色常量的地方。

**非目标:**
- 引入第三方的终端渲染/美化包（如 `chalk` 或 `colors`），依然保持项目的零依赖特性。
- 修改大模型底层流式吐字的通信管道，本次变革仅针对本地交互反馈终端进行防腐隔离。

## 架构决策

- **决策一：采用语义化的包裹函数 API (Wrapper API)**
  - *方案*：我们不暴露底层的颜色常量对象（如不使用 `Theme.GREEN + text + Theme.RESET`），而是对外暴露纯函数 `theme.success(text)`。
  - *理由*：通过函数接管渲染过程，我们在未来如果需要将 Agent 接入基于 JSON 的富媒体前端，只需重写这些方法返回带有结构化标签的内容，而不用修改一处业务代码。
- **决策二：函数的纯粹性设计**
  - *方案*：`theme` 下所有的方法必须是纯函数，即输入普通 string，输出经过视觉处理的 string。它不应该具有直接将字符输出到 `stdout` 的副作用（即不能在内部调用 `console.log`）。
  - *理由*：保持可测试性，同时兼容现有的 `readline.write()` 机制流转。

## 风险与权衡

- **风险: 颜色泄露（游标复位遗漏）** → 在手动拼接和替换的过程中，如果内部实现漏掉了颜色复位控制符（`\x1b[0m`），会导致紧跟在后面的标准输出全盘颜色错乱。
  - *缓解措施*：在 `theme` 模块的底层包裹实现中，统一执行强制性复位后缀追加机制，确保每个被包裹的字符串视觉表现彻底内聚。
