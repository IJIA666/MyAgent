## 背景

当前系统的浏览器感知机制仅依赖于 `generateAriaSnapshot` 方法，该方法通过严格的交互元素选择器来过滤网页内容，这导致普通非交互的文字（如文章正文、博客段落、SPA 信息记录等）在感知阶段被全量剥离。智能体在遇到此类纯内容展示页面时，由于得不到关键的文本感知输入，无法进行有效阅读、提取和分析。因此，需要在内置的原生浏览器操作集中，引入一个只读的网页文本内容提取工具 `browser_get_text`，作为智能体的眼睛，恢复其在内容展示页面的文本感知。

## 目标与非目标

**目标:**
1. 实现只读原生浏览器文本提取工具 `BrowserGetTextTool`（注册名为 `browser_get_text`），并注册于虚拟 MCP 中。
2. 支持使用 CSS 选择器参数（`selector`，可选，默认 `"body"`）在目标页面进行范围过滤与提取。
3. 提取过程中能自动过滤不包含可读文本的标签噪声（包括 `<script>`、`<style>`、`<noscript>`、`<svg>` 等）及受 CSS 隐藏的不可见元素。
4. 针对选择器在页面匹配多个节点的情况，提供高容错、防崩溃的多节点并行提取与拼接（使用 `\n\n` 分隔）。
5. 引入硬性的最大文本提取长度截断防御机制（限制在 80,000 字符内），以防大量无用数据撑爆大模型 Token。

**非目标:**
1. 不修改 `generateAriaSnapshot` 现有的交互元素过滤快照逻辑。
2. 不在底座中实现复杂的人工智能网页正文主动提取排版算法（如计算各块密度等），直接依赖 Playwright 官方渲染树进行人类可见文本的抓取。
3. 不破坏已有的向后兼容性，本变更完全为增量纯新增工具。

## 架构决策

- **决策 1：选用 Playwright 原生提供的 `locator.innerText()` API**
  - **理由**：Playwright 的 `innerText()` 能够高度模拟人类对网页的物理阅读感知。它在浏览器渲染布局树层工作，会自动忽略所有受 CSS（如 `display: none`、`visibility: hidden`）隐藏的元素，且天然不解析 `<script>` 和 `<style>` 的内部源码。这避免了我们自行在 JS 端编写深度递归过滤 DOM 树带来的高计算开销与逻辑 Bug。
  - **替代方案**：通过 evaluate 在浏览器端使用 `textContent` 克隆并剔除噪声。由于在内存中克隆的未插入 DOM 树的节点调用 `innerText` 恒为空，使用 `textContent` 则不可避免地会将 script/style 源码导出，产生极大的幻觉噪声。因此舍弃。
- **决策 2：结合 `locator.all()` 提取所有元素，消除严格模式冲突**
  - **理由**：当提供的 CSS 选择器匹配到页面上多个节点时，直接对 locator 调用 `innerText()` 会触发 Playwright 的严格模式异常（Strict Mode Violation）导致系统崩毁。我们使用 `locator.all()` 先获取匹配的 locator 实例数组，再遍历提取，既保证了多节点提取的灵活性，又消除了严格模式崩溃的隐患。
- **决策 3：Schema 警告与执行层硬截断机制双重防御**
  - **理由**：全页 body 提取在遇到庞大页面时极易产生上兆的字符流。我们通过双重方式进行防御：第一是在 JSON Schema 的 `selector` 说明中，用强烈的警告性语气规制大模型，使其在需要阅读长文或列表时必须传入精确 CSS 选择器以规避拉取 body 的高昂代价；第二是在执行层物理兜底使用 `.slice(0, 80000)`，防止极端恶劣大网页载荷导致内存或 Token 超限崩溃。

## 风险与权衡

- **[风险 1：选择器过于宽泛，导致 Token 暴涨或截断后丢失关键尾部文本]** -> **缓解策略**：在 JSON Schema 的描述中加入强规则警告，引导智能体必须优先分析页面结构并传入精确选择器。同时，80,000 字符作为物理安全截断水位，能够包容绝大多数超长正文，且防范系统崩溃。
- **[风险 2：获取文本时页面未加载完毕，提取到空内容]** -> **缓解策略**：由于调用此工具前必须已调用 `browser_navigate`，导航已做了 `waitUntil: 'load'`。如果智能体在执行此步骤时依然发生元素为空，工具将抛出明确的选择器未找到错误，使得智能体能基于错误进行重试或调整选择器。
