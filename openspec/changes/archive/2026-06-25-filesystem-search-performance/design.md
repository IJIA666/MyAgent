## 背景

当前系统的本地文件检索机制由 `GrepSearchTool` 与 `GlobSearchTool` 共同支撑，其底层的文件查找逻辑依赖于一个递归的同步目录扫描函数 `scanDir`。由于该函数在主线程中全同步运行（使用 `readdirSync` 和 `statSync` ），且缺乏对大型开发关联子目录（如 `.venv`、构建目录、缓存目录等）的智能排除过滤，导致在大中型代码库环境下执行全文 Grep 匹配时会卡死 Event Loop 并带来内存耗尽（OOM）的风险。

## 目标与非目标

**目标:**
- 将 `scanDir` 从同步递归改造为基于 Node.js 原生 API 的异步流式遍历器，降低检索时的内存峰值。
- 在目录层级实现前置的“剪枝（Pruning）”策略，识别到被排除的目录直接跳过，绝不下探。
- 自研一个极简的 Promise 信号量调度器，将全文检索时的并发文件读取句柄数量严格控制在 20-50 之内，彻底消除 `EMFILE` 风险。
- 将文件排除规则统一交由 `AppConfig` 的 `runtimeLimits` 配置项进行动态载入与配置化隔离。

**非目标:**
- 坚决不改变 `GrepSearchTool` 与 `GlobSearchTool` 面向 LLM 的入参和出参契约 Schema，确保调用方无感。
- 坚决不引入任何额外的第三方 npm 包（如 `p-limit`, `fast-glob` 等），确保该模块零外部依赖。
- 不对除文件检索工具外的其它文件工具（如 `readFile`, `writeFile`）进行异步化或信号量改造。

## 架构决策

1. **基于 `fs.promises.opendir` 的异步流式迭代器**
   - **决策**：舍弃原有的 `readdirSync` 收集，改用 Node.js 内置的 `fs.promises.opendir` 结合 `async function*` 异步生成器。
   - **理由**：`opendir` 返回一个异步迭代器，按需从系统缓冲中拉取文件条目，不会像 `readdir` 那样一次性将数万文件名读入 V8 堆内存，对超大项目能维持极低的稳定内存开销。
2. **顶层目录前置剪枝 (Top-level Pruning)**
   - **决策**：规则匹配逻辑与异步迭代器深度结合。当迭代器检测到某一 `Dirent` 是目录且在排除名单中时，立刻拦截，不再对其执行下行 `yield*`。
   - **理由**：若下探到叶子节点才过滤路径，扫描依然会遍历巨量的垃圾文件夹，只有前置剪枝才能使 IO 物理消耗减少几个数量级。
3. **自研极简 Promise 信号量调度器 (Zero-Dependency Semaphore)**
   - **决策**：不引入 `p-limit` 等依赖，通过维持一个执行中的 Promise 队列手写极简限流器。当并发达到限制时，后续的 `readFile` 任务将返回一个排队等待的 Promise，在有任务 resolve 后按序被唤醒。
   - **理由**：贯彻项目“零依赖、内聚稳定”的技术方针，降低项目向下兼容的包负担，且极简限流逻辑约 20 行即可完成。

## 风险与权衡

- **【文件描述符超载风险 (EMFILE)】**
  - **风险描述**：异步并发读取海量文件内容执行正则匹配时，可能会瞬间突破操作系统的文件描述符上限限制，抛出 `EMFILE` 错误。
  - **缓解策略**：在遍历文件执行读取时，强行经过自研信号量调度器包装，设定最高并发数为 30，实施滑动窗口限流。
- **【排除规则正则表达式预编译开销】**
  - **风险描述**：对每一层目录进行排除判断时，重复实例化正则或 Glob 转换会带来不必要的 CPU 消耗。
  - **缓解策略**：在检索函数入口处，将配置项加载的排除规则（如 `.venv`, `dist`, `node_modules`）一次性预编译为正则表达式，并在递归过程中复用编译后的 regex 实例。
