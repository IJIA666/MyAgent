## 背景

在当前的 `MyAgent` 系统中，除了基础的文件读写与局部编辑等 8 个原生工具外，缺乏针对目录管理、路径删除、批量文件读取、Git 只读查看以及敏感操作审核等高频功能的原生支持。大模型为了实现这些能力，不得不频繁组装终端命令行并在 `executeCommand` 中执行。这引发了跨平台兼容失败率高、命令注入与路径越权风险高、终端输出解析低效的问题。

本设计旨在扩展 `MyAgent` 原生 TS 工具链，并在系统底座实现对敏感操作的前置确权凭证校验（ `WriteApproval` 拦截）、批量读取的体积熔断及双轨代码修补机制。

## 目标与非目标

**目标:**
1. **跨平台原生路径管理**：实现原生 TS 目录创建、文件/目录安全删除、文件移动与复制，彻底磨平 Windows/Linux 命令差异，并强制在底层做工作区路径越权校验。
2. **高吞吐无幻觉批量读取**：实现多文件并行批量读取工具，采用“前置体积熔断与拒签自适应信息返回”代替硬性字符物理截断，防止不完整代码引发 LLM 上下文幻觉。
3. **高容错代码修补**：实现基于标准 Unified Diff 库解析的严格补丁应用工具；以及作为替代 and 主力的“上下文签名特征块替换”工具，基于大致行范围与期望原文滑动窗口特征匹配执行块替换，解决行号漂移问题。
4. **只读 Git 感知**：原生封装 Git 状态、日志和增量 Diff 查看，返回结构化 JSON 数据，隔离写操作。
5. **原生安全确权卡关**：敏感删除操作（ 如 `deletePath` ）直接对接底座原生的 `ApprovalService` 挂起式审批服务，通过控制台实时卡关，确保审计安全。
6. **单层扁平 Schema 规范**：所有原生工具参数设计保持扁平化单层结构，杜绝复杂对象嵌套，优化 DeepSeek 及 OpenAI 的接口推断性能。

**非目标:**
1. **不开发** 自研的 Unified Diff 模糊匹配对齐算法。出现上下文冲突或错位时，严格模式直接强硬报错熔断。
2. **不开发** 复杂的会话级临时凭证状态机与 Token 流转机制。直接复用成熟的挂起式审批拦截，保持大模型一次性调用闭环。
3. **不开发** 任何带有写/变更属性的 Git 工具（ 如 `git commit`/`git push` ）。
4. **不开发** 基于 LSP 语言服务的深度类型级分析（ 列为长远非核心演进目标 ）。

## 架构决策

### 决策一：双轨代码修补策略（ 严格 Patch 模式 + 签名特征块替换 ）
* **原因**： 徒手在 Node.js 中编写针对 Unified Diff 的 Fuzzy 模糊对齐匹配不仅复杂度高，而且在 DeepSeek 排版幻觉（ 空格缩进错位 ）下极易将补丁错配到其他相似的声明区域，产生严重隐患。因此，我们在修补工具上采用“双轨并行”：
  1. 对于标准的严格 Patch 模式，采用成熟的第三方 Unified Diff 解析库，遇到冲突直接报错拒签；
  2. 作为主力替换工具，提供“上下文签名特征块替换”：LLM 给出大致的行号范围 `[startLine, endLine]` 并传入 2-3 行的期望原文特征签名 `expectedContent` 和替换后的 `replacementContent`。工具在行号邻域范围内使用滑动窗口检索该签名特征，定位成功后执行块替换。该方式实现简单，且对大模型的行号偏移和空格幻觉具备天然的极高容错性。

### 决策二：批量读取前置熔断与拒签自适应信息返回
* **原因**： 如果在读取超限时在尾部进行物理硬截断（ 如只返回前 80% 的代码 ），会遗留未闭合的花括号或残缺语句，大模型在上下文被破坏后极易误判文件不完整并产生逻辑幻觉。因此，我们废弃硬截断，当并行读取的批次文件总体积/ Token 超出 50,000 字符阈值时直接熔断报错。同时，为了规避对超大压缩或非标准代码文件解析时可能导致的 CPU 阻塞与内存卡顿风险，我们**坚决不引入重型 AST 解析器**，改用毫秒级的轻量正则表达式行捕获（ 提取 `class` / `function` / `interface` / `export const` 等关键字大纲 ）。对正则不适用的文件，则降级返回“文件总行数与首尾各 20 行”。这让大模型能极低开销、极速地拿到文件大纲概要，决策如何局部精读。

### 决策三：复用底座原生挂起式安全审批（ ApprovalService 集成 ）
* **原因**： 虽然中途挂起线程在分布式网络应用中不可取，但本系统定位为本地单机 CLI 会话应用。底座已经具备了成熟的异步挂起 `ApprovalService` 服务以及 REPL 输入监听器 `InputListener` 隔离与 `resolve` 唤醒机制。更重要的是，在 OpenAI 标准接口与流式 API 规范下，大模型流式吐出 Tool Call 后已在等待工具执行结果，此时挂起底层工具的 Promise 执行，只相当于工具调用网络延迟，**并不存在大模型推理侧的超时断开风险**。因此，我们直接复用已有基建对高危操作（ 如 `deletePath` ）进行底层拦截挂起卡关。这最大化利用了已有代码，设计极度精炼稳定，杜绝了大模型幻觉绕过与 Token 传递的复杂开销。

### 决策四：工具参数单层扁平化 Schema 规范
* **原因**： 系统主要对接 DeepSeek API 且适配 OpenAI 协议标准。大模型在组装多重嵌套的对象类型参数（ 如 parameters 下又套一层 objects ）时，推断失误率明显高于单层扁平字段。所有原生工具的 API 定义将统一约束在单层扁平结构中。

## 风险与权衡

* **特征签名在重复结构下定位失焦**：
  * **风险**： 当“特征块替换”工具被调用时，若大模型提供的 expectedContent 过于简短（ 比如只提供了一个右括号 `}` ），且在行号邻域附近存在多个重复结构，将导致滑动窗口检索匹配出多处定位，引发匹配冲突。
  * **缓解策略**： 在工具的 Schema 参数 description 中强行约束 LLM ，必须提供包含具有唯一区别度的上下文特征签名（ 如包含多行或带有特定关键字的语句 ）。如果滑动窗口搜寻到多于 1 处的签名对齐，工具直接报错熔断并要求缩窄行号范围。

* **挂起卡关导致的 CLI 界面 Stdin 抢占冲突**：
  * **风险**： 工具底层被 `ApprovalService` 挂起以在控制台进行 readline 提问时，如果 REPL 的全局 `InputListener` 没有物理注销并关闭输入流监听，用户输入的审批键值会被原输入流抢占拦截，导致事件穿透、死锁或回显污染。
  * **缓解策略**： 严格在 CLI 层的审批处理函数中，在前置提问 rl.question 启动前，物理注销 InputListener 全局监听并 close 全局 process.stdin。在 resolve 解锁唤醒底座后，重新 start 重建全局监听。
