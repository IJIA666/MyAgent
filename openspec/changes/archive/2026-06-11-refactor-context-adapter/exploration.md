# 探索报告：规则加载、缓存管理与 Agent 架构演进

## 1. 探索背景与技术考量
在架构演进中，需要平衡以下技术考量：
- **高频规则加载**：系统需要根据用户指令实时切换领域上下文（如按需加载特定的 `SKILL.md`），以保持模型专注度。
- **提示词缓存（Prompt Caching）限制**：多数主流大模型采用前缀匹配机制。一旦对头部的系统提示词（System Prompt）进行修改，会影响缓存命中率，增加延迟与成本。

为了兼顾灵活性与缓存匹配率，需要寻找合理的上下文注入解决方案。

## 2. 架构设计：Harness + Skill 模式
评估表明，当前系统的调度逻辑（特别是 `session.ts` 中基于 `while` 循环的流程）适用于 Harness + Skill 的设计模式。

- **Harness（约束框架）**：
  - **不采用图结构工作流**：不需要引入具有预设图节点和状态转移的复杂工作流框架。
  - **基于主循环路由**：由大模型决定每一步的逻辑，通过设置 `maxIterations` 避免无限循环。
- **Skill（临时技能注入）**：
  - **双层结构**：全局 System Prompt 仅保留技能名称与目录索引，使模型具备全局视野。
  - **动态加载**：当需要使用某项技能时，将技能的执行手册作为临时上下文加载。

## 3. 上下文处理机制：策略适配器与临时挂载
为了兼顾不同模型的缓存匹配，采用策略适配器模式（Context Adapter Pattern）。

### 第一阶段：固定前缀与尾部临时挂载
针对目前主流的前缀缓存模型，确立以下方案：
1. **前缀固定**：将基础规则作为初始消息载入后，在会话生命周期内锁定为只读状态。
2. **临时挂载**：将提取的 `SKILL.md` 使用 XML 标签（如 `<transient_skill>`）包裹，临时拼接在最新一条 User 消息之前。
3. **清理机制**：单次交互处理完毕后，将该临时消息从消息序列中移除。

*注：系统接受因多轮调用同一技能带来的部分 Token 损耗，以保持流程的简洁与解耦。*

## 4. 缓存机制分析与历史上下文隔离
在调研中，存在以下技术特征：

1. **缓存阈值特征**：
   - **高频动态注入的影响**：如果在 System Prompt 中动态注入工具列表和环境状态，可能由于基础文本较短，达不到模型开启缓存的最小字数阈值（例如 1024 标记），导致缓存无法生效。
   - **大文本体积效应**：当注入较长的静态文本（如技能规范）时，因超过了字数阈值，能够使缓存机制生效，从而降低交互延迟。
2. **历史数据影响**：
   - 在特定会话中产生的详细执行日志会留存在历史记录中。切回全局模式后，模型可能会受到历史记录的影响（即近因效应）。后续设计沙盒退出时，需考虑历史压缩（Context Compression）或由用户手动清理。

## 5. 远期规划：子代理委派与缓存复用 (Subagent Forking)
在单体流程的基础上，为解决处理长周期、多任务（如全局检索、代码试错）时容易出现的上下文干扰与大模型关注度分散问题，后续可引入子代理委派机制：
- **子会话隔离**：主流程遇到复杂任务时，可以启动独立的子上下文窗口（Subagent）执行具体的调试与试错步骤。
- **缓存复用**：启动子会话时利用前缀匹配，使子会话能复用主会话的上下文缓存以降低开销。
- **结果汇报**：子会话执行完毕后，仅向主流程返回提炼后的摘要和最终结果，避免主上下文被过多冗余信息干扰。

## 6. 进阶能力：水位线监控与中部压缩机制 (Context Management)
在上下文注入与委派机制之间，需引入上下文控制以应对长周期任务：
1. **水位线监控 (Token Analytics)**：在每次发起 LLM 请求前，实时分析当前上下文占总容量的比例。
2. **中间上下文压缩**：当上下文使用率达到设定阈值（如 80%）时，保留头部全局规则与尾部近期对话记录，将中间历史对话进行提炼摘要并替换，以防止上下文溢出并保留长期记忆。

## 7. 现状诊断与下一步行动 (Action Items)
目前的提示词拼接与临时挂载逻辑硬编码在 `src/brain/session.ts` 核心控制流内。

**后续实施计划：**
- **架构解耦**：创建并引入标准的 `ContextAdapter` 接口，将 `session.ts` 中的动态提示词组装与入栈逻辑彻底抽离，并为后续集成“水位线监控”和“中部压缩”预留接口。
- **收益**：使控制流更加清晰，并为后续适配不同模型扫清障碍。
