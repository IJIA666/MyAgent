# 探索主题：模型工作模式感知边界

## 1. 问题定义

MyAgent 当前会把 `SecurityMode: Plan`、Plan 专用规则、诊断预算和内部副作用分类通过系统提示词、动态 `<system-reminder>` 或事件消息暴露给模型。真实日志表明，模型会立即围绕这些内部状态进行元推理，分散对用户目标的注意力。需要明确：模型究竟应感知当前工作模式名称，还是只感知完成任务所需的行为约束与可用能力。

本探索只讨论模型上下文与运行时控制平面的边界，不讨论具体诊断证据解析、收敛算法或审批 UI 实现。

## 2. 关键发现与调研结果

- **代码库现状**：
  - `src/core/usecases/engine/model-request-assembler.ts` 会把 `SecurityMode: ${currentMode}` 注入最后一条 User 消息。
  - `src/core/usecases/brain/prompts.ts` 在稳定提示词中直接描述 Plan 模式的工具使用规则。
  - `ModelRequestAssembler` 已能按运行时 `workMode` 裁剪工具；`HumanApprovalPlugin`、`ApprovalPolicy` 和工具策略层也会独立消费模式完成真实授权判定。因此，安全执行不需要模型知道内部枚举名。
  - 最新 `.myagent` 会话中，模型第一轮 reasoning 直接引用 `Plan`、扫描预算和模式规则，随后把注意力转向框架限制，证明内部状态注入会形成明显的元认知干扰。
- **竞品核实**：
  - Claude Code 在 Plan 工作流中向模型明确注入 `Plan mode is active`，同时配套计划文件、退出 Plan 和正式审批协议。
  - OpenCode 的 `packages/opencode/src/session/prompt/plan-mode.txt` 同样明确通知 Plan，并定义分阶段调研、设计、计划文件与退出工具。
  - Gemini CLI 的 prompt preamble 会标明 `Default / Plan / YOLO / Auto-Edit`；其 Plan 还包含 `enter_plan_mode`、`exit_plan_mode`、计划文件和审批转换。官方说明见 https://geminicli.com/docs/cli/plan-mode/ 。
  - 这些事实说明主流编码 Agent 并非普遍隐藏 Plan；但它们暴露 Plan 的主要理由是 Plan 同时改变任务阶段和工作流，而不只是调整工具权限。
- **关键洞察**：
  - “任务阶段”与“审批策略”是两个独立维度。Plan 可以表示规划阶段；Safe、Auto、YOLO 表示审批强度。当前 `WorkMode` 把两者混在一个枚举中。
  - 模型必须知道当前能做什么、不能做什么，否则会产生大量注定被拒绝的调用；但模型不需要知道控制平面的字段名、枚举值、白名单优先级或副作用分类。
  - 工具裁剪和运行时策略决定真实能力，提示词只负责帮助模型有效使用当前能力，不能成为安全边界。

## 3. 方案对比与推荐方向

| 评估维度 | 方案 A：完全隐藏 | 方案 B：只暴露行为约束与能力 | 方案 C：显式暴露内部模式名 | 结论 |
| :--- | :--- | :--- | :--- | :--- |
| 越权调用与无效往返 | 高 | 低 | 低 | B/C 较好 |
| 与控制平面耦合 | 最低 | 低 | 高 | B 更稳健 |
| 模型元认知干扰 | 低 | 低 | 高 | A/B 较好 |
| 模式重命名与扩展成本 | 低 | 低 | 高 | B 更好 |
| 支持普通权限策略 | 差 | 最佳 | 过度暴露 | B 最适合 |
| 支持正式 Plan 工作流 | 差 | 可表达阶段约束 | 最直接 | 若存在正式工作流，B/C 均可 |
| 安全保证 | 取决于运行时 | 取决于运行时 | 取决于运行时 | 三者均不能替代物理策略 |

**推荐路径**：采用方案 B——模型感知任务所需的行为约束和当前可用能力，但不感知内部 `WorkMode`、审批策略或副作用分类枚举。

模型可以收到：

> 本轮仅允许读取、分析和提出建议，不得修改文件或系统状态。可用工具已经按当前权限配置。

模型不得收到：

- `SecurityMode: Plan`
- `workMode=Auto`
- `YOLO mode`
- `planSideEffect=read`
- 白名单优先级、授权容器和其他控制平面术语

运行时仍必须独立完成：

1. 根据会话状态裁剪或物化工具表面；
2. 在 ToolPolicy 和执行边界判定副作用；
3. 在 ApprovalPolicy 中决定审批选择；
4. 在授权消费链中落实 call、session、persistent；
5. 即使模型违反行为提示，也在物理层拒绝越权操作。

如果未来 MyAgent 将 Plan 升级为包含计划文件、阶段转换、正式审批和退出协议的完整工作流，可以向模型暴露“当前处于规划阶段”这一业务语义，但仍不应暴露内部枚举和审批实现细节。

长期建议把现有单一 `WorkMode` 拆成两个正交维度：

- `TaskPhase`: `execute | plan`
- `ApprovalPolicy`: `safe | auto | bypass`

模型最多感知 `TaskPhase` 对应的行为要求；`ApprovalPolicy` 始终属于控制平面。

## 4. 约束、风险与未知项

- 行为约束不能只写“请勿修改”，必须与实际工具裁剪、策略拒绝和审计保持一致，否则仍会出现提示词与物理能力漂移。
- 完全移除 Plan 名称后，需要验证不同模型能否仅凭“只读、分析、建议”约束稳定停止写入尝试。
- 如果工具表面随权限动态变化，会影响 API 前缀缓存；该成本应由配置和实测决定，不能以缓存为理由把安全职责重新推给提示词。
- CLI 面向用户仍可展示当前工作模式；本探索限制的是发给模型的上下文，不限制用户界面和审计日志。
- 当前 change `harden-agent-evidence-and-authorization-loop` 的 proposal、design、specs 和返工任务必须按该边界统一修订，不能只删除一行 `SecurityMode` 注入。

## 5. 否决方案

- **完全隐藏且保持完整工具列表**：模型无法预判哪些操作会被拒绝，会恢复无效调用和重试循环。
- **直接暴露 `SecurityMode` / `WorkMode` 枚举**：把模型与控制平面实现绑定，并已在真实日志中造成元认知干扰。
- **只依赖提示词保证只读**：提示词不是安全边界，无法替代工具裁剪、策略拒绝和执行期校验。
- **把 Safe、Auto、YOLO 当成任务阶段告知模型**：这些是审批策略，不应改变模型对用户目标的理解，也不应诱导模型因 YOLO 而降低谨慎程度。
