## 背景

当前内置工具执行链为 `ToolCallOrchestrator -> ToolRegistry.callTool -> ToolExecutor.execute`，审批由 `HumanApprovalPlugin` 在执行前通过 `ToolPolicyPort` 和 `ApprovalPolicy` 处理，执行后再由工具解析实际 effect。诊断状态由 AgentLoop 维护并通过 `ModelRequestAssembler` 注入动态 reminder。

现有边界分别具备部分能力，但没有形成闭环：终端工具能识别 Plan 安全只读命令，却仍固定进入审批；命令前缀提取与授权消费按字符串规则分裂；`DiagnosticEvidenceRecord` 及解析函数没有接入 AgentLoop 的真实工具结算路径；系统查询只有计数没有通用停机条件；目录工具的部分测量协议不能覆盖直接子项元数据失败；提示词虽然要求谨慎，最终回答仍能输出无证据的泛化建议。

## 目标与非目标

**目标:**

- 让同一个标准化操作描述同时驱动执行前授权、执行后 effect 和后续授权命中，避免不同阶段各自猜测。
- 将 Plan 定义为无副作用模式，对静态可证明安全的只读操作直接放行，对未知、敏感或写入操作保持审批或拒绝。
- 将对象级证据作为诊断状态的唯一事实源，并让错误、部分结果和完整测量按目标并存。
- 使用证据增益与实际成本约束所有诊断工具，而不是只限制某个工具名或某类任务。
- 让批量工具稳定返回部分成功信息，并让最终回答的每个强结论能够追溯到相应证据。
- 通过基础提示词和动态 reminder 引导模型聚焦、具体和可执行，禁止重复常识、堆砌候选或用泛泛建议替代未知项。

**非目标:**

- 不为 `dir`、C 盘、Windows 清理或任何单一测试样例增加生产特判。
- 不开放复合 Shell、重定向、命令替换或脚本块进入 Plan。
- 不把 Shell 扩展成通用文件分析入口；结构化内置工具仍是首选。
- 不新增与 `SafetyOperation`、`ApprovalEffect` 或 `DiagnosticEvidenceRecord` 平行的领域模型。
- 不在本 change 中引入 Workflow、固定诊断步骤图或面向具体领域的清理知识库。

## 架构决策

### 1. 以标准化操作语义驱动 Plan 判定

在工具策略边界增加可验证的副作用分类：`read`、`write`、`unknown`、`sensitive-read`、`hardline`。内置工具通过自身元数据和参数解析产出可信分类；终端命令必须先完成 shell family 解析、解包和参数结构校验，只有被证明为原子只读的命令才能得到 `read`。

Plan 对 `read` 直接 `pass`，对 `write` 和 `unknown` 拒绝，对 `sensitive-read` 进入受限审批，对 `hardline` 直接拒绝。这样审批不再替代静态安全边界。

替代方案是继续维护“Plan 可审批命令列表”。该方案会让无副作用操作产生重复审批，并且无法解释审批持久化后为何仍重复询问，因此不采用。

### 2. 审批 UI 只展示可提交且可消费的效果

`ApprovalPolicy` 根据标准化资源和当前模式生成 choices。每个 choice 在展示前必须同时满足：能够映射为授权效果、能够在安全检查链中被消费、作用域与资源类型匹配。命令授权不再依赖任意文本的前两段猜测；只有参数解析器能形成稳定操作族时才允许 `session` 或 `persistent`，否则只允许 `call/deny`。

所有适用模式使用同一授权优先级链。模式可以禁止某类效果，但不能展示随后永远不会生效的选项。

### 3. 对象级证据账本成为唯一诊断事实源

AgentLoop 在每个工具结算点调用注册的结果解释器，将结果规范化为 `DiagnosticEvidenceRecord[]`。状态不再以单一 `evidenceLevel` 作为事实源；回合级摘要只从当前记录派生，用于展示和快速决策。

错误记录绑定具体目标和指标。一个目标失败不会抹掉其他目标的有效测量；同一目标的新完整测量可以替换旧的部分记录，但保留错误审计信息。无法解析的自由文本只产生 presence 或 error，不得通过“大数字正则”自动升级整个任务。

### 4. 以证据增益和成本驱动通用收敛

诊断状态为每次调用记录目标集合变化、指标新增、完整性提升、耗时、扫描条目、输出体积和失败类型。预执行守卫根据剩余预算和连续低增益次数决定允许、要求缩窄或阻止。

`systemQueryAttempts` 保留为观测指标，但不单独决定停机。结构化工具和 Shell 查询使用同一成本模型；原子 Shell 只有在目标信息无法由已注册只读工具提供时才能补位。

### 5. 使用统一的部分成功结果包络

批量枚举、扫描和读取工具返回统一字段：成功对象、失败对象、跳过对象、截断/取消原因、覆盖范围和完整性。单个子项权限失败不得抛弃其他成功结果；根目标不可读、参数契约无效或执行无法开始时才整体失败。

工具参数应在 schema 中表达条件依赖，不能表达时由工具提供安全默认值或在执行前返回明确的参数校验错误，避免被无关的子项错误遮蔽。

### 6. 最终回答使用“主张—证据”质量门禁

在诊断类最终回答提交前，对结构化主张执行校验。量化值、估算、完成度、主要原因和风险结论必须能匹配目标、指标和覆盖范围；无法匹配的内容必须删除或改写为未知项/待验证项。partial 和 lower-bound 必须自动携带不确定性表达。

第一阶段采用确定性规则校验高风险主张和量化声明，不依赖再调用一次模型进行自评，避免引入新的幻觉与延迟。

### 7. 提示词要求具体，但不承担最终安全责任

基础提示词增加通用输出纪律：先回答当前问题，只陈述有依据的发现，给出下一步动作和判定条件；禁止复述常识、列出没有筛选依据的长候选清单、用“建议优化/注意风险”等空泛措辞代替具体未知项。

动态 reminder 只注入当前相关证据摘要、未覆盖目标、预算、停滞原因和允许的下一步，不注入冗长历史。提示词用于引导模型，质量门禁用于保证底线，两者职责分离。

## 风险与权衡

- **[只读误判可能导致静默泄露宿主信息]** -> 敏感路径和凭据读取独立分类为 `sensitive-read`；终端只读分类必须同时验证命令、参数和 shell 结构，未知操作不得按 read 处理。
- **[操作族授权过宽]** -> 只有可信解析器可以生成可持久化资源，并在 ApprovalPolicy 中交叉校验；不稳定命令只能单次授权。
- **[证据解释器覆盖不足]** -> 未注册解释器时保守产生 presence/error，不允许自由文本数字自动提升；逐步为高价值内置工具补齐解释器。
- **[最终回答门禁误伤正常建议]** -> 仅对量化、完成度、主要原因、风险和执行性结论强制绑定证据；明确标注为一般背景且与当前结论分离的内容允许保留，但提示词要求最小化。
- **[统一部分成功包络增加工具返回体积]** -> 失败与跳过项按类别聚合并设置样本上限，完整明细可卸载到 tool-output 文件。
- **[一个 change 涉及多个能力]** -> 以单一闭环数据流为边界，任务按授权、证据、工具、提示词和集成验收分阶段，禁止顺带重构无关模块。

## 迁移计划

1. 先补齐标准化副作用分类与审批效果消费测试，调整 Plan 只读策略。
2. 将现有证据解析函数接入 AgentLoop，移除单一等级的写入式更新路径。
3. 引入通用成本/增益状态和部分成功结果包络，迁移 `listFiles` 作为首个实现。
4. 更新基础提示词、动态 reminder 和最终回答质量门禁。
5. 使用磁盘诊断、日志排查、代码分析三类回归夹具验证，不接受仅单场景通过。

回滚时可分别关闭最终回答门禁和增益守卫，但不得恢复“审批通过即视为安全”或丢弃对象级证据。Plan 行为变更如需回滚，必须整体恢复对应规格与测试，不能只恢复 UI 弹窗。

## 开放问题

- 命令操作族是否在本 change 中先使用现有 `command-prefix` 的受限增强形式，还是直接扩展为包含 shell family、根命令和允许参数模式的结构化资源；推荐后者，但实现前需核对持久化配置迁移成本。
- 最终回答质量门禁的失败应自动要求模型重写一次，还是直接把违规主张降级并返回；推荐先确定性降级，避免额外模型循环。

## 后续方向

### WorkMode 拆分：TaskPhase 与 ApprovalPolicy

当前单一 `WorkMode` 枚举（`Plan | Safe | Auto | YOLO`）将任务阶段与审批策略两个正交维度混在一起。长期建议拆分为：

- **TaskPhase**: `execute | plan` — 模型主动感知，通过提示词暴露行为约束
- **ApprovalPolicy**: `safe | auto | bypass` — 控制平面，不暴露给模型

本 change 已向此方向迈出了第一步：从发送给模型的上下文中移除了 `SecurityMode` 注入，改用行为约束（"本轮仅允许读取、分析和提出建议"）。后续独立的 change 可：
1. 新增 `TaskPhase` 维度，逐步迁移现有 Plan 工作流语义
2. 将 `ApprovalPolicy` 从 `WorkMode` 拆分，使其只影响运行时授权策略
3. 确保 `TaskPhase` 始终通过提示词约束暴露，不暴露内部枚举名

**注意**：本 change 不新增状态维度或迁移现有 `WorkMode`，上述拆分为后续方向。
