# 探索主题: 长期记忆双路混合检索与重排融合（Hybrid Search & RRF）

## 1. 问题定义
在当前的单路语义（向量）检索实现中，系统能够非常优秀地匹配概念相似的历史记忆事实。然而，在软件工程和智能体开发场景下，用户输入常常包含高精确度的类名、文件路径、API 标识符（例如 `LongTermMemoryPlugin`、`session.ts` 等）。向量检索往往由于嵌入维度的泛化而丢失这些精确的物理文本关键词，导致最直接的事实无法被精确检索召回。
为了解决这一痛点，我们需要探索一种物理文本关键字匹配（精确定位）与向量检索（模糊意图）相结合的“双路混合检索与重排融合”方案，以提升智能体在精准概念召回方面的稳定性。

## 2. 关键发现与调研结果
- **代码库现状**：
  - 核心接口 [VectorDbPort](file:///d:/Projects/MyAgent/src/ports/driven/VectorDbPort.ts) 目前仅提供单路的向量检索方法 `search(vector: number[], limit: number)`。
  - [LongTermMemoryPlugin](file:///d:/Projects/MyAgent/src/core/usecases/LongTermMemoryPlugin.ts) 插件在 `BeforeModel` 阶段只进行了向量检索召回，缺乏物理关键字的并行匹配。
  - 长期记忆持久化存储在物理文件 `.agent/MEMORY.md` 中，每一条事实都是以 `- **` 开头的要点行，非常便于在内存中切割进行文本匹配。
- **核实与洞察**：
  - 联网调研表明，针对向量检索与关键字匹配等不同尺度的多路召回，业界最稳定、无痛的融合算法是 **倒数排名融合（RRF - Reciprocal Rank Fusion）**。
  - RRF 通过对各路检索结果的位置排名倒数进行加权累加（公式：$Score(d) = \sum_{r} \frac{1}{k + rank(r, d)}$，常数 $k$ 业界推荐为 60），能够完全绕开向量距离（`[0, 1]`）与关键字匹配次数（无上限）等不同度量尺度之间的归一化难题，提供最稳定的零样本重排效果。

## 3. 方案对比与推荐方向

| 评估维度 | 方案 A：在插件层做双路检索与内存 RRF | 方案 B：在适配器层扩展双路检索接口 | 选型分析 |
| :--- | :--- | :--- | :--- |
| **接口侵入性** | **极低 ✓**：无需修改 `VectorDbPort` 接口定义，不影响外部其他使用者。 | **高 ✗**：需要扩展并重构 `VectorDbPort` 接口签名和全部适配器类。 | 方案 A 更加解耦。 |
| **关键字路灵活度**| **高 ✓**：可以直接读取最新的物理内存事实块并进行灵活分词或正则，无需频繁同步向量数据库表结构。 | **低 ✗**：所有的文本搜索和过滤必须在向量数据库中做表属性关联。 | 方案 A 对开发临时文件匹配非常契合。 |
| **计算与内存开销**| **中**：需要在内存中对 `.agent/MEMORY.md` 的行切片做 `includes` 正则过滤，当记忆超过万条时略有开销。 | **低 ✓**：全部过滤托管给 LanceDB 表底层处理，性能好。 | 在万条以内小文件场景下二者性能无差异，方案 B 在海量数据下有优势。 |

**推荐路径**：
首选 **方案 A（插件层 RRF 融合重排）**。
在当前项目体量下，智能体的长期记忆（`.agent/MEMORY.md`）通常控制在百条以内，在插件层内存读取文件并进行 `includes` 或正则表达式过滤拥有极高的灵活性，并且完全不影响驱动端口（Driven Ports）设计。
具体动作路径：
1. **向量路**：计算 Query 向量，从向量数据库检索出 Top-N 的匹配列表。
2. **关键字路**：对 Query 文本利用正则提取关键标识符作为匹配字（具体优先级规则：被反引号包裹的文本 `` `标识符` `` -> 大写字母开头的驼峰标识词 -> 常见技术文件名模式如 `.ts` 或 `.md` ），排除无意义的自然语言虚词。直接遍历物理文件切片，使用 `includes` 计算每个片段匹配到的关键字个数并降序排列。
3. **RRF 融合**：使用 RRF 算法（常量 $k=60$）合并两路结果，取最终 Score 最高的前 5 个片段。

## 4. 约束、风险与未知项
- **关键字路的提取精准度**：必须通过正则表达式硬编码落实如下三种高优模式的级联捕获，避免引入中英文自然语言噪音：
  1. 反引号捕获：``/`([^`]+)`/g``（如 `` `AgentLoop` ``，代表最高匹配权重）
  2. 驼峰标识捕获：`/\b[A-Z][a-zA-Z0-9]{3,}\b/g`（如 `SessionManager`，匹配字数在 4 字符及以上的类名/方法名）
  3. 物理文件名捕获：`/\b[a-zA-Z0-9_-]+\.(?:ts|js|json|md|py|go|java)\b/g`（如 `session.ts`，匹配常见技术文件后缀）
- **同步时效性**：方案 A 依赖直接读取 `.agent/MEMORY.md` 做关键字匹配，这也要求物理文件和向量数据库表的内容保持强同步，否则会导致两个召回结果对不上。

## 5. 否决方案
- **基于相似度分数线性相加（Linear Combination）的融合方案**：由于关键字匹配的分数（如命中词数 1, 2, 3）和向量余弦相似度分数（`[0.5, 1]`）的尺度完全不一致，物理意义不兼容。强行使用线性加权（如 $0.7 \times \text{similarity} + 0.3 \times \text{keyword\_hits}$）极易导致阈值失准而彻底失效，故予以否决。
