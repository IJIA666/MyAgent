# 探索主题: 超过 300 行的核心模块评估与治理方案

## 1. 问题定义
目前项目中虽然经过了 `internal-refactor-v1` 的大幅度解耦，但依然残留了少部分体积超过 300 行的代码文件（主要是 `session.ts`, `cli.ts`, `command.ts`, `context.ts`）。我们需要评估这些大文件是否存在“上帝类”的坏味道，并探讨下一步的治理方案。

## 2. 关键发现与调研结果
- **代码库现状**：
  经扫描，当前体积最大的几个文件分别是：
  1. `src/brain/session.ts` (423 行)：刚完成领域服务剥离，虽然代码缩减了约 40%，但内部的 `chat()` 方法依然庞大。这是由于 ReAct 死循环的状态机（解析流、拦截错误、调用工具、计算 Token 等）逻辑天然呈现极高的内聚性，强行拆分反而会割裂推理的完整逻辑闭环。
  2. `src/interface/cli.ts` (377 行)：包含了基于 Node.js `readline` 的交互式终端处理、终端色彩渲染以及多路异步流拦截等核心职责。
  3. `src/interface/command.ts` (375 行)：目前承载了所有 `/` 开头的内置命令的硬编码执行分发逻辑（如 `/model`, `/mcp`, `/help` 等的解析与处理）。这是一个典型的“上帝路由器”的坏味道。
  4. `src/brain/context.ts` (353 行)：`SessionContext` 类不仅囊括了核心的历史对话维护，还揉合了复杂的 Token 预算估算逻辑以及实体落盘序列化。

- **核实与洞察**：
  代码的维护成本不仅看“行数绝对值”，更要看“职责纯粹度”。`session.ts` 的 `chat` 方法的高圈复杂度来源于大模型调用的核心时序状态流转，属于“必要的复杂性”。反观 `command.ts`，其呈现的则是“发散式修改”的反模式——未来每增加一个系统级 Slash 命令，都要来修改这个巨无霸函数。

## 3. 方案对比与推荐方向

| 评估维度 | 方案 A: 严格按行数盲目强行拆分 | 方案 B: 基于职责与坏味道驱动拆分 (推荐) | 结论 |
| :--- | :--- | :--- | :--- |
| **核心指导原则** | 唯代码行数论（一刀切要求所有文件 < 300 行） | 遵循单一职责（SRP）与开闭原则（OCP） | B 占优 |
| **重点拆分对象** | 强行切分 `session.ts` 高内聚的 `chat` 流水线 | 优先将 `command.ts` 改造为命令注册模式，将 `context.ts` 的周边方法剥离 | B 占优 |
| **代码可读性影响**| 将连续推理流打散成大量碎片函数，上下文穿透困难 | 消除意大利面条式的 switch-case 逻辑，模块更聚焦 | B 占优 |
| **长远扩展性** | 无实质性提升，甚至增加心智负担 | 重构 `command.ts` 后，新增指令实现“热拔插”，不改动主逻辑 | B 占优 |

**推荐路径**：
选择 **方案 B**。我们将有限的重构精力聚焦于解决真正的坏味道：
1. **重构 `command.ts`**：引入标准的“命令模式 (Command Pattern)”。将每个 slash command（如 `/model`, `/mcp` 等）拆分为独立的策略实现文件（存放于 `src/interface/commands/` 下），而 `command.ts` 仅保留基类接口抽象与自动注册分发枢纽。
2. **抽离 `context.ts` 的旁支逻辑**：剥离专门计算 Token 消耗的模型估算算法，将类似 `estimateSnapshotTokens` 的繁重方法抽出为独立的 `TokenEstimator`，让上下文模型回归为纯粹的数据充血模型。
3. **保持 `session.ts` 的现状**：它目前的 400 余行恰好容纳了项目中最重要的生命周期主干，不建议为了单纯压降行数而对其“开膛破肚”。

## 4. 约束、风险与未知项
- `cli.ts` 和 `command.ts` 是终端 UI 侧的命脉入口。在对它们进行动态注册分发拆分时，必须小心处理对 `SessionContext` 的上下文引用传递，以及保证命令执行时的 `async` 异步终端渲染不会导致后续输入光标撕裂。

## 5. 否决方案
- **按行数强行切块 `session.ts`**：被坚定否决。如果把 `chat` 内的工具解析、Token 检查、缓存击穿诊断拆成外部的零散片段，由于它们强依赖并频繁变动当前轮次的各种局部变量字典，必定会导致各种变量被当作参数四处透传（Parameter Creep），这属于典型的得不偿失。
