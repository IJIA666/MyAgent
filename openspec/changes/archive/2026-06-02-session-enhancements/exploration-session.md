# 探索主题: 会话历史管理 (Session Persistence)

## 1. 问题定义
当前框架的 `SessionManager` 将所有上下文（`messageHistory`）完全维护在内存中。应用重启后，之前的对话、分析进度和工具调用上下文全部丢失。用户需要实现会话的持久化与恢复，使得每次启动都能找回或延续之前的上下文。

## 2. 关键发现与调研结果
- **现有逻辑**：
  - `src/brain/session.ts` 内部仅有一个 `private messageHistory: ChatCompletionMessageParam[] = []`，在 `chat()` 中随着流式交互动态追加内容。
  - `src/index.ts` 在启动时始终创建全新的 `SessionManager` 实例，无 `sessionId` 概念。
  - 当前仅有 Tracer（交互追踪仪）会在 `.myagent/traces/` 下以 JSONL 格式单向追加记录流水，但该流水属于审计用途，未经过结构化设计，不适合用作状态反序列化恢复。

- **核心洞察**：
  - 恢复不仅是重载消息数组，还需要恢复工具的鉴权状态和 MCP 服务器连接。不过目前 MCP Server 的连接在 `initWorkspace` 阶段是全局重连的，所以重点仅在于无损恢复 `messageHistory` 状态。
  - 会话必须要有唯一标识（`sessionId`），并且需要确定是在应用退出时一次性落盘，还是在每个对话回合结束时（即流输出完毕后）实时落盘。后者更抗意外宕机。

## 3. 方案对比与推荐方向

针对“每次打开都可以回到之前记录”的触发机制，存在以下几种架构演进路线：

| 方案 | 优点 | 缺点 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **方案 A：工作区单例绑定** (Auto-Resume) | 启动时自动寻找该工作区下最新的一份会话文件直接反序列化。对用户最无感，真正实现“每次打开接着聊”。 | 想要强行开启全新上下文时，必须手动执行清除指令（如 `/clear` 或 `/new`）。 | 偏好长期伴随式、长周期沉浸开发的用户 |
| **方案 B：纯手动显式恢复** (Explicit Resume) | 保持启动永远是全新干净的会话。提供 `/history` 列表与 `/resume <id>` 供手动穿越。 | 如果意外退出，下次启动还要敲命令才能回去，略显繁琐。 | 偏好干净环境、将 Agent 视为一次性问答工具的用户 |
| **方案 C：混合启动策略** (CLI Flags) | 结合两者。默认启动全新的，但支持带参数 `myagent --resume` 启动。或在 `cli.ts` 启动时若发现遗留会话，给出提示 `(找到最近的会话，是否继续？[Y/n])`。 | 需要改动 CLI 启动流程参数解析，增加一点引导交互。 | 工业级通用 Agent 常见的做法（如 Claude Code） |

**探索决策达成**：用户明确选择了 **方案 B（纯手动显式恢复）**。这确保了 Agent 作为一个纯粹、无污染的计算与思考引擎，每次启动都具备确定性的干净初态。仅通过显式的 `/history` 查看和 `/resume <id>` 穿越来干预时间线。相关的持久化落盘机制将限定在 `.myagent/sessions/<sessionId>.json` 的静默序列化上。

## 4. 约束、风险与未知项
- **恢复时的状态撕裂**：如果上一次会话卡在正在生成中（执行工具流）宕机，直接反序列化可能会将中断的脏数据读入，需要在重载时执行一次健康度清理（例如裁切掉末尾未闭合的 Assistant 碎片）。
- **工具版本的兼容性**：如果上一次会话调用了某 MCP 工具，随后该工具签名被开发者修改，反序列化历史记录时强关联该历史可能在后续复用时出 bug（此风险目前较低，因为历史对象只是静态 Context）。

## 5. 否决方案
- **使用复杂的关系型数据库（如 SQLite）**：对于一个轻量级的纯本地工作区 Agent 而言过重。直接基于 `.myagent/sessions/` 目录下的 JSON 文件做反序列化完全足够，且便于用户自行通过编辑器查看和清理。
- **方案 A（无感续连）与 方案 C（混合询问）**：被正式否决。此类方案侵入了终端的初始态，违背了“保持启动永远干净”的架构审美和用户偏好，可能导致长期开发环境下的隐式状态错乱。
