# 探索主题: 磁盘清理场景驱动的 Agent 能力缺口分析

## 1. 问题定义

以"让 agent 帮助清理 Windows C 盘"为具体场景，反向检验 MyAgent 当前架构的综合能力。核心思路：agent 先规划（只读扫描 → 产出清理方案 → 用户审阅），用户批准后再执行。skill（磁盘清理的领域知识）不在本次讨论范围——焦点是 **agent 框架本身需要具备什么能力才能支撑这类复杂场景**。

## 2. 关键发现与调研结果

- **代码库现状**：
  - **Skill 系统**：已有成熟的 SKILL.md + frontmatter + load_skill 按需加载机制，载体形态是业界共识，无需重新设计
  - **Plan 模式**：当前仅做到物理裁剪 write 工具声明（`enablePlanToolStripping`），没有"产出可审阅方案 → 用户确认 → 切换模式执行"的两阶段协议。深层原因见 §3.2
  - **人机交互**：仅有审批系统的二元 yes/no（`ApprovalPort.waitApproval()`），没有结构化提问能力（"选 A/B/C"）
  - **SubAgent**：`MemoryService.runMemoryRefinementSubAgent()` 有一个原始实现（独立 SessionContext + 受限 ToolRegistry + 单工具），但无并行编排、无结构化通信、无结果聚合
  - **大输出处理**：`ToolDispatcher.handleLargeToolOutput()` 采用双向折叠策略——上下文窗口内截断（头尾保留、中间省略），但完整原始输出落盘到 `.myagent/tool-outputs/` 目录，数据不丢失。截断侧侧重的是上下文窗口的经济性，而非数据完整性
  - **安全审批**：`checkSafety()` 仅返回 pass/suspend/deny 三元状态，无风险分级
  - **插件系统**：6 个内置插件 + 洋葱管道 + Immer Draft 沙箱，架构成熟可扩展

- **核实与洞察**：
  - 磁盘清理场景暴露了 5 个能力缺口：AskUserQuestion、Plan 两阶段协议、SubAgent 编排、大目录分层摘要、风险分级审批
  - 其中 **AskUserQuestion + Plan 两阶段协议** 被判定为最高杠杆切入点——这是端到端用户体验的核心链路

## 3. 方案对比与推荐方向

### 3.1 AskUserQuestion 实现形态对比

| 评估维度 | A. 原生工具 (Native Tool) | B. 插件 (Plugin) | C. 系统级事件 (System Event) |
| :--- | :--- | :--- | :--- |
| 模型感知 | 强 — 模型主动调用，符合 tool-use 范式 | 弱 — 需要 prompt 约定标记格式，脆弱 | 中 — 模型如何触发该事件本身就是一个待解问题 |
| 改造范围 | 新增一个工具定义 + CLI 监听 | 新增一个 Plugin 注册 | 扩展 `AgentEvent` 枚举 + agent-loop 分支 + 触发机制 |
| 暂停/恢复机制 | 天然支持 — 工具调用时 agent-loop 挂起等待结果，与审批挂起模式同构 | 需要在 Hook 中手动阻塞 agent-loop，引入额外复杂度 | 需要新增事件处理分支，且事件与 ReAct 循环的衔接不自然 |
| 与现有基础设施的复用 | 高 — 审批系统的 suspend/wait 通道可直接复用为工具内部的交互等待 | 中 — 复用 Hook 机制，但 Hook 设计为横切关注点，不适合做核心交互原语 | 中 — 统一事件模型，但 AskUser 的本质是一次"带参数的同步等待"，事件模型的异步语义不匹配 |
| 动态选项生成 | 强 — 模型在调用参数中动态生成选项（title + options 数组） | 中 — 需要在标记中编码选项，解析脆弱 | 强 — 事件 payload 携带选项 |
| 可复用性 | 高 — 任何场景模型都能调用，与场景无关 | 中 — 依赖 prompt 约定，不同场景可能需要不同的标记格式 | 高 — 但需要模型理解何时触发事件 |

**推荐路径**：**方案 A（原生工具）**，理由如下：

1. **工具调用是 agent-loop 的天然暂停点，且挂起通道已打通**。经代码核实，完整调用链为：
   - `ToolRegistryPort.callTool(sessionContext: SessionEventPort & ApprovalPort)` — 端口契约层已注入
   - → `LocalFileSystemMcpServer.callTool()` — `virtual-mcp.ts:231` 已调用 `sessionContext.waitApproval()` 实现审批挂起
   - → `tool.execute(args, contextToPass, signal)` — `virtual-mcp.ts:252` 已将 `sessionContext` 传入工具
   - AskUserQuestion 工具的 `execute(args, sessionContext)` 方法内可直接调用 `sessionContext.waitApproval()` 挂起等待用户输入，无需新增任何通道，无需修改 agent-loop，纯增量开发。

2. **工具参数即是交互 schema**。模型通过 OpenAPI/JSON Schema 定义的工具参数来声明问题、预设选项、是否多选、是否开放自由输入（`allowFreeInput`），CLI 层按 schema 渲染交互界面——固定选项渲染为选择列表，自由输入渲染为文本输入框。这不是"另搞一套协议"，而是对 tool-use 范式的自然延伸。

3. **与 Plan 模式天然兼容**。AskUserQuestion 是只读交互（不产生副作用），即使在 Plan 模式下也不会被 write 裁剪过滤掉。agent 在规划阶段可以随时向用户提问澄清需求。

4. **B 和 C 被否决的原因**：B 把核心交互原语塞进了插件（横切关注点）——插件适合做"对已有行为的增强"，不适合做"引入全新交互模式"。C 的事件模型是异步通知（fire-and-forget），而 AskUser 是同步等待（ask-and-wait），语义不匹配；而且 C 没有回答"模型如何触发事件"——最终还是要落到工具调用或标记解析上，等于绕了一圈回到 A 或 B。

**~~约束条件~~**：~~该推荐的前提是确认 agent-loop 的 suspend 通道能被工具内部直接复用（而非仅限 BeforeTool 插件钩子）。如果存在架构限制，则需评估在工具 `execute()` 中走独立等待通道的代价。~~ **已核实，风险排除**：`ApprovalPort` 通过 `callTool → virtual-mcp → tool.execute(args, sessionContext)` 调用链已注入到工具的 `execute()` 方法（`virtual-mcp.ts:252`），且 `waitApproval()` 在 MCP 层已有成熟调用先例（`virtual-mcp.ts:231`）。

#### 3.1.1 工具 Schema 设计：必须支持自由文本输入

单纯的 `title + options[]` 模型存在一个实质性的功能缺口：**无法处理开放式问题**。

```
// 可以覆盖的场景：
ask_user(title="选择清理策略", options=["保守清理", "激进清理", "仅系统临时文件"])

// 无法覆盖的场景：
ask_user(title="你想优先清理哪些目录？")  // 无法穷举选项
ask_user(title="对这个方案有什么补充意见？")  // 本质上是开放问题
```

如果只有固定选项，AskUserQuestion 退化成一个投票/选择工具，而不是对话工具。真实的对话中，用户需要能输入超出预设选项范围的内容。

**Schema 设计方案**：

工具参数增加 `allowFreeInput: boolean`（默认 `false`）。当为 `true` 时，CLI 层在渲染选项列表后自动追加一个 "Other（自定义输入）" 选项，选中后切换为自由文本输入框。

```
// 工具参数 schema：
{
  title: string,              // 问题标题
  options?: string[],         // 预设选项列表（可选；为空或省略时，若 allowFreeInput 为 true，退化为纯文本输入框）
  multiSelect?: boolean,      // 是否允许多选，默认 false
  allowFreeInput?: boolean    // 是否允许用户输入自定义文本，默认 false。需模型显式声明，不自动追加
}

// 返回值统一为字符串（非索引）：
// - 选中预设选项时，返回选项文本
// - 用户输入自定义文本时，返回用户手写内容
// - 多选时，用约定分隔符拼接
// - 纯开放式问题（无 options）时，直接返回用户输入
```

**为什么返回值必须是字符串而非选项索引？** 因为模型在调用时已经知道选项内容（它就写在调用参数里），返回索引是冗余的，而且无法统一处理"选中预设选项"和"用户自定义输入"两种情况。统一返回字符串——模型不需要知道这来自选项列表还是自由输入，直接作为对话内容消费。

**设计决策**：
- ~~`allowFreeInput` 是否自动生效还是显式声明~~ **已拍板**：需模型显式声明，不自动追加 Other。理由：某些问题要求用户严格在预设选项中做枚举选择（如「选择清理级别：保守/激进」），自动追加 Other 会引入噪音。显式声明意味着模型有意识地决定「这道题需要开放输入」，语义更清晰
- 多选 + 自由输入的交互复杂度（用户选了几个预设选项后又输入自定义文本）——CLI 渲染需要专门设计，留到 propose 阶段解决

### 3.2 Plan 模式两阶段协议

当前 agent-loop 主循环结构（`agent-loop.ts`）：

```
while (iteration < maxIterations) {
  上下文组装 → LLM 推理 → 工具并发执行 → 检查 complete → continue
}
```

**为什么天然难以插入"规划完成后的等待点"？**

关键问题在于：**agent-loop 不知道什么是"规划完成"**。从循环视角看，规划阶段和执行阶段的差异仅仅是"这轮有没有调用 write 工具"——这是一个事后判断，不是事前状态。循环本身是无状态的迭代器，没有"当前处于 plan 阶段还是 exec 阶段"的概念。

当前循环中存在的控制点有四类：
| 控制点 | 机制 | 能否充当等待点 |
|:---|:---|:---|
| 工具执行中的审批挂起 | `suspend` 事件 + `ApprovalPort.wait()` | ✅ 可以，但仅在工具粒度，不在方案粒度 |
| 轮次间的自然间隙 | `continue` 前 | ❌ 无等待机制，直接进入下一轮 |
| `complete` 事件 | `return` 退出循环 | ❌ 退出即结束，无法恢复 |
| 插件 `restart` 信号 | 回退 `iteration` 计数器重试 | ❌ 是回退重试，不是挂起等待 |

**核心矛盾：惯例 vs 协议**

在讨论具体路径之前，必须正视一个根本性矛盾：

- "两阶段协议"的价值在于**强制性保证**——用户一定看到了方案，执行前一定有确认
- 用户明确否决了"固化流程"——不希望框架层硬编码交互步骤
- 任何依赖模型自觉调用的机制（约定）都不提供强制保证——模型可以跳过它

**Plan 模式已经在物理层提供了保证**：write 工具被裁剪后，agent **物理上无法执行写操作**。这不是 prompt 层的惯例，是工具列表层的硬约束。因此"规划→审阅→执行"中的"规划"和"执行"已经是天然隔离的——唯一需要设计的只是在两者之间有一个诚实的过渡机制。

**可行路径分析**：

- **路径 1（零代码改动，推荐）**：利用现有的 WorkMode 切换。用户在 Plan 模式下看到 agent 输出的规划，手动切换到 Auto 模式，输入"执行上述方案"。agent-loop 完全不需要感知"两阶段"——这是工作流层面的用户行为。**这是诚实的方案**：它承认"审批权在用户手里"这一事实，不试图用具调用伪装成授权行为。

- **路径 2（`submit_plan` 工具）**：被否决，理由见 §5。

- **路径 3（agent-loop 阶段状态机）**：被否决，理由见 §5。

**推荐**：**路径 1**。当前架构已经提供了 Plan 模式的物理隔离（write 工具裁剪），手动 WorkMode 切换是唯一诚实的过渡方式。后续如果需要更流畅的体验，方向不是用具调用模拟协议，而是在 CLI 层优化 WorkMode 切换的交互（如快捷键切换 + 预设的"执行上述方案"指令），保持用户作为授权主体的地位。

## 4. 约束、风险与未知项

- **SubAgent 的具体方案尚未设计**，用户计划在后续针对性调研
- 磁盘清理的领域知识（skill 内容）不在本次探索范围，但 skill 的**知识密度与形态适配**（过程性 vs 判断性知识）可能在未来成为独立话题
- ~~AskUserQuestion 工具内部复用审批挂起通道的可行性~~ **已核实**：`ApprovalPort` 通过 `callTool → virtual-mcp → tool.execute(args, sessionContext)` 调用链已注入到工具的 `execute()` 方法（`virtual-mcp.ts:252`），且 `waitApproval()` 在 MCP 层已有成熟调用先例（`virtual-mcp.ts:231`）。风险排除
- **AskUserQuestion 的 CLI 渲染需与审批弹框区分**：两者共用底层挂起通道（`waitApproval()`），但语义不同——审批是"拦截风险"，提问是"正常交互"。propose 阶段必须专门设计 CLI 侧的差异化渲染（标题、选项样式、交互方式），不能默认复用安全审批的展示逻辑，否则用户会看到所有问题都以"是否放行此操作？"的口吻呈现

## 5. 否决方案

- **固化流程（扫描→分析→规划→审批→执行）**：用户明确表示主流 agent 应保持灵活性，不应将交互流程硬编码。agent 应自主决策何时扫描、何时提问、何时执行
- **插件形态的 AskUserQuestion**：插件适合横切关注点（日志、熔断、规则注入），不是核心交互原语的合适载体。把 AskUser 塞进插件等于把"提问"当成副作用处理，语义不对
- **系统事件形态的 AskUserQuestion**：事件模型是异步通知，AskUser 是同步等待，语义冲突。且没有回答"模型如何触发"这个前置问题
- **`submit_plan` 工具（Plan 路径 2）**：两个致命缺陷。(1) 冗余性：如果 AskUserQuestion 已存在，模型可以用 `ask_user` 表达"批准/拒绝"，`submit_plan` 不提供额外能力。(2) 核心矛盾：它试图用工具调用惯例来模拟两阶段协议的强制性保证——模型完全可以不调用此工具就切换执行，这不是协议，只是 prompt 约定的惯例。惯例不提供保证，协议才提供。而强制协议（框架层阶段状态机）已被用户否决。因此不存在"软性但可靠"的中间地带——要么承认审批权在用户手里（路径 1），要么在框架层强制执行（路径 3），不存在第三条路
- **agent-loop 阶段状态机（Plan 路径 3）**：在循环中硬编码 `phase: 'plan' | 'exec'` 状态切换，违背用户"不要固化流程"的明确要求，且增加 agent-loop 复杂度。用户行为模式灵活多变（可能先执行一部分再规划、可能边执行边调整），状态机无法穷举所有模式
