## 改造原因

当前 MyAgent 的人机交互能力仅限于审批系统的二元 yes/no 决策——模型执行写操作时弹出安全审批，用户只能选择"放行"或"拒绝"。这缺失了一种关键的交互原语：**agent 在推理过程中主动向用户提出结构化问题并等待回答**。

真实场景（如磁盘清理规划）中，agent 需要向用户提问：
- "你想优先清理哪些目录？"（开放式）
- "选择清理策略：保守 / 激进 / 仅系统临时文件"（选项式）
- "对这个方案有什么补充意见？"（自由输入）

缺乏这一原语迫使所有交互退化为"用户必须在输入框中预先把所有信息说完"，agent 无法主动澄清模糊意图或征求意见。这是 agent 从"单次指令执行器"进化为"协作式助手"的关键能力缺口。

## 变更内容

- **新增 `ask_user_question` 原生工具**：模型在推理过程中调用，声明问题、选项、是否多选、是否开放自由输入。工具 `execute()` 通过新建的 `InteractionPort` 挂起等待用户输入，返回用户选择/输入的字符串
- **新增 CLI 交互渲染层**：实现 `InteractionPort`，监听 `ask_user_question` 工具调用，在终端渲染差异化的交互界面（与审批弹框区分）。固定选项渲染为选择列表，自由输入渲染为文本输入框，多选 + 自由输入混合模式需专门设计
- Plan 模式两阶段协议**不涉及代码改动**：依赖现有 WorkMode 切换的零代码方案（用户手动从 Plan 切到 Auto 再输入"执行"）

## 业务能力

### 新增业务能力
- `ask-user-question`: agent 在推理过程中通过原生工具调用的方式向用户发起结构化提问（选项选择、自由文本输入、混合模式），CLI 层渲染交互界面并返回用户回答。这是 agent 从被动执行者升级为协作式助手的关键交互原语

## 影响范围

- **新增文件**：`src/adapters/tools/impl/interaction/` 下的工具定义与实现
- **CLI 层**：`src/adapters/input/interface/cli.ts` 或 `facade.ts` 需新增交互渲染逻辑，与审批弹框共用底层挂起通道但使用独立的展示样式
- **虚拟 MCP 服务器**：`src/adapters/tools/virtual-mcp.ts` 注册新工具实例，工具声明通过 `getTools()` 动态注入模型的 function calling 列表，无需修改 prompts.ts
- **无破坏性变更**：纯增量开发，不修改 agent-loop 核心逻辑，不修改现有工具和插件
