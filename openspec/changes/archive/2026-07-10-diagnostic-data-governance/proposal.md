## 改造原因

当前项目会在本地持久化结构化运行日志、会话 trace 和插件 audit。trace 默认包含 system prompt、对话上下文、reasoning、工具参数与结果，audit 默认包含工具调用载荷和上下文补丁；而 Agent 能够接触密钥、配置、邮件和用户文档，使 `.myagent` 成为一份高敏感的二次数据仓库。现有日志轮转只限制 `run.log` 的单文件规模和备份数量，没有统一的数据分级、写盘前脱敏或 trace/audit 保留上限。

本次需要在运维诊断、授权审计、故障回放和敏感数据最小化之间建立明确契约。现在处理是因为写盘边界已经稳定，继续扩大原始内容采集会增加泄露面；应先定义默认安全边界，再保留由用户明确开启的短期完整回放能力。

## 变更内容

- 新增诊断数据分级契约：运维诊断默认记录稳定事件和关联元数据，审计默认记录策略结果与摘要，完整会话回放必须显式开启。
- 在 `run.log`、trace、audit 各自的写盘边界执行统一的字段感知脱敏，并以模式匹配作为兜底；脱敏发生在首次落盘前。
- 为 trace 和 audit 提供独立、保守且可配置的保留上限，避免会话诊断文件无限增长；不引入新的生命周期清理框架或集中式遥测后端。
- 保持已有 trace 读取/回放能力对历史格式的兼容；新写入的默认 trace 不再承诺包含完整 prompt、reasoning、工具参数和结果。
- 明确 session snapshot 是恢复状态而非诊断制品，本次不改变其完整消息保存、加载和恢复语义；如未来需要治理 snapshot，应单独立项。
- **BREAKING**：默认 trace 从完整内容记录改为受控内容记录，依赖默认完整 trace 内容的本地调试流程必须显式启用 replay 模式。

## 业务能力

### 新增业务能力

- `diagnostic-data-governance`: 提供诊断制品分级、写盘前敏感字段脱敏、采集开关和保留策略。

### 修改业务能力

- `trace-logging`: 修改默认 trace 内容采集和回放策略，完整内容改为显式开启。
- `unified-logger`: 修改日志写盘契约，增加统一的安全数据治理和脱敏要求。

## 影响范围

- 影响运行日志、会话 trace 和插件 audit 的数据模型、序列化边界、配置和读取行为。
- 影响 Agent 运行期间的诊断文件内容，以及用户查看和回放 trace 的操作方式；不改变模型调用、工具执行、上下文恢复或审批决策语义。
- 预计涉及 logger、tracer、trace format/reader、审计插件、配置文档和相关测试；需要补充默认安全模式、显式 replay、秘密字段、嵌套载荷、换行清洗和保留清理的契约测试。
- 不涉及 `session-persistence` 的恢复快照治理，不涉及异步日志管道重写，不涉及集中式遥测或数据库引入。
