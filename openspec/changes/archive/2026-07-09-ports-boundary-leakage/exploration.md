# 探索主题: Ports 边界泄漏与抽象收口

## 1. 问题定义
当前仓库已经采用 `core / ports / adapters` 的分层骨架，但 `ports` 目录中的若干接口仍直接依赖 `core` 的具体类型，导致“端口层应当只表达契约”的原则被破坏。结果是输入适配器、测试驱动和未来的替代实现都被当前核心实现细节绑死，耦合度高于表面分层所呈现的程度。

## 2. 关键发现与调研结果
- **代码库现状**：`src/ports/driving/ChatUseCase.ts` 直接导入 `ApprovalService` 与 `AgentEvent`，意味着驱动端口不是纯接口，而是暴露了核心实现的具体服务与事件类型。
- **代码库现状**：CLI 门面 `src/adapters/input/interface/facade.ts` 直接依赖 `SessionManager`，而不是只依赖 `ChatUseCase` 这类输入端口契约，导致 UI 层能看到过多核心细节。
- **代码库现状**：`src/ports/driven/tools/ToolAccessMetadataPort.ts`、`src/ports/driven/tools/AgentPlugin.ts` 也在引用 `core` 里的安全与插件类型，说明端口层正在成为“核心类型的转运层”，而不是稳定抽象层。
- **核实与洞察**：目前不存在明显的 `core -> adapters` 反向依赖硬伤，说明大方向是对的；真正的问题是 `ports` 的抽象纯度不够，导致替换成本并没有因为分层而真正下降。

## 3. 方案对比与推荐方向
| 评估维度 | 方案 A：接受当前“半抽象端口”现状 | 方案 B：收口为纯契约与纯数据结构 | 结论 |
| :--- | :--- | :--- | :--- |
| 短期改动成本 | 低 | 中 | A 占优 |
| 长期可替换性 | 弱 | 强 | B 占优 |
| 测试友好性 | 中，Mock 仍受具体类型牵制 | 强，适合构造轻量桩实现 | B 占优 |
| 认知清晰度 | 弱，分层名义大于实际 | 强，边界更真实 | B 占优 |
| 迁移风险 | 低 | 中 | A 略优 |

**推荐路径**：采用方案 B，但要分两步做。第一步先把 `ChatUseCase` 上暴露的 `ApprovalService`、`AgentEvent` 换成端口层自有契约或纯数据结构；第二步再把 CLI 对 `SessionManager` 的直接依赖收敛到输入端口。这样能先修复最明显的边界泄漏，而不会一次性大面积重写核心实现。

## 4. 约束、风险与未知项
- 当前 CLI 的审批恢复、挂起交互和渲染节奏与 `SessionManager` 的具体行为绑定较深，直接替换为纯端口可能需要补充新的驱动契约。
- 插件与安全类型到底应归属 `core` 还是 `ports`，需要统一原则；否则只会从一个目录搬到另一个目录，问题本质不变。
- 如果未来确认插件就是核心域模型的一部分，那么端口层至少也应只引用稳定 DTO，而不应暴露完整核心服务对象。

## 5. 否决方案
- **维持现状，仅依靠命名说明这是“逻辑端口”**：这会掩盖真实耦合，后续替换适配器时仍会撞到同样的问题。
- **先改所有 ports 再回头整理调用方**：动作过大，不利于逐步验证，容易形成一轮高风险抽象重写。
