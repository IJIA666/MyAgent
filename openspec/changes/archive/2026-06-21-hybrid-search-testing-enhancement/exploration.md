# 探索主题: 长期记忆双路混合检索与 RRF 重排的测试增强策略

## 1. 问题定义
目前已完成长期记忆双路检索（向量路 + 物理关键字匹配路）与 RRF 重排算法的全部核心开发。本探索旨在评估现有单元与集成测试的覆盖面、识别潜在的死角、并为实际人工/交互式测试设计严谨的用例，确保混合检索在各种极端及复杂环境下的可靠度。

## 2. 关键发现与调研结果
- **代码库现状与覆盖率分析**：
  根据 Vitest 覆盖率收集结果，`LongTermMemoryPlugin.ts` 的语句覆盖率为 **92.03%**，分支覆盖率为 **83.72%**，表现优异。
  未覆盖的行级区间（Uncovered Line #s）主要聚焦于以下防御性或偶发的分支：
  - **单路容错异常捕获**：`vectorDb.search` 抛错捕获块（第 85-87 行）与 `searchMemoryByKeywords` 抛错捕获块（第 92-94 行），目前测试套件未对数据库离线或文件读取崩溃做抛错模拟。
  - **JIT 兜底注入分支**：在无 system prompt 时 unshift 一个 system 消息的逻辑，在新测试中大多命中了已有 system message 的追加逻辑，没有充分测试 unshift 边界。
  - **自省失败捕获**：当自省回调函数 `onSessionEndCallback` 执行出错时的 Catch 块（第 268 行），属于静默保护逻辑。

- **核实与洞察**：
  - 双路 RAG 系统的主要痛点在于：若单路数据库连接超时，整路挂起会导致智能体推理严重变慢，甚至抛出未捕获异常致使主循环中断。我们在第四阶段代码设计中，通过并行 `Promise` 加独立 `try-catch` 容错对两路进行了物理隔离，这是十分正确的做法。

## 3. 方案对比与推荐方向
为进一步加强此功能的质量保障，我们对比以下三种增强测试方案：

| 评估维度 | 方案 A (仅靠现有单元/集成测试) | 方案 B (补全异常分支 + 防御用例) | 方案 C (实机 REPL 交互手测用例) | 结论 |
| :--- | :--- | :--- | :--- | :--- |
| **覆盖死角** | 无法验证单路报错下的系统健壮性 ✗ | 能 100% 覆盖容错异常逻辑 ✓ | 无法自动化拦截代码回退 ✗ | B 占优（覆盖边界） |
| **真实度** | 依靠虚拟 Mock 驱动 ✗ | 依靠虚拟 Mock 驱动 ✗ | 使用真实向量库及大模型进行链路拉通 ✓ | C 占优（验证综合效果） |
| **维护成本** | 低 ✓ | 中（需维护 Mock 报错） ✗ | 高（手测） ✗ | A/B 占优 |

**推荐路径**：
我们将结合 **方案 B** 和 **方案 C**。
1. **自动测试方面 (方案 B)**：补全对向量检索抛错（模拟网络断开）的单路容错单元测试，验证此时物理路是否依然能独立工作；
2. **实手测方面 (方案 C)**：提供一份标准的竞争召回测试用例，让您可以在命令行交互（REPL）中实机检验向量与物理重排去重的效果。

## 4. 约束、风险与未知项
- **I/O 锁竞争**：在实机 REPL 中，如果自省子智能体正在往 `MEMORY.md` 写入事实，而主智能体同时在 BeforeModel 钩子中试图通过 `fs.promises.readFile` 读取该文件，可能会发生短暂的 I/O 竞争或锁占用。我们在插件内使用独立的 `try-catch` 进行容错是必不可少的。

## 5. 交互式实机（REPL）手测方案

为在交互式 REPL 终端中直观验证混合检索、RRF 重排与容错效果，设计如下严谨用例：

### A. 环境与测试数据准备
1. **物理 facts 准备**：在 `.agent/MEMORY.md` 物理事实文件中，手动追加以下两条特定格式事实：
   - `- **SessionManager**：这是会话管理的控制中枢，它负责插件的生命周期和洋葱模型的构建。`
   - `- **TypeScript**：这是项目的核心开发语言，所有的插件和驱动都必须使用 TypeScript 编写。`
2. **向量事实准备**：通过对话自省提炼或向量库注入，准备一条具有“状态管理”语义、但**不包含** `SessionManager` 或 `TypeScript` 字面关键词的事实，例如：
   - `- **状态管理规范**：在智能体框架里，上下文修改是通过 Immer Proxy 来保证并发写入时的安全忙锁。`

### B. 测试执行步骤
1. **启动应用**：进入 REPL 会话命令行交互环境。
2. **输入测试 Query**：
   > `请问 SessionManager 在状态管理上是怎么运行的，这个项目用什么语言写？`

### C. 预期校验结果
1. **关键词正则提取路**：系统自动捕获大写驼峰标识词 `SessionManager`，匹配并**成功召回** `- **SessionManager**` 物理事实。（由于 Query 中不包含 TypeScript 字面词，该词未被正则提取为关键词，因此 TypeScript 事实零匹配，关键字路不召回该条）。
2. **向量语义检索路**：系统将 Query 转化为 embedding 后，由于 Query 包含“状态管理”语义，**成功召回**相关向量事实。
3. **RRF 融合与重排**：两路结果无偏融合，过滤无用元素并保留 Top-5 事实注入大模型 System Prompt 尾部的 `<long-term-memory>` 块。
4. **终端最终回答**：大模型应答必须包含 **SessionManager 负责插件生命周期** 以及 **使用 Immer Proxy 并发忙锁进行状态管理** 这两个核心召回要素。

### D. 单路故障容错模拟
1. 手动修改或阻断向量数据库的初始化/网络连接，使其在执行 `vectorDb.search` 时抛出错误。
2. 再次发送上述提问。
3. **预期表现**：控制台在后台静默报错（有 error 日志），但 REPL **完全没有中断**，物理关键字路继续成功召回 `SessionManager` 事实，大模型能结合该事实正确进行答复。

## 6. 否决方案
- **全量无 Mock 自动集成测试**：在自动化 CI 中使用真实的 OpenAI/LanceDB 物理进行双路召回集成测试。
  - *否决原因*：API Key 消耗大、测试执行速度极慢、容易因为外部网络波动导致 CI 流水线随机失败，背离了单元测试快速高可用的设计初衷。
