# 探索主题: 时间旅行回退机制 (Time-Travel Rollback)

## 1. 问题定义
在 Agent 与用户的交互循环中，当大模型推理跑偏、陷入死循环、或者误解了用户意图并开始盲目调用工具时，系统需要一种安全网来“喊停”并“撤销”这些错误状态，从而引导 Agent 重回正轨。这种“回退机制”是打造工业级高可用 AI 助手的核心防线。

## 2. 关键发现与调研结果
- **概念拆解**：“回退”在架构上必须被严格拆分为两层：
  - **A. 会话/上下文回退 (Context Rollback)**：清理模型脑子里的记忆残局。
  - **B. 物理操作副作用回退 (Side-effect Rollback)**：清理模型对物理世界（如本地文件、数据库）造成的实际破坏。
- **开源标杆调研**：通过深度拆解当前主流顶级 Agent 源码（Claude Code、OpenClaw 等），得出重要工业共识——**所有高完成度的纯 Agent 框架，全都仅实现了 A（记忆截断/打断），彻底舍弃了 B（物理回滚）**。
- **Claude Code 错觉剖析**：破除了“Claude Code 双击 ESC 能撤销操作”的错觉。源码（`inProcessRunner.ts`）证实，`ESC` 的本质仅触发 `AbortController` 截断当前流式输出，并向 LLM 上下文强塞中断信号，它对已经写入底层的文件损坏无能为力。
- **全网最新前沿研究印证**：经过全网检索（2024-2025 年学术界与工程界共识），强行做物理快照回滚会引发严重的 **“语义回滚攻击 (Semantic Rollback Attacks)”** 与 **“静默状态损坏 (Silent State Corruption)”**。例如：Agent 回滚后丢失了记忆，重新执行可能会导致重复发邮件、重复转账等灾难性后果。业界前沿的做法是放弃硬回滚，转而引入**工具标签（可逆/不可逆/幂等）**与**业务层事务补偿（Compensating Transaction）**机制。

## 3. 方案对比与推荐方向
| 方案 | 优点 | 缺点 | 结论 |
| :--- | :--- | :--- | :--- |
| **A. 上下文记忆截断 (Context Truncate)** | 实现轻量，架构低耦合；通过对 `messageHistory` 数组弹栈（pop）即可丢弃发散轮次。 | 无法还原已经被错误工具修改的物理环境，防爆破能力弱。 | **强烈推荐 (业界标配)** |
| **B. 物理事务补偿回滚 (Saga / 快照)** | 极致的“后悔药”体验。 | MCP 工具生态是黑盒单向通信，天然不兼容逆函数；基于快照的回滚极度拖慢运行性能，且无法撤销网络请求（如发邮件）。 | **明确否决** |

**推荐路径**：
遵循主流框架共识，**彻底放弃物理回退路线，全力实现上下文会话截断机制**。后续将在 `SessionManager` 中引入类似 `rollback(n_turns)` 截断历史数据或 `abort()` 中断当前思考流的核心能力。至于物理文件的安全兜底，完全交还给开发者的原生 Git 生态。

## 4. 约束、风险与未知项
- 当执行上下文弹栈（Pop History）时，需要如何通知终端或 UI 界面同步移除对应的聊天气泡，保持“视-脑一致性”？
- 如果在使用 MCP 工具的中途被阻断，是否会引发死锁或内存泄漏？

## 5. 否决方案
- **应用层维护底层快照 (Snapshotting)**：正如全网调研所指出的，物理快照恢复会导致 Agent 出现“失忆并发动语义回滚攻击”，重复执行不可逆外部调用，极具危险性，故全盘否决。
- **实现 MCP 工具层的强制撤销原语 (Undo Primitives)**：要求每个写操作提供撤销载荷。考虑到 MCP 协议的控制权不在我们手中，且外部 API（如发信）天然不可逆，强制所有工具支持 Undo 并不现实。未来若要处理此类问题，应在业务逻辑层考虑“事务补偿（Compensation）”而非底层框架级的撤销。
