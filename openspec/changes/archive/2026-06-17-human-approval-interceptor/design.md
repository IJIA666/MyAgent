## 背景

当前智能体具备直接执行终端命令的底层能力。安全防线仅依赖 `terminal-guard.ts` 中基于基础正则（阻断复合语法如 `&&`）及路径边界隔离的物理约束，无法拦截类似 `rm -rf` 等在语义层面构成破坏的高危合法命令。现有的终端拦截尝试直接把交互能力（`readline` 等）内嵌到工具层中，这严重污染了工具的纯无状态性，阻碍了内核对执行流的多端表现层（Web / CLI 等不同 UI 形态）解耦。

## 目标与非目标

**目标:**
- 将高危工具（如 terminal_command）的交互审批层从底层工具实现中剥离，交由系统级事件 `AgentEvent` 进行外抛。
- 在宿主介入审批时，安全、轻量地原地挂起大循环执行进度。
- 保证挂起状态防内存悬空，能在超时或主动断开连接时释放。
- 保证挂起过程对现有 `AgentLoop` 核心流引擎本身达成“零侵入”。

**非目标:**
- 绝不引入如 `LangGraph` 般的重型状态机编排引擎或依赖。
- 不提供跨进程会话级别的持久化中断保存机制（仅限于当前事件循环内存级别的阻塞）。
- 不引入类似 `Effect-TS` 这种重型函数式并发框架。

## 架构决策

**决策一：引入 `ApprovalService` 服务**
引入独立的 `ApprovalService` 维护所有阻塞态的异步凭证（Deferred Promise）。
- **Why?** 因为我们采用的是基于原生 ES6 的异步挂起机制（即“方案 B++”）。通过显式的服务集中管控 Promise 的 resolve / reject 句柄，我们能非常方便地注入统一的超时检测定时器、或接受外部网关层面的提前中断（rejectAll），这是内联裸写 Promise 难以实现的。

**决策二：采用生命周期插件中原地 `await` 挂起的方案 B++，弃用扩展 `AgentLoop` 控制流的方案 A**
- **Why X over Y?** 在原始的【方案 A】中，我们考虑通过让大循环 `yield` 出特殊的 `suspend` 状态来交出控制权。但研究发现这种做法会使业务逻辑（如判定审批决策是否需要写入白名单）向通用引擎 `AgentLoop` 泄露；且对于大模型并发输出的多个需要审批的 `tool_calls`，外置挂起极难协调顺序。
- 而采用【方案 B++】在 `BeforeTool` 插件层通过 `await ApprovalService.wait` 原地阻塞流的执行，能借用 Node.js 异步栈和事件循环自然等待。大循环 `AgentLoop` 仅仅只感受到一个执行时长较长的中间件，且 `for...await` 将保证工具是被**串行**逐个阻断询问的，避免了前端产生多个重叠弹窗与死锁风险。

**决策三：采用 `AgentEvent` 抛出通信信号解耦**
- **Why?** 确保内核引擎与最终端解耦。无论在 CLI 环境使用 `readline`，还是在 Web 客户端渲染模态框，或者甚至 MCP 客户端，只需订阅 `type: 'suspend'` 事件，并在渲染出 UI 获取结果后调用暴露出的 `ApprovalService.resolve` 即可，做到了真正的零 UI 耦合。

## 风险与权衡

- **[内存泄漏风险] 挂起的 Promise 未被唤醒致死锁** 
  - *缓解策略*: 在 `ApprovalService.wait()` 内置绝对时长的超时兜底（默认 5 分钟），超时自动转为 `deny` 决策；同时暴露主动阻断 `rejectAll()` 接口以备外部强行销毁。
- **[CI/测试死锁风险] 非交互环境无法唤醒**
  - *缓解策略*: 在 `ApprovalService` 中预留 `mockDecision` 机制或非 TTY 探测机制。测试时可直接令 `wait()` 退化为自动放行。
