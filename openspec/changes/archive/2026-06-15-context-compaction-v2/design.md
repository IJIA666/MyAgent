## 背景

MyAgent 目前采用同步阻塞式上下文压缩，当上下文即将触及模型 Token 上限时，会强制暂停当前交互，同步调用大模型对历史记录进行全文归纳。这种模式会导致用户界面长达数十秒甚至数分钟的假死；此外，完全交由 LLM 总结极其容易导致复杂标识符（UUID、绝对文件路径、端口号）被篡改遗漏，并可能因网络超时或审核拦截导致会话永久陷入“满负荷死锁”（变砖）。

## 目标与非目标

**目标:**
- 根除压缩卡顿：通过后台异步静默提炼机制，实现上下文截断时的“零延迟假死”。
- 保障执行无损：通过系统级逻辑（而非大模型总结）硬重载最近的活跃文件，确保文件路径和变量绝不失真。
- 实现确定性兜底：无论遭遇何种恶劣网络或并发限流，确保会话上下文总能被强制截断，永不“变砖”。
- 增强标识符与身份护栏：通过 Strict Identifier Preservation 与 Handoff Instructions 阻止模型角色错乱和标识符扭曲。

**非目标:**
- 暂不引入全套的 Subagent 调度框架与跨进程通信，仅在当前进程利用异步任务/后台线程机制完成提炼。
- 暂不实现长效向量化记忆检索（RAG），本方案仅解决当前会话窗口内的线性截断问题。

## 架构决策

1. **异步生成机制 (Post-Turn Hook)**
   - 决策：在交互过程中，通过 `afterTurn` 后置钩子，在后台静默发起 `generateSummary` 任务，将结果保存至本地状态文件。当主对话 Token 达到 80% 红线时，直接执行指针级的数组硬截断，瞬间读取已有的状态文件作为前缀。
   - 替代方案：等到爆仓再启动多线程 Worker 计算。原因：即使多线程不卡界面，依然要等大模型网络回包，只有“提前定期总结”才能做到真正的零阻塞截断。
2. **带预算的核心状态重载 (File Pinning)**
   - 决策：在内存中维护最近高频读写或系统调用的核心文件（限制最多 5 个）。当截断发生时，用原生代码而非 LLM，将这 5 个文件的最新内容以 `<transient_file>` XML 标签原封不动拼接进 System Context。预算上限为 25,000 Token，超限硬截断。
3. **两层防重构提示词 (Prompt Safeguards)**
   - 决策：硬编码防篡改机制。第一是 `Identifier Preservation` 禁令，禁止缩写任何 IP/UUID 等；第二是 `Handoff Instructions`（接班简报），在发生模型状态切换时，明确下发“你是 LEADER，仅做指挥无需重复工作”的指令体系。
4. **确定性静态兜底 (Deterministic Fallback)**
   - 决策：当辅助模型总结连续失败 3 次且当前已达满负荷红线，调用原生函数 `_build_static_fallback_summary`。提取最后执行的工具和上一条用户请求，拼接成纯文本字符串强行截断历史。保命优于完美总结。

## 风险与权衡

- **风险：重载的 5 个文件内容过大，导致截断后再次瞬间爆仓。** 
  -> 缓解策略：设定严苛的双层护栏——单文件上限 5,000 Token，总大盘上限 25,000 Token。超出的部分仅保留文件头尾。
- **风险：异步后台请求期间，用户又发送了大量消息（脏读/滞后）。** 
  -> 缓解策略：引入 `Summary Revision`。截断时，除了拼接最近的一份后台 Summary 之外，还保留从该 Summary 生成时刻至今的增量 `Raw Messages`，由主模型自行对齐上下文。
