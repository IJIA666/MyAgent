## 背景

针对 `src/core/usecases/`（22个文件）和 `src/ports/driven/`（13个文件）的物理平铺技术债进行重组，以子域内聚的 Clean Architecture 原则划分目录，提供优良的代码物理视图，为后续的测试套件同构对齐清理通道。

## 目标与非目标

**目标:**
- **用例层 100% 归纳**：将 `src/core/usecases/` 下的 22 个文件分配移入 `plugins/`、`engine/`、`brain/`、`security/` 四个新建的子目录。
- **接口层 100% 归纳**：将 `src/ports/driven/` 下的 13 个接口文件分配移入 `llm/`、`db/`、`tools/`、`session/`、`security/` 五个新建的子目录（`ApprovalPort.ts` 明确归入会话事件域 `session/`）。
- **级联对齐**：修正所有的 `src` 内部引用及 `test/` 单测的相对 `.js` ESM 后缀导入路径。
- **质量保证**：重构完成后，全量测试用例（205个）全绿通过，类型安全。

**非目标:**
- **坚决不动单测物理位置**：阶段一测试文件本身物理位置和命名保持在 `test/` 原分类中不动，以防止测试目录移动产生二次路径破裂，保障单测始终充当可靠的校验哨兵。
- **无破坏重构**：绝不改动任何核心用例和接口的逻辑行为、函数签名或类实现，纯物理移动。

## 架构决策

1. **子域职责划分网格**：
   - 遵循我们在 `exploration.md` 中订立的分类清单，将 22 个 usecase 实体与 13 个契约端口精准归入对应的微观域下。
2. **ESM 相对后缀级联更新流水线**：
   - 由于 IDE 重构工具无法在移动文件时自动校正 TS 模块引用的 `.js` 相对后缀（如 `from './prompts.js'`），我们将执行**“分批物理搬迁 -> 全局 ripgrep 扫描检测 -> 人工修正相对路径与后缀名”**流水线，实现 100% 的精准对齐。

## 风险与权衡

- **[风险点]：ESM 导入大面积死锁破裂，报错刷屏无法调试**
  - **[缓解策略]**：严格执行“原子化、分批迁移”：
    1. **第一批**：将 plugins 用例（9个）物理移动，用 ripgrep 修正相关源码及单测的引用，跑 `npm test` 确认全绿；
    2. **第二批**：将 engine/brain/security 用例（13个）物理移动，修补引用并跑测通过；
    3. **第三批**：将 driven 接口（13个）物理移动，修补引用并跑测通过。
    分批推进，杜绝一次性全盘移走。
- **[风险点]：重构修改中误删历史代码或 JSDoc 注释**
  - **[缓解策略]**：文件只做整体物理搬运和 import 修补，严禁改动任何业务逻辑和原注释内容，遵循最小重构。
