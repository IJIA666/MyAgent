# 业务能力: context-compaction

本规范定义了会话上下文的静默自适应压缩、物理会话轮换、时序 Checkpoint 注入、记忆重建，以及大模型覆写下的窗口管理与防漏自适应机制。

## 业务需求

### 需求: 自适应与手动触发压缩

系统必须支持根据当前激活模型的最大上下文 Token 水位线自适应触发静默压缩，同时必须在交互终端中提供手动一键强制压缩的入口。

#### 场景: 75% 水位自适应触发
- **WHEN** 会话即将向模型发起推理请求，且当前估算的总 Token 占用率达到模型最大上下文窗口的 75% 水位时
- **THEN** 系统必须静默执行上下文压缩流程，在控制台向用户抛出紧凑状态日志，并不影响当前轮次的 ReAct 执行

#### 场景: 终端手动 Compact 触发
- **WHEN** 用户在终端交互控制台或 slash 命令中显式触发 `/compact` 或执行 Compact 命令时
- **THEN** 系统必须跳过 Token 水位估算，立即强制触发会话上下文压缩逻辑

### 需求: 物理会话轮转与时序 Checkpoint 注入

上下文压缩执行成功后，系统必须在 SQLite 中物理结束当前 Session 并在数据库中建立关联的全新 Session ID，同时必须将更早的历史消息提炼为摘要，作为 `role: "user"` 的 `<conversation-checkpoint>` 消息块插入新会话队列最前端。

#### 场景: 会话物理轮转
- **WHEN** 压缩完成并即将保存新状态时
- **THEN** 系统必须调用本地 SQLite 数据库将旧会话标记为结束，生成全局唯一的关联新 Session ID，并使 `SessionManager` 与日志追踪仪物理绑定该新 ID

#### 场景: 时序 Checkpoint 追加
- **WHEN** 新会话初始化并准备组装发送给大模型的消息历史时
- **THEN** 系统必须将由大模型提炼出的历史总结文本包装在 `<conversation-checkpoint>` 标签中，以 `role: "user"` 的消息形态插入首个消息节点，并在文中标明“这是历史上下文而非新指令”的引导说明以防止指令偏航

### 需求: 大模型同步提炼摘要

系统在触发压缩时，必须通过调用大模型（LLM）对需要被剔除的旧历史消息进行语义分析与归纳，同步生成精简的开发轨迹摘要。

#### 场景: 同步调用 LLM 提炼摘要
- **WHEN** 触发压缩流程且确定需要归档旧对话时
- **THEN** 系统必须将需要剔除的 messages 列表拼装为总结 Prompt，通过 LlmDriver 发起一次大模型生成调用，提炼出不超过 1000 字符的摘要内容

#### 场景: 摘要提炼 Prompt 构造
- **WHEN** 生成提炼 Prompt 时
- **THEN** 提示词模板必须明确约束总结模型：
  1. 必须提炼并保留已达成的核心技术与开发设计决策；
  2. 必须提取所有已被创建或物理改动的文件路径及修改内容概要；
  3. 必须保留当前未被解决的核心痛点或下一阶段的技术任务目标；
  4. 必须过滤掉调试和执行工具时产生的海量冗余日志与反复失败尝试的干扰噪音；
  5. 必须硬性约束回复长度在 1000 字符以内以控制 Token 负载。

### 需求: 核心文件记忆重建

系统在轮换会话后，必须自动搜集并提取被剔除历史中最近被 `view_file` 或 `write_to_file` 访问过的关键文件路径，将其全量重新挂载至新会话头部以防止上下文断档。

#### 场景: 自动搜集挂载文件
- **WHEN** 会话物理轮换并重置上下文适配器时
- **THEN** 系统必须扫描被剔除历史中最近操作过的代码文件路径，读取其磁盘上最新内容，并在新会话头部的 user 消息中以 `<transient_file>` 标签形式打包作为轻量级附件挂载（受单文件 5k tokens 和总共 50k tokens 的硬性额度限制）

### 需求: 大模型与网络参数配置化管理

系统必须支持将每个内置大模型的上下文窗口（Context Window）以及调用选项（如采样温度、超时限制、最大重试次数、自定义请求头）在配置层进行声明，且必须提供通过通用环境变量覆写整个模型配置（包括 API 端点、实际调用模型名称、上下文窗口大小、温度、超时、重试及请求头）的能力，以实现 Claude Code 式的高度可扩展性。

#### 场景: 模型最大窗口与调用选项配置化
- **WHEN** 载入大模型连接配置时
- **THEN** 系统必须将各内置模型（如 `deepseek-v4-flash`）的上下文窗口属性（`contextWindow`）、温度（`temperature`）、重试次数（`maxRetries`）、超时时间（`timeout`）及自定义请求头（`headers`）写入其 `ModelProfile` 档案；在执行自适应 Token 压缩时，系统必须基于此配置中的 `contextWindow` 属性（而非硬编码名字判定）计算 75% 触发水位。

#### 场景: Claude Code 式模型与网络配置环境变量覆写
- **WHEN** 从 `BUILTIN_MODELS` 工厂解析模型连接配置（`getModelConfig`）时
- **THEN** 系统必须支持通过 `process.env` 进行动态覆写：
  1. 支持通过 `process.env.DEEPSEEK_MODEL`（或对应的其他模型覆写变量）动态改写最终发送给 API 的模型标识符名称，允许使用第三方兼容端点。同时，系统必须支持匹配并自动剥除模型名中的 `[1m]`、`[128k]` 等窗口后缀（以防第三方 API 接收到带后缀的模型名发生校验报错），并将解析出来的物理窗口大小在系统内自适应应用；
  2. 支持通过 `process.env.DEEPSEEK_CONTEXT_WINDOW` 动态覆写上下文物理窗口大小，系统必须支持对其指定的文本缩写（如 `1m` / `1M` 代表 1000000；`128k` / `128K` 代表 128000）进行解析还原。如果检测到模型名称被覆写但缺失窗口环境变量及后缀匹配时，系统必须自动将其退化至保守的上下文物理窗口限制（32k，即 32000 tokens）以防由于第三方小模型限制而导致溢出；
  3. 支持通过 `process.env.DEEPSEEK_TEMPERATURE` 动态覆写采样温度；
  4. 支持通过 `process.env.DEEPSEEK_TIMEOUT`（毫秒）动态覆写网络超时限制；
  5. 支持通过 `process.env.DEEPSEEK_MAX_RETRIES` 动态覆写网络请求的最大重试次数；
  6. 支持通过 `process.env.DEEPSEEK_HEADERS`（以换行符或分号分隔的名值对）动态覆写并解析为自定义 HTTP 请求头合并注入。
