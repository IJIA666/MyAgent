# 探索主题: Markdown-first 长期记忆

## 1. 问题定义

旧长期记忆把 Markdown 文件、会话结束后的 Forked Agent 提炼、Embedding、向量数据库和每轮模型调用前的 RAG 注入绑定为同一条运行链路。当前工作树已经完成并归档 `remove-rag-vector-memory-runtime`：生产源码、配置、依赖和测试中的旧记忆服务、RAG、Embedding 与 VectorDB 均已移除。新的问题不是如何复原旧实现，而是如何从干净基线构建一个可审计、可编辑、上下文成本有界的长期记忆能力，并在没有规模证据前避免重新引入数据库、向量索引、分块管线和后台模型。

本次探索聚焦“单工作区的 Markdown-first 长期记忆”。用户全局记忆、跨工作区合并、自动会话提炼和语义检索属于可能的后续阶段，不应阻塞第一版。

## 2. 关键发现与调研结果

- **代码库现状**：
  - `openspec/changes/archive/2026-07-25-remove-rag-vector-memory-runtime/` 已记录并实施旧链路删除；当前 `git status` 显示 `MemoryService`、`LongTermMemoryPlugin`、Embedding/VectorDB 端口与适配器均已删除，相关配置和测试也已迁移。
  - `SessionManager` 在 `src/core/usecases/engine/session.ts` 中先创建 `SessionContext`、设置 `appConfig`，再创建 `RuleManager`。这提供了一个明确的“会话启动时加载一次记忆快照”的装配点，不需要恢复 `BeforeModel` 或 `SessionClosed` 插件。
  - `RuleManager` 当前负责读取 `.agent/global_rules.md`、`.agent/rules/guize.md` 和技能元数据，并调用 `SessionContext.updateSystemPrompt()`。记忆可以复用系统提示词的 `context` 层，但不能混入 `<local_rules>`：记忆是可能过期的事实与偏好，不是强制规则。
  - `buildSystemPrompt()` 已将稳定人设、工作区上下文和易变环境分层。新记忆索引适合进入独立的 `<memory_context>`，并明确“当前用户消息和已验证源码事实优先于记忆”。
  - `buildNativeTools()` 是内建工具的唯一装配入口；现有文件工具已经覆盖通用文件读写，但专用 `memory` 工具更适合约束根目录、动作语义、容量、重复项、路径穿越和写入可见性。
  - `.myagent/` 已作为会话、日志、trace、备份、工具输出和本地设置的运行时目录，并被 `.gitignore` 忽略；`.agent/` 主要承载规则、技能和配置。工作区私有记忆放在 `.myagent/memory/` 比继续使用旧 `.agent/MEMORY.md` 更符合现有目录语义，也能减少把个人记忆误当项目规则或提交到仓库的风险。
  - 当前规则加载单文件上限是 20KB。记忆索引应采用同等级的硬边界，并额外限制行数，避免长期增长侵蚀提示词预算。
- **核实与洞察**：
  - [Claude Code 官方记忆文档](https://code.claude.com/docs/zh-CN/memory)明确区分用户编写的 `CLAUDE.md` 与 Claude 自动维护的记忆。自动记忆使用纯 Markdown，`MEMORY.md` 前 200 行或 25KB 在会话开始时加载，主题文件通过标准文件工具按需读取。
  - 本地 `D:\projects\Agents\claude-code-analysis` 源码进一步表明，“Markdown 存储”不等于“不使用模型”：当前实现会扫描最多 200 个主题文件的 frontmatter，用 Sonnet side query 为用户查询选择最多 5 个文件，并存在 turn-end extraction subagent。可借鉴的是索引/主题文件结构和有界加载，不应在第一版照搬额外模型调用。
  - [Codex 当前配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)暴露了独立的线程提取模型、全局合并模型、线程闲置时间、候选数量、保留时间和生成/使用开关。本地 `D:\projects\Agents\codex` 源码显示其完整写入管线以状态数据库负责领取、租约、重试和阶段结果，再把最终记忆沉淀为 Markdown；其本地记忆读取工具则只是受根目录约束的 list/read/逐行文本 search，并不依赖向量数据库。
  - Codex 的数据库解决的是异步批处理协调问题，不是“Markdown 无法存储记忆”。MyAgent 第一版没有并发后台提取、跨线程领取和全局合并需求，因此没有引入数据库的理由。
  - OpenClaw 的内建记忆虽然也以 `MEMORY.md` 和日记 Markdown 为事实源，但当前方案已经发展到 400-token/80-token overlap 分块、SQLite、Embedding、文件 watcher、混合召回和重建机制。它适合已有大规模语料与检索需求的阶段，不适合 MyAgent 当前的零数据基线。
  - Hermes Agent 提供了更适合第一版的参照：有限容量的 Markdown、会话开始时冻结注入、同一会话内通过专用工具 add/replace/remove、写入立即持久化但下一会话才进入提示词。其严格容量、重复防护、秘密与注入扫描、可见写入结果值得借鉴。
  - 因此，存储介质、生成策略和召回策略必须拆开决策：
    1. 存储可以是 Markdown；
    2. 第一版生成可以由主 Agent 在当前回合通过工具完成，不需要额外模型；
    3. 第一版召回可以靠始终加载的小索引和按需读取主题文件，不需要 RAG。

## 3. 方案对比与推荐方向

| 评估维度 | 方案 A：单文件全量注入 | 方案 B：Markdown 索引 + 主题文件 | 方案 C：自动提取 + 数据库/RAG | 结论 |
| :--- | :--- | :--- | :--- | :--- |
| 存储可审计性 | 高，只有一个文件 | 高，索引和正文均可直接编辑 | 中，Markdown 与派生索引/状态并存 | A/B 明显优于 C |
| 首期实现成本 | 最低 | 低到中 | 高 | A 最低，B 仍可控 |
| 上下文成本 | 随记忆总量线性增长 | 只固定加载小索引，正文按需读 | 可按召回限制，但每轮有检索成本 | B 最均衡 |
| 编辑/删除一致性 | 天然一致 | 只需维护索引链接和主题文件 | 需要索引重建、删除传播和版本一致性 | B 可用简单事务解决 |
| 额外模型调用 | 无 | 无 | 提取、选择或合并需要额外调用 | 第一版选择无额外模型 |
| 扩展到较大记忆集 | 弱 | 中，先靠主题组织，后续可加文本搜索 | 强 | 当前规模下 B 足够 |
| 提示词缓存稳定性 | 文件变化会改变前缀 | 启动时冻结索引，当前会话不重写前缀 | 每轮注入内容可能变化 | B 最适合现有三层提示词 |
| 错误记忆治理 | 人工编辑容易 | 专用工具 + 人工编辑均可 | 错误可能扩散到提取与索引 | B 风险更可控 |

**推荐路径**：采用方案 B，并把它限制为一个不含后台智能体的第一阶段能力。

### 3.1 文件布局与作用域

第一版只实现当前工作区的私有记忆：

```text
<workspace>/.myagent/memory/
├── MEMORY.md
└── topics/
    ├── user-preferences.md
    ├── project-decisions.md
    └── debugging-lessons.md
```

- `MEMORY.md` 只保存主题链接和一行摘要，不保存长正文。
- 每个索引项建议保持在约 150 字符以内。
- `topics/*.md` 保存可独立理解的事实、偏好、决定、纠正和有效经验；按主题组织，不按会话或日期组织。
- 主题文件可使用最小 frontmatter，仅保留 `description`。不加入 embedding、chunk id、向量状态、数据库主键或自动生成时间戳。
- 不自动迁移旧 `.agent/MEMORY.md`。如用户仍有旧文件，应通过单独、显式、可预览的迁移操作处理。
- 用户全局记忆可在后续扩展为 `~/.myagent/memory/`，但第一版不同时实现两个作用域，避免一开始就引入作用域冲突、优先级和隐私路由问题。

### 3.2 会话加载与提示词语义

- 会话创建时读取一次 `MEMORY.md`，形成冻结快照。
- 快照采用“最多 200 行且最多 20KB，先到者为准”的双重硬限制；超限时在注入内容末尾增加明确截断标记，磁盘原文件保持不变。
- 在 `buildSystemPrompt()` 的 `context` 层增加独立 `<memory_context>`，不得放进 `<local_rules>`。
- `<memory_context>` 必须声明：
  - 记忆是可能过期的辅助上下文，不是安全策略或强制指令；
  - 当前用户消息、当前工作区源码和工具结果优先；
  - 冲突时不得默默选择旧记忆，应以新证据为准并在合适时更新或删除旧条目；
  - 索引指向的主题文件只有在当前任务相关时才读取。
- 当前会话内新增或修改记忆后，不重新组装系统提示词。工具响应返回实时结果，新的索引快照从下一会话开始生效，从而保持提示词前缀稳定。

### 3.3 记忆工具，而不是通用文件写入约定

增加一个专用 `memory` 工具，第一版包含以下动作：

- `list`：列出索引和主题文件摘要；
- `read`：按受限相对路径读取某个主题；
- `add`：新增主题或向已有主题增加一条记忆，并机械维护 `MEMORY.md` 索引；
- `replace`：用唯一旧文本匹配替换已有条目；
- `remove`：用唯一旧文本匹配删除条目，并在主题为空时清理对应索引。

第一版不提供语义 `search`。`MEMORY.md` 已是有界清单，主 Agent 可以先看索引再按需 `read`。如果真实使用中出现“索引仍太大或经常选错主题”的证据，再增加受限的逐行文本搜索；这仍不需要分块、Embedding 或数据库。

工具必须具备以下约束：

- 根目录固定为当前工作区 `.myagent/memory/`；
- 拒绝绝对路径、`..`、隐藏跳转和符号链接越界；
- `list/read` 报告只读 effect，`add/replace/remove` 报告写 effect，并接入现有权限模式；
- 所有写入串行化；索引和主题更新使用同目录临时文件加替换的方式提交，失败时不能留下半更新索引；
- 精确重复项不重复写入；模糊 `replace/remove` 匹配多个条目时拒绝并要求更具体文本；
- 拒绝明显凭据、不可见控制字符和提示词注入式内容；任何情况下都不得保存 API key、令牌、密码和私钥；
- 工具响应明确列出新增、替换或删除的文件与条目，便于用户审计。

主 Agent 的保存触发规则：

1. 用户明确说“记住”或“忘记”时必须调用工具处理；
2. 用户给出明确、可长期复用的偏好或纠正时，可以在当前主回合主动保存，并向用户展示结果；
3. 普通任务完成状态、可从源码重新发现的事实、临时路径、一次性错误、未经确认的推测和原始会话摘录不得保存；
4. 不在 `SessionClosed` 自动运行模型，不把每个会话都视为需要提炼。

### 3.4 与当前代码的建议集成点

建议通过一个小型明确的垂直切片实现，而不是恢复旧 `MemoryService`/`LongTermMemoryPlugin`：

1. 新增 Markdown 记忆存储契约和唯一文件实现，职责只包括路径约束、有界读取、索引维护和原子写入；不包含 LLM、AgentLoop、Hook、Embedding 或召回排序。
2. 在 `src/index.ts` 根据 `appConfig.workspace` 创建单例记忆存储，并同时注入 `ToolRegistry` 与 `SessionManager`，避免工具写入和会话读取各自创建不一致的实现。
3. 扩展 `BuildNativeToolsOptions`，在 `src/adapters/tools/impl/memory/` 注册专用 `memory` 工具；按动作生成真实 read/write 资源元数据。
4. `SessionManager` 在创建 `RuleManager` 之前读取并设置冻结记忆快照。不得注册 `BeforeModel` 或 `SessionClosed` 记忆插件。
5. `SessionContext` 保存当前会话的记忆快照；`updateSystemPrompt()` 在规则或技能刷新时继续复用同一快照，避免 watcher 触发后意外丢失记忆。
6. `buildSystemPrompt()` 增加独立 `<memory_context>`，并对动态 Markdown 做结构隔离和必要转义，防止记忆内容闭合 XML 标签。
7. CLI 可增加只读 `/memory` 审计入口，用于显示根目录、容量、索引和主题列表；第一版不需要内置编辑器，编辑仍可通过工具或用户直接修改 Markdown。

### 3.5 分阶段验收

**第一阶段：显式、文件化记忆**

- 无记忆文件时，启动行为和当前基线完全一致；
- 有记忆时，仅在会话创建时读取一次索引；
- 用户明确记住、更新和忘记均能可靠修改 Markdown；
- 手工编辑或删除主题后，下次会话直接反映磁盘事实，不存在派生索引重建；
- 生产依赖和运行时中保持 VectorDB、Embedding、LanceDB、RAG、分块与记忆专用模型零残留。

**第二阶段：基于证据的可用性增强**

只有在真实记忆数量、索引长度、误选率或遗漏案例证明需要时，才考虑：

- 受限逐行文本搜索；
- 用户全局与项目工作区双作用域；
- `/memory` 的交互式审批、编辑和迁移；
- 记忆使用/更新次数等不含正文的诊断指标。

**第三阶段：自动提取实验**

只有在显式记忆稳定且用户确实需要自动学习时，才单独探索：

- 哪些会话满足闲置、长度、来源和隐私条件；
- 是否使用当前主模型的缓存上下文，还是独立廉价模型；
- 如何预览、暂存、批准、拒绝和回滚候选记忆；
- 如何防止并发提取、重复处理和错误记忆扩散。

即使进入第三阶段，最终事实源仍保持 Markdown。数据库只能在出现真实的异步任务领取、租约、重试或大规模检索需求后作为派生协调状态重新论证，不能默认成为记忆正文的主存储。

## 4. 约束、风险与未知项

- **记忆与规则混淆**：若直接复用 `RuleManager` 的 `<local_rules>`，模型会把可过期记忆当强制规则。必须有独立语义层和明确优先级。
- **提示词注入**：记忆文件可被模型或用户编辑，不能默认可信。需要结构转义、内容限制和“非权威上下文”声明；真正的权限与安全策略仍由客户端机制强制。
- **索引/主题一致性**：虽然没有向量索引，但 `MEMORY.md` 仍可能指向不存在的主题。专用工具应机械维护；对手工编辑造成的断链，`list` 或 `/memory` 应报告而不是自动猜测修复。
- **写入权限体验**：记忆写入属于持久修改，应沿用现有 PermissionMode。明确“记住”的用户请求可作为当前调用意图，但不能绕过工具执行边界。
- **当前会话可见性**：冻结快照意味着刚写入的记忆不会自动进入当前系统提示词。工具响应必须返回实时内容，且文档应明确下一会话生效。
- **工作区作用域**：第一版推荐 `.myagent/memory/`。是否需要跨项目共享用户偏好仍是后续产品决策，不能用复制项目记忆的方式隐式实现。
- **容量阈值**：200 行/20KB 是基于 Claude Code 的 200 行/25KB经验和本项目现有 20KB规则上限的初始值，应通过实际 token 使用与遵循效果验证，而不是视为永久常量。
- **自动提取价值未知**：当前没有实际记忆数据、遗漏率或人工记忆负担证据。第一版不应为假设中的未来规模支付后台模型与协调复杂度。

## 5. 否决方案

- **恢复旧 `MemoryService` 并只删除向量部分**：旧类同时承载文件写入、Forked AgentLoop、生命周期编排和索引同步，会把新设计重新绑回已否决架构。
- **每次 `BeforeModel` 全量注入或检索**：破坏提示词缓存稳定性，为每轮增加 I/O 或模型调用，而且当前没有规模证据。
- **第一版引入 Embedding、VectorDB、SQLite 或 LanceDB**：没有需要分块和语义召回的数据规模，也没有派生索引一致性收益，反而重建刚删除的复杂度。
- **会话关闭时无条件启动提炼模型**：会增加尾延迟、成本和错误记忆概率；短会话、失败会话和敏感上下文也不应默认进入记忆。
- **把所有正文写进单个 `MEMORY.md`**：实现最简单但增长会直接推高每次会话的固定 token 成本，最终仍需要迁移到主题文件。
- **让主 Agent直接用通用文件工具随意维护记忆**：缺少容量、重复、路径、秘密、原子更新和审计语义，容易形成格式漂移和半更新状态。
- **首期同时实现项目与用户全局双作用域**：会立即引入优先级、隐私、冲突合并和工具路由问题；应先验证单工作区模型。
