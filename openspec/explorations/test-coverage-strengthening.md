# 探索主题: 核心领域服务与基础工具单元测试覆盖率补强

## 1. 问题定义

在完成六边形架构解耦后，系统划分为核心层（Core）与适配层（Adapters）。虽然整体单元测试全部通过且拥有 100% 绿灯质量，但根据 Vitest 覆盖率分析，当前系统仍存在多处核心业务逻辑与常用基础工具的测试缺口（整体 Statement 覆盖率约 49%），这给后续的功能演进与重构埋下了回归隐患。

本主题旨在针对这些“被遗忘的测试死角”进行结构性分析，并确定后续的补强路线。

## 2. 关键发现与调研结果

### 代码库现状

通过执行 `npx vitest run --coverage`，我们对当前代码库的测试覆盖率现状进行了量化审计，主要发现以下几个重灾区：

1. **`core/usecases` 领域服务核心逻辑缺失测试（最关键的缺口）**：
   - **现状与定位**：该目录目前仅有 **43.39%** 的 Statements 覆盖率。这里是整个项目的核心调度枢纽，`SessionManager`、`AgentLoop` 都承载于此，测试密度理应最高。
   - **测试盲区**：虽然当前 Change 新增的 `loopback.test.ts` 已经覆盖了自唤醒锁下沉逻辑的核心路径，但 `AgentLoop` 本身的推理迭代逻辑（`chat` 中的 tool_calls 处理分支、大模型异常拦截分支）、`CompactionService`（上下文压缩服务）、`ContextRepository`（落盘/回滚）、`ToolDispatcher`（工具输出防爆/JIT 注入）等大部分分支依然处于裸奔状态。
2. **`adapters/input/interface` 的结构性覆盖盲区**：
   - **现状与定位**：目前该目录的 Statements 覆盖率仅为 **6.5%**。
   - **结构性原因**：`CliFacade` 作为 UI 渲染层与系统终端控制台高度强耦合（依赖 stdin/stdout 物理状态），传统的集成测试和 Mock 极其困难。
   - **测试补强可行性**：在六边形重构后，`CliFacade` 本身已经被成功降级为纯粹的“事件渲染器”。理论上，我们可以通过 Mock `SessionManager` 发射的 `agent_event` 广播事件流，针对 `handleAgentEvent` 内的各个 case 分支（如渲染 thinking, content, error, suspend, complete）补写单元测试，并断言控制台的渲染行为，即可低成本拉高覆盖率并确保渲染行为一致性。
3. **测试并发写竞态风险**：
   - `ContextRepository.ts` 和 `ToolDispatcher.ts` 的业务逻辑均高度依赖于 `process.cwd()` 下的物理文件读写（如 `.myagent/sessions`、`.myagent/temp`）。如果在测试中直接读写这些默认路径，不仅会污染生产环境文件，还会在 Vitest 并发测试中引发测试写竞态。

### 核实与洞察

- **覆盖率长效监测**：将 `@vitest/coverage-v8` 引入项目开发依赖是一项非常成功的决策。它可以在每个 Change 落地后留下基准快照，使得我们在后续迭代中可以随时监测测试覆盖率的涨跌趋势，建立长效质量监控。
- **沙箱隔离手段**：对于依赖物理 IO 的 `ContextRepository` 和 `ToolDispatcher`，我们已验证在单元测试的 `beforeEach` 中使用 `fs.mkdtempSync` 创建独立的沙箱目录并打桩/重定向工作区目录是 100% 消除并发执行竞态的成熟模式。
- **UI 事件 Mock 策略**：针对 `CliFacade` 结构性难以测试的问题，使用 Node 原生的 `EventEmitter` 进行 `agent_event` 的 Mock 派发，能低成本完成对控制台输出的流式渲染及阻塞中断分支验证。

## 3. 方案对比与推荐方向

| 评估维度 | 方案 A：单独立项，本期立即补强单元测试 | 方案 B：暂不起战役，随后续 Change 逐步伴随补充 (推荐) |
| :--- | :--- | :--- |
| **项目进度影响** | **高 ✗**：会阻塞接下来的核心功能演进（如多智能体、通道网关）。 | **无 ✓**：与正常的功能开发并行，不额外占用大段独立工时。 |
| **修改可控性** | **中 ✗**：在核心逻辑稳定但部分细节可能微调的前提下，单独立项容易造成测试代码编写后再次重构。 | **高 ✓**：在后续修改对应模块的代码时顺手补齐单测，测试与逻辑变更紧密对齐。 |
| **质量防护价值** | **即时 ✗**：仅能在静态层面提高覆盖率，无法通过业务功能回归来验证价值。 | **长效 ✓**：针对变动频繁的核心逻辑实行“改到哪里，补强到哪里”的动态防御。 |

**共识结论与后续路径**：
当前我们不需要针对此覆盖率数字立即发起独立的补强战役，以避免阻断系统功能演进。我们达成以下两点行动共识：
1. **长效趋势监控**：在后续所有的 Change 提请合流（`/openspec-sync`）前，将覆盖率数据的自检作为一个必经的安全哨卡，确保覆盖率趋势稳步向上。
2. **伴随式增量补强**：在接下来的业务 Change 开发中，只要涉及核心领域服务（如调整 `AgentLoop` 推理流、重构压缩/落盘逻辑）或适配层重构，必须强制**随手在对应的测试用例中补齐缺失的分支和单元测试**。补强重点锁定在：
   - `AgentLoop` 推理循环的主路径和工具分发分支测试。
   - `CliFacade.handleAgentEvent` 接收事件流各分支的渲染行为测试。

## 4. 约束、风险与未知项

- **UI 单元测试的 stdout 捕获**：在测试 `CliFacade` 的输出时，断言 `process.stdout.write` 或 `console.log` 的输出需要小心过滤终端的 ANSI 转义字符，以防在不同操作系统终端下断言失效。
- **`process.cwd()` 重定向清理**：伴随测试中如需重定向进程工作目录，必须在 `afterEach` 中还原 `process.chdir`，否则会引发 vitest 其它测试定位失败。

## 5. 否决方案

- **方案 A (单独立项本期硬攻)**：该方案因为会产生不必要的开发停顿，且在核心业务逻辑微调前过度编写静态单测容易产生重构浪费，被予以否决。

## 3. 方案对比与推荐方向

| 评估维度 | 方案 A：物理隔离与 Mock 结合的精细单元测试 (本期推荐) | 方案 B：模拟端到端 ChatUseCase 的集成测试 |
| :--- | :--- | :--- |
| **测试精准度** | **高 ✓**：可针对特定分支、错误处理（如写盘失败、JIT寻路截止、压缩失败熔断）进行精准打桩。 | **低 ✗**：仅能通过输入对话间接验证输出，难以精确控制底层的异常分支。 |
| **运行效率** | **极快 ✓**：每个单元测试执行时间通常在 10ms - 50ms 内，无需调起大模型。 | **较慢 ✗**：需要构造复杂的 ReAct 执行流和模拟大模型回包，运行成本高。 |
| **外部副作用** | **无 ✓**：通过拦截 `process.cwd()` 在系统临时目录生成沙箱，测试结束后自动清理。 | **中 ✗**：可能会在项目的实际目录下产生临时 sessions 和 temp 文件夹。 |
| **维护成本** | **低 ✓**：与六边形架构中高内聚的 usecase 层直接对齐，逻辑修改时单测易重构。 | **高 ✗**：大模型会话流程一旦调整，端到端断言容易大面积失效。 |

**推荐路径**：采用 **方案 A**。为缺失的领域服务和核心工具编写高精细度的单元测试：
1. **测试沙箱化**：在每个测试文件中，利用 `beforeEach/afterEach` 结合 `fs.mkdtempSync` 动态创建唯一的隔离文件夹，并通过对 `process.cwd()` 进行 mock 打桩来完成文件路径隔离。
2. **靶向补强**：针对 `CompactionService`, `ContextRepository`, `ToolDispatcher`, `search` 分别创建独立的单元测试文件，补齐对于分支条件的覆盖（例如压缩熔断次数 3 次后生成兜底摘要等）。

## 4. 约束、风险与未知项

- **`process.cwd()` 打桩风险**：在 Vitest 中 Mock `process.cwd()` 有时可能影响到 Node 内部模块（如 `path.resolve`）的全局隐式解析，需要小心隔离。若 mock 不便，可向服务构造函数传入或支持可选的 `workspacePath` 进行重构，或者采用在 beforeEach 中修改 `process.chdir`、在 afterEach 还原的优雅物理方案。
- **物理文件的测试清理**：临时沙箱文件夹必须在测试完毕后彻底递归删除，以防物理磁盘空间泄漏。

## 5. 否决方案

- **方案 B (端到端集成测试验证)**：该方案因为运行效率低下、分支控制薄弱、容易产生副作用且与六边形分层理念相悖，被作为核心覆盖手段予以否决。仅保留作为大流程保障。
